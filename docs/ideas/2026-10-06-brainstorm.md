- 작성일: 2026-10-06
- 기준: `docs/superpowers/specs/2026-10-05-momeokjo-design.md`(R1~R37), `docs/qa/2026-10-05-qa-plan.md`, `.superpowers/research/`(design-references, app-feel, share-and-risk), 현재 코드(`web/`, `shared/`, `worker/`)
- 원칙: **유저 편의 최우선, 최대한 덜 선택하고 최대한 좋은 결과.** 새 필수 입력은 늘리지 않아요. 아이디어마다 "선택을 늘리는가?"를 따로 적었어요.
- 상태: 아이디어 단계예요. 채택하면 SDD 규칙대로 스펙에 `R38~`을 먼저 추가하고 실패하는 테스트부터 써요.

## 0. 지금 상태 요약 (판단 근거)

- 뽑기는 전부 브라우저에서 해요(`shared/recommend.ts`의 `drawTrio`, 가중치 = 평점·리뷰 수 × 인원 보정 × 개인화 배수, 같은 그룹은 ×0.35).
- 개인화(`shared/personal.ts`)는 "최근에 연 곳·보낸 곳은 며칠 덜"과 "자주 연 그룹은 최대 ×1.45 더"예요. **그룹 가산은 같은 종류를 더 자주 내놓는 방향으로만 작동해요.** 점심은 어제와 다른 걸 먹고 싶은 경우가 많아서 이 부분은 반대 힘이 필요해요(B1).
- 공유는 3곳 텍스트 + `?t=…&h=…&r=…` 링크예요. 받은 사람은 3곳 시트를 보지만, **고른 결과를 돌려보낼 방법이 채팅방 말고는 없어요**(C1).
- `web/usePlaces.ts`는 반경이 바뀔 때마다 `/api/places`를 다시 불러요. 캐시 키가 거점 5 × 반경 19 = 95개라 캐시 적중률이 낮고, 슬라이더를 끌면 네트워크를 기다려요(QA S-7, F-2).
- 목록의 이름·좌표는 전부 비공식 상세 API에서 와요(로컬 API 응답은 ID만 저장). **비공식 API가 막히면 새 가게는 목록에 아예 못 들어와요.** 기존 데이터를 얼마나 오래 쓸지가 사실상 유일한 완충이에요(H1).
- 무료 플랜에서 조심할 것: CPU 10ms(1000m 캐시 미스 응답이 경계), D1 읽기 하루 500만 행(대량 워밍으로 한 번 소진), Workers 요청 하루 10만, subrequest 50.

#### C1 상세: 투표를 무료 플랜에서 어떻게 할까

- **투표 id는 공유할 때 브라우저가 만들어요.** `crypto.getRandomValues`로 base62 10자 → 공유 URL에 `&v={pollId}`. 공유 순간에는 서버를 부르지 않아요. 투표가 처음 들어올 때 행이 생겨요(만들기 API 없음).
- **테이블 하나:** `poll_votes(poll_id TEXT, voter TEXT, choice INTEGER, at INTEGER, PRIMARY KEY(poll_id, voter))`. `voter`는 기기 localStorage의 무작위 값(IP 저장 안 함). `choice`는 0(다 별로)~3. 다시 누르면 UPSERT로 바뀌어요. 가게 id는 URL에 이미 있으니 저장하지 않아요.
- **API:** `POST /api/polls/:id` `{voter, choice}` / `GET /api/polls/:id` → `{counts:[n0,n1,n2,n3], total}`. 집계는 `GROUP BY` 한 번이라 투표 수만큼만 읽어요(투표당 보통 2~8행).
- **"실시간"은 짧은 폴링으로:** 보이는 동안만, 처음 1분은 3초, 이후 10초, 10분 뒤 멈춤(다시 보면 한 번). 1인당 약 70회 요청.
  - 계산: 하루 투표 100건 × 4명 × 70회 ≈ 2.8만 요청 → Workers 하루 10만의 약 28%, D1 읽기는 수십만 행 수준(한도의 몇 %). **투표가 하루 300건을 넘으면 Workers 요청 한도가 먼저 위험해요.**
  - 완화: `GET`을 투표 id별 Cache API 2초 캐시로 감싸 D1 읽기를 줄이고, 투표 직후에는 응답에 집계를 실어 보내 추가 GET을 없애요.
- **Durable Objects 대안:** 투표 id별 DO + WebSocket Hibernation이면 1인당 연결 1번으로 진짜 실시간이 돼요. 무료 플랜에서도 SQLite 기반 DO를 쓸 수 있지만(요청·실행 시간 한도는 따로라 가격표 재확인 필요) 바인딩·마이그레이션(`new_sqlite_classes`)·연결 관리가 늘어요. **1단계는 D1 + 폴링, 투표가 하루 수백 건을 넘으면 DO로** 옮기는 순서를 추천해요.
- **남용 방지:** `pollId`·`voter` 정규식, 본문 1KB 상한, `Origin`/`Sec-Fetch-Site` 확인, 기존 `RATE_LIMITER`로 IP당 분당 제한, 투표 id당 최대 30표. Cron이 하루 지난 행을 지워요(삭제도 쓰기 행으로 세지만 투표 수만큼이라 작아요).
- **확정:** 보낸 사람 화면에서 1등 카드에 "여기로 가요"(A5)가 강조돼요. 동점이면 거리가 가까운 쪽.

## 2. Top 7 추천

선정 기준: 가치 ÷ 난이도가 높고, 선택을 줄이며, 무료 플랜 비용을 늘리지 않거나 오히려 줄이는 것. 투표(C1)는 난이도 3이지만 "함께 정하기"의 빈 고리라서 넣었어요. 날씨(D1)는 8순위예요(외부 API 하나가 더 늘어서).

### 1) A1 열자마자 3곳 — 가치 5 / 난이도 2 / 비용 없음

- **이유:** 앱을 여는 이유는 100% "뽑기"예요. 재방문자는 필터를 거의 안 바꾸고(R25로 저장됨) 바로 "모먹죠?"를 눌러요. 그 한 번을 없애면 열고 2초 안에 3곳이 보여요.
- **첫 조각:**
  - `web/App.tsx`: `data`가 처음 도착하고(`pending`과 상관없이 후보 ≥ 1), 공유 링크 파라미터가 없고, 재방문자(`mmj:tip-draw:v1`가 닫힘 상태이거나 `mmj:personal:v1`에 신호가 있음)이고, 사용자가 아직 아무것도 안 눌렀으면 `onDraw()`를 한 번 부르는 `useEffect` + `useRef` 가드.
  - 자동 뽑기는 `shown` 신호를 남기지 않게 `onDraw({ auto: true })` 인자 추가. 시트를 닫으면 오늘 날짜를 `mmj:auto-draw-off`에 저장해 그날은 다시 자동으로 띄우지 않아요.
  - 스펙에 R38 추가, `prefers-reduced-motion`이면 셔플 없이 바로.

### 2) B1 최근 먹은 종류 피로도 — 가치 4 / 난이도 1 / 비용 없음

- **이유:** 지금 R37의 그룹 가산은 "자주 간 종류를 더"만 해요. 어제 국밥 먹은 사람에게 오늘 또 국밥을 주는 방향이라 점심 결정과 맞지 않아요. 순수 함수 하나로 결과 체감이 크게 바뀌어요.
- **첫 조각:**
  - `shared/personal.ts`: `Signal`에 선택 필드 `cat`(카테고리 마지막 단계, `shared/category.ts`의 `lastLevel`) 추가, `isSignal`은 `cat` 없음 허용. `categoryFatigue(s, cat, now)` = 최근 36시간 `kakao_open`/`shared` 1번마다 ×0.6, 바닥 0.4. `personalMultiplier`에 곱하기.
  - `web/personal.ts`: 신호 기록 시 `cat` 채우기.
  - 테스트: `R37: 어제 카카오맵을 연 '국밥'은 오늘 ×0.6, 36시간 뒤엔 1`, `R37: 피로도와 30일 그룹 가산은 함께 곱한다`.

### 3) A2 부족하면 알아서 완화 — 가치 4 / 난이도 2 / 비용 없음

- **이유:** 지금은 0곳이면 빈 상태에서 사용자가 "어떤 조건을 풀지" 골라야 해요. 점심 5분 전엔 그 선택이 제일 귀찮아요. 1~2곳일 때도 3곳을 채워 주는 게 "덜 선택"에 맞아요.
- **첫 조각:**
  - `shared/recommend.ts`: `relaxToFill(places, filters, now, min = 3)` → `{ candidates, relaxed: RelaxStep[] }`. 순서: 평점 → 예산 → 카테고리 → 반경 +300m(최대 1000m). **영업 중은 풀지 않아요.** 완화로 들어온 곳은 `relaxedIds`로 표시.
  - `web/App.tsx` `onDraw`: `drawTrio` 전에 후보 < 3이면 `relaxToFill` 결과를 쓰고, 토스트 "조건에 맞는 곳이 적어서 평점 조건을 풀었어요". 완화로도 0곳이면 기존 빈 상태(R29) 유지.
  - `web/components/TrioSheet.tsx`: 완화로 들어온 카드에 "조건 밖" 옅은 표시.
  - 테스트: `R21: 후보 1곳이면 평점→예산 순으로 풀어 3곳을 채운다`, `R21: 영업 중 조건은 풀지 않는다`.

### 4) C1 받은 사람 원탭 투표 + 집계 — 가치 5 / 난이도 3 / 비용 낮음

- **이유:** 지금 흐름은 "3곳 공유 → 채팅방에서 '2번?' 'ㄱㄱ' '난 1번'"이에요. 받은 사람이 링크에서 번호를 한 번 누르면 끝나게 하면 그룹 결정이 앱 안에서 닫혀요. 로그인 없이 가능해요.
- **첫 조각 (D1 + 짧은 폴링, 위 C1 상세 참고):**
  - `migrations/0004_poll_votes.sql`: `poll_votes` 테이블 하나.
  - `shared/share.ts`: `shareUrl`에 `v`(pollId) 추가, `parseShareParams`에 `pollId`(정규식 `^[0-9A-Za-z]{10}$`).
  - `worker/app.ts`: `POST/GET /api/polls/:id` (zod 검증, `Origin` 확인, `RATE_LIMITER`), `worker/repo.ts`에 UPSERT·집계 쿼리. 카카오 호출 없음.
  - `web/components/TrioSheet.tsx`: 받은 시트에서 카드 번호 탭 = 투표, 아래 "다 별로". 집계는 카드 오른쪽 작은 숫자. 보낸 사람은 같은 링크로 다시 열면 집계를 봐요(보낸 쪽도 `mmj:polls`에 자기 poll id 저장).
  - `worker/maintenance.ts`: Cron에서 24시간 지난 투표 삭제.
  - 운영 지표: 하루 투표 수와 Workers 요청 수를 같이 봐서 300건/일을 넘으면 DO 전환 검토.

### 5) G1 거점당 1000m 한 번만 받기 — 가치 4 / 난이도 2 / 비용 절감

- **이유:** 사용자에겐 슬라이더가 즉시 반응하고(네트워크 대기 없음), 운영에겐 캐시 키가 95 → 5개로 줄어 캐시 적중률이 크게 올라가요. D1을 한 번 소진한 전례가 있어서 가장 값싼 보험이에요.
- **첫 조각:**
  - `web/usePlaces.ts`: 요청 반경을 `MAX_RADIUS`로 고정하고 의존성에서 `radius` 제거(거점만).

  - `worker/app.ts`: 서버는 그대로 둬도 동작해요(호환). 나중에 반경 파라미터를 1000만 받도록 좁혀요.
  - 스펙 R12·R16·R29·R34 수정, QA S-7 닫기. 느린 LTE 첫 로딩 시간은 P6 페르소나로 측정하고 필요하면 G2를 이어서.

### 6) F1 거점 고정 짧은 링크 — 가치 4 / 난이도 1 / 비용 없음

- **이유:** 판교·과천 팀은 매번 봉은사역(기본)에서 거점을 바꿔야 해요. `mmj.itmz.me/pangyo`를 슬랙 채널 북마크에 한 번 걸어 두면 팀 전체의 거점 선택이 사라지고, 그 자체가 사내 홍보 링크가 돼요.
- **첫 조각:**

  - `web/useSettings.ts`: 경로 거점이 있으면 저장 거점으로 덮어쓰고(북마크 용도라 저장), 주소창은 그대로 둬요.

  - 런북: frozen이 이틀 넘게 이어지면 H3(로컬 수집) 판단.

## 3. 하지 말아야 할 것 5개

1. **필터·설정·설문을 늘려서 정확도를 올리려는 것.** "매운 거 좋아해요?" 같은 취향 설문 온보딩, 메뉴 키워드 검색, 주차·키즈존 같은 필터는 정확도를 조금 올리는 대신 매번 선택을 늘려요. 정확도는 행동 신호(R37, B1, B2)와 컨텍스트(D1, D2)로 조용히 올려요.
2. **로그인·닉네임·계정 기반 기능.** 투표에 이름을 받거나 "내 히스토리"를 서버에 두는 순간 링크 하나로 끝나던 흐름이 깨져요. 투표는 기기 무작위 id로 충분하고, 누가 뭘 골랐는지는 채팅방에서 이미 알아요.
3. **임의 좌표·GPS 개방이나 요청만으로 거점 자동 생성.** 좌표마다 격자 수집(로컬 API)과 상세 보충이 새로 일어나서 D1·카카오 쿼터·subrequest가 한꺼번에 터져요(대량 워밍으로 D1을 한 번 소진했고, 격자 크롤링으로 계정이 차단된 사례도 있어요). 거점은 요청을 받아 사람이 판단해서 한 줄씩 늘려요.
4. **카카오 로컬 API 응답 저장, 그리고 크롤러·수신자 경로에서 비공식 API 새로 부르기.** 로컬 API는 ID만 저장한다는 정책(2026-08-26 답변)을 깨지 말고, 동적 OG·투표·공유 링크 열기에서는 D1에 있는 것만 읽어요. 미리보기 봇이나 링크 하나가 카카오 호출을 일으키면 차단과 쿼터 리스크가 바로 커져요. 브라우저에서 비공식 API를 직접 부르는 것도 같은 이유로 하지 않아요.
5. **비용을 모르고 붙이는 "실시간"과 이벤트.** 1초 간격 폴링, 이벤트마다 D1 한 행 쓰기, 화면 전환마다 새 API 요청은 무료 플랜의 Workers 요청 10만·D1 쓰기 10만을 조용히 먹어요. 폴링은 보일 때만·점점 느리게·10분 상한, 지표는 카운터 UPSERT나 Analytics Engine으로, 새 기능은 출시 전에 "하루 N명 기준 요청·읽기·쓰기" 계산을 스펙에 적어요.
