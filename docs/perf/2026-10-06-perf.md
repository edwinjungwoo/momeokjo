## 바꾼 것

1. **화면 번들에서 zod 제거** (−86KB 원문, −24.6KB gzip). 설정 복원(`shared/settings.ts`)은 손으로 검증하되 규칙은 예전 스키마와 같다(특성 테스트 추가). 이벤트 상수·세션 함수는 `shared/eventCore.ts`로 나눠 화면은 그쪽만 부르고, 서버 검증 스키마는 `shared/events.ts`에 남겼다. 회귀 방지 테스트: `test/shared/clientBundle.test.ts`가 `web/main.tsx`에서 닿는 모듈을 따라가며 zod 값 import가 없는지 본다.
2. **가게 사진을 WebP로**: 카카오 썸네일 서버는 정해진 크기만 허용한다(C120·C128·C160·C200·C320 가능, C100·C112·C144·C256·R480·R320은 403). 64px 칸에 C128(2배), `.fwebp.q70` 순서여야 품질이 WebP에 적용된다(`.q50.fwebp`는 2~3배 크다).
3. **로고·마스코트 WebP**: 각 포즈를 가장 크게 쓰는 높이의 2배로 줄였다(로고 126×56). 원본 PNG는 `public/brand`에 그대로 두어(아무도 부르지 않으면 비용 0) 다시 만들 수 있게 했다. `og.png`(크롤러)·아이콘(매니페스트·iOS)은 PNG 유지.
4. **첫 화면 경로**: Pretendard CSS를 `media="print" onload` 방식으로 비차단 로드(FCP −0.45초, 글꼴 자체는 원래도 `font-display: swap`이라 보이는 차이는 같다). 지도 SDK 로더를 `<link rel=preload>`로 앱 JS와 나란히 받고(`main.tsx`의 호출만으로는 앱 JS 실행 뒤에야 시작해서, 150ms RTT·1.6Mbps 로컬 측정에서 요청 시작이 약 0.16초 → 0.88초로 늦어진다. `/admin`에서는 쓰이지 않는 1.4KB가 되지만 정적 HTML이라 걸러낼 수 없어 그대로 둔다), `dapi.kakao.com`·`t1.daumcdn.net` preconnect, `img1.kakaocdn.net` dns-prefetch. SDK 로드는 React 렌더를 기다리지 않고 `main.tsx`에서 시작한다(`/admin` 제외). 첫 목록 요청은 250ms 디바운스를 거치지 않는다(거점을 바꿀 때만).
5. **다시 열면 바로**: 거점별 마지막 `/api/places` 원문을 IndexedDB(`mmj-cache`)에 저장(최근 3곳, 원문 300만 자 이하, 3일 지나면 안 씀 — 서버 상세 유지 기간과 같게, 스펙 §3.1 보수적 해석). 열면 저장본을 먼저 보여주고 바로 새로 받아 바꾼다. 24시간 넘은 저장본은 흐리게 두고 자동 뽑기(R39)는 새 목록을 기다린다. 새로 받는 데 실패하면 저장본을 둔 채 "최신 정보를 불러오지 못했어요"를 띄운다.
6. **목록 점진 렌더**: 60행만 먼저 그리고 끝(센티널)이 보이면 120행씩 붙인다. 늘린 개수는 줄이지 않는다. "후보 N곳"은 전체 수 그대로.
7. **좌표 소수 6자리**(약 0.1m): 17자리 좌표는 압축이 안 돼 목록 gzip의 1할이었다. 거리는 원래 좌표로 계산.
8. **`public/_headers`**: `/assets/*` 1년 immutable, `/brand/*`·아이콘·`og.png` 하루 + 일주일 SWR, `manifest` 하루. HTML은 기본값(`max-age=0, must-revalidate` + ETag) 그대로. Worker가 만드는 `/api/*` 응답에는 적용되지 않는다(문서 확인).

## 일부러 안 바꾼 것

- **`build.target: "es2022"`**: Vite 8 기본값(`baseline-widely-available`: Chrome 111·Safari 16.4)이 es2022보다 새롭다. es2022로 바꾸면 JS는 같고 CSS만 0.13KB 커져서 기본값을 둔다. `reportCompressedSize`도 기본이 켜짐.
- **Pretendard 자체 호스팅**: 글꼴 CSS를 비차단으로 바꾼 뒤에는 남은 비용이 글꼴 파일(첫 화면 8~10조각, 약 250KB)이고, 이는 같은 동적 subset을 우리 도메인에서 주어도 같다. 92개 woff2(약 2MB)를 저장소에 넣는 비용에 비해 이득(jsdelivr 연결 1개)이 작다. 첫 방문 전송량에서 가장 큰 항목이라 후속 후보: 화면 글자만 담은 작은 subset + 가게 이름은 시스템 글꼴.
- **TrioSheet·공유·통계 모듈 분리 로드**: TrioSheet는 재방문자 자동 뽑기로 바로 쓰이고 gzip 2KB 남짓, analytics·share도 1KB 안팎이라 나눌 이득이 없다. `/admin`은 이미 따로 불러온다.
- **목록 응답 영업시간·메뉴 압축**: 원문 기준 영업시간 24%, 메뉴 13%지만 gzip에서 빼 보면 영업시간은 4%(반복이 많다)뿐. 메뉴(gzip의 25%)는 결과 카드가 단건 응답 전에 바로 보여주는 데 쓰여서 유지. `url`(id로 만들 수 있음)도 gzip 4%라 API 모양을 바꾸지 않았다.
- **캐시 미스 서버 경로의 JSON.parse**: 900행 변환(메뉴·영업시간·강점·태그 파싱 + `toApiPlace`) 1.8ms, 직렬화 1.3ms(M 시리즈 node). 보내지 않는 필드 중 파싱하는 것은 태그(soloFriendly/groupFriendly 계산에 필요)와 4번째 이후 메뉴(0.7ms 중 일부)뿐이라 그대로 둔다. Observability의 CPU 시간으로 다시 확인.
- **지도 핀**: 대역 SDK 기준 900핀 생성·갱신은 필터 탭 지연에서 목록 대비 작았다(핀 DOM을 빼도 최악 216ms → 목록이 원인). 실제 SDK의 CustomOverlay 비용은 운영에서 확인.
- **아이콘 PNG 최적화**: `icon-192.png`(54KB)는 첫 로드에 낮은 우선순위로 받히지만 화면에는 안 쓰인다. 무손실 최적화 도구가 없어 그대로.
- **JSON 압축**: 커스텀 도메인 응답은 Cloudflare가 `Accept-Encoding`에 맞춰 br/gzip으로 압축한다. 운영에서 `content-encoding` 확인 항목에 넣었다.

## 캐시 미스 서버 CPU (Task 28)

`node scripts/bench-places.mjs [곳 수] [반복]` — 실제 `getPlaces → 목록 조각 → placesBody` 경로를 esbuild로 묶어 부르고 D1만 가짜로 바꾼다.
행은 상세 픽스처 12곳을 `parseDetail`로 읽어 `saveDetail`과 같은 열 모양으로 만들고 이름·메뉴·사진에 무작위성을 줬다(본문 원문 2,000곳 ≈ 1.37MB).
동대문 1000m를 흉내 내 반경 안 2,000곳(상자 안 2,616행), 봉은사역은 1,100곳(1,438행). 60회 중앙값, 가짜 D1이 행을 복사하는 시간은 뺐다. Node 26, Apple M 시리즈.

| 경로 | 동대문 2,000곳 | ×3 (Workers 어림) | 봉은사역 1,100곳 | ×3 |
|---|---|---|---|---|
| 전 (열 4개 JSON.parse → `toApiPlace` → `JSON.stringify`) | 8.7~8.9ms | ~26ms | 4.5ms | ~14ms |
| 후, `list_json` 있음 (조각에 거리만 붙여 이어 붙임) | **0.63~0.70ms** | **~2ms** | **0.36ms** | **~1ms** |
| 후, `list_json` 없음 (0005 전 행 — 열에서 만듦) | 10.6ms | ~32ms | 5.6ms | ~17ms |

×3이 8ms를 넘어서 `places.list_json`(0005)을 넣었다. 두 경로의 본문은 글자까지 같다(스크립트가 `sameBody: true`를 확인, 테스트로도 고정).
측정에 들지 않는 것: workerd가 D1 결과(행마다 ~0.7KB 문자열)를 JS 객체로 읽는 비용. 조각이 있는 행은 무거운 열을 D1에서 받지 않아 이 비용도 전보다 작다.
예전 행이 남아 있는 동안(Cron이 실행마다 200행씩, 수천 행이면 몇 시간)은 섞인 비율만큼 느리다 — 배포 직후 첫 몇 시간의 캐시 미스는 전과 비슷하다.
