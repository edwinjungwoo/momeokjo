# 모먹죠 (mmj.itmz.me) 설계 스펙

- 작성일: 2026-10-05
- 상태: 리뷰 대기
- 형태: 하루짜리 해커톤 프로젝트, 완전 공개 웹앱

## 1. 개요

선약 없는 평일 점심, 점심시간 5~10분 전에 "점심 고?" "ㅇㅇ"로 즉석에서 꾸려진 일행이 **어디 갈지 1분 안에 정하도록** 돕는 지도 + 큐레이션 앱.

- 기준점은 미리 정한 거점(`shared/hubs.ts`: 봉은사역(기본), 동대문역사문화공원역, 판교역) 중 하나를 고른다. 임의 위치는 받지 않는다.
- 반경(100~1000m), 인원, 카테고리, 1인 예산, 평점, 영업 여부로 후보를 좁히고 "모먹죠?" 버튼으로 서로 다른 후보 3곳을 가중 랜덤으로 뽑아 함께 보여준다. 일행에게는 3곳을 한 번에 공유해서 고르게 한다.
- 원칙: **최대한 덜 선택하고 최대한 좋은 결과.** 새 필수 입력은 늘리지 않고, 이 기기에서의 행동(카카오맵 열기, 공유)으로 다음 뽑기를 조용히 개인화한다(R37).
- 데이터는 카카오 로컬 API(공식)와 카카오맵 장소 상세(비공식)를 쓴다.

### 개발 원칙

- **데이터가 최우선이다.** 데이터 파이프라인을 먼저 만들고, 데이터 품질 수용 기준(§7)을 통과한 뒤에 UI를 만든다.
- **SDD:** 이 문서가 기준이다. 요구사항은 `R*`(기능), `Q*`(데이터 품질) 번호로 추적한다. 구현하다가 스펙과 다른 판단이 필요하면 스펙을 먼저 고친다.
- **TDD:** 모든 `R*`는 실패하는 테스트로 시작한다. 테스트 이름은 요구사항 번호로 시작한다(예: `R7: 전골(중) 67,000원은 대표가격 계산에서 제외`).

## 2. 아키텍처

```
[브라우저 React SPA]
  │  GET /api/places?hub&radius            GET /api/places/:id
  ▼
[Worker: Hono]
  ├─ 정적 에셋 (Vite 빌드 결과)
  ├─ PlacesService ── TileCollector ──▶ 카카오 로컬 API (공식, REST 키)
  │                └─ DetailEnricher ─▶ 카카오맵 장소 상세 (비공식)
  ├─ D1: places, place_details, tiles
  └─ scheduled(): 모든 거점 반경 1km 사전 수집 (5분마다)

필터링, 정렬, 뽑기는 전부 브라우저에서 한다 (반경 내 가게는 수백 곳 이하라 전송 가능).
```

## 3. 외부 데이터 소스

### 3.1 카카오 로컬 API (공식)

- `GET https://dapi.kakao.com/v2/local/search/category.json`
- 파라미터: `category_group_code=FD6`, `rect=minLng,minLat,maxLng,maxLat`, `page=1..3`, `size=15`, `sort=accuracy`
- 헤더: `Authorization: KakaoAK {KAKAO_REST_KEY}`
- 한 번의 검색으로 최대 45개(15 × 3페이지)까지만 받을 수 있다. 응답의 `meta.total_count`로 실제 개수를 확인한다.
- **저장 금지 정책 (2026-10-05 확인):** 카카오맵 API FAQ(2022-10-18)는 "로컬 API 등을 호출하여 응답받은 결과 데이터를 별도로 저장하여 사용하는 것은 허용하지 않습니다"라고 한다. 2026-08-24 답변에 따르면 임시 저장도 불허다. 2026-08-26 답변에 따르면 "장소ID만 기록하고 나머지 표시 정보는 실시간 호출하는 방향은 운영 정책상 허용 가능"하다 (https://devtalk.kakao.com/t/faq-api/125610, https://devtalk.kakao.com/t/api-20/151271). 그래서 **로컬 API 응답에서는 장소 ID만 저장한다.** 이름, 좌표, 카테고리는 요청을 처리하는 동안 메모리에서만 쓴다(간식 제외 판단).
- 보수적으로 읽어서, 화면이 기기에 두는 목록 저장본(R45, IndexedDB에 `/api/places` 응답 원문 — 표시 정보는 상세 응답에서 온 것)도 서버 상세 유지 기간(R9, 3일)보다 오래 쓰지 않는다(`shared/placesCache.ts`의 `PLACES_CACHE_MAX_AGE_MS`; 24시간 넘으면 흐리게 보여주고 자동 뽑기는 새 목록을 기다린다).

### 3.2 카카오맵 장소 상세 (비공식)

- `GET https://place-api.map.kakao.com/places/panel3/{id}`
- 필수 헤더: `pf: PC`, `Origin: https://place.map.kakao.com`, `Referer: https://place.map.kakao.com/`, 브라우저 User-Agent, `Accept: application/json`. 헤더가 없으면 406이 반환된다(2026-10-05 로컬에서 확인).
- **Cloudflare 엣지에서 호출 가능 확인 (2026-10-05, `wrangler dev --remote`, 3건 모두 200).** 응답 크기는 가게당 50~120KB다.
- 사용하는 필드 (2026-10-05 id 27531028 "중앙해장" 응답으로 확인):
  - 평점: `kakaomap_review.score_set.average_score`, `kakaomap_review.score_set.review_count`
  - 강점: `kakaomap_review.score_set.strength_counts[{id,count}]` + `kakaomap_review.strength_description[{id,name}]`
  - 메뉴: `menu.menus.items[{name, price}]`
  - 영업시간: `open_hours.week_from_today.week_periods[].days[]`. 각 day는 `day_of_the_week_desc`("월(10/5)")와 함께 `on_days.start_end_time_desc`("11:30 ~ 22:00", 자정을 넘기면 "16:00 ~ 02:00"), `on_days.break_times_desc`(["14:30 ~ 18:00 브레이크타임"]) 또는 `off_days_desc`("휴무일")를 가진다.
  - 예약/태그: `place_add_info.ai_mate.store_facility_icons[].text`와 `place_add_info.store_facility_icons[].text`(예: "예약가능"), `place_add_info.full_detail_infos[].items[].contents[].label`(예: "혼밥", "단체석", "회식장소", "점심특선")
  - 메뉴 가격은 -1이나 0일 수 있다(가격 미표기).
  - **장소 요약 (표시 정보의 출처):** `summary.name`, `summary.category.{name1,name2,name3}`, `summary.point.{lat,lon}`, `summary.address.road`(없으면 `disp`), `summary.phone_numbers[0].tel`
- 형식이 바뀌거나 막힐 수 있으므로 **모든 필드는 optional로 파싱**하고, 하나가 실패해도 나머지는 살린다.
- **차단 시 대안:** Worker IP에서 호출이 막히면, 로컬 Node 스크립트로 수집해서 `wrangler d1 execute --remote`로 D1에 적재한다. 이 경우 Cron 상세 수집은 끈다.

## 4. 데이터 모델 (D1)

```sql
CREATE TABLE tiles (
  key TEXT PRIMARY KEY,           -- R1 격자 키
  collected_at INTEGER NOT NULL,
  place_count INTEGER NOT NULL,
  saturated INTEGER NOT NULL DEFAULT 0  -- 최대 깊이에서도 45 초과면 1
);

-- 로컬 API 응답에서는 격자별 장소 ID만 기록한다 (§3.1 저장 금지 정책)
CREATE TABLE tile_places (
  tile_key TEXT NOT NULL,
  place_id TEXT NOT NULL,
  PRIMARY KEY (tile_key, place_id)
);
CREATE INDEX idx_tile_places_place ON tile_places(place_id);

-- 장소 상세(§3.2) 응답에서 얻은 정보. 상세를 한 번도 성공하지 못한 장소는 name 등이 NULL이다
CREATE TABLE places (
  id TEXT PRIMARY KEY,
  status TEXT NOT NULL,            -- 마지막 시도 결과 'ok' | 'failed'
  name TEXT, category_name TEXT, category_group TEXT, lat REAL, lng REAL, address TEXT, phone TEXT,
  rating REAL, review_count INTEGER, price INTEGER,
  menus_json TEXT, hours_json TEXT, strengths_json TEXT, tags_json TEXT, bookable INTEGER,
  fail_reason TEXT,
  fetched_at INTEGER NOT NULL
);
CREATE INDEX idx_places_lat_lng ON places(lat, lng);

-- 앱 전역 상태 (0003). place_blocked_until = 상세 API 쿨다운이 끝나는 시각(epoch ms, R10),
-- tiles_changed_at / unfetched_cleared_at = Cron 미수집 확인 신호(R11)
-- detail_mode = R44 강등 모드 {"mode":"frozen","since","until"}, block_count:{KST 날짜} = 그날 쿨다운 횟수(차단이 있는 날만, 기록할 때 지난 날 키를 지움)
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
CREATE INDEX idx_places_status_fetched_at ON places(status, fetched_at); -- R11 만료 후보
-- meta에는 R38 날짜별 D1 사용량도 둔다: d1_read:{UTC yyyy-mm-dd}, d1_written:{...} (90일 뒤 R35 정리 때 지움)

-- R35 익명 사용 이벤트 (0004). IP·User-Agent·위치·자유 입력은 저장하지 않는다. 90일 보관
CREATE TABLE events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts INTEGER NOT NULL,   -- 서버가 확인한 epoch ms (클라이언트 시각 ±10분 밖이면 서버 시각)
  day TEXT NOT NULL,     -- KST yyyy-mm-dd
  hour INTEGER NOT NULL, -- KST 0–23
  anon TEXT NOT NULL, session TEXT NOT NULL, hub TEXT NOT NULL, type TEXT NOT NULL,
  place_id TEXT, props TEXT  -- 검증한 props의 짧은 JSON
);
CREATE INDEX idx_events_day ON events(day);
CREATE INDEX idx_events_type_day ON events(type, day);
```

카카오맵 링크는 `https://place.map.kakao.com/{id}`로 만든다.

## 5. 기능 요구사항

### 5.1 수집: 가게 목록 (공식 API)

- **R1 고정 격자.** 위도 간격 `0.00225°`(약 250m), 경도 간격 `0.0028°`(위도 37.5° 기준 약 250m)로 지도를 나눈다. 격자 키는 `"{floor(lat/0.00225)}:{floor(lng/0.0028)}"`이다. `tilesCoveringCircle(center, radius)`는 원과 겹치는 모든 격자 키를 반환한다.
  - 예: 반경 0이면 중심이 속한 격자 1개, 반경이 격자 경계를 넘으면 인접 격자 포함
- **R2 쿼드트리 분할.** 격자(또는 하위 사각형)를 rect 검색했을 때 `meta.total_count > 45`이면 4등분해서 각각 다시 검색한다. 최대 깊이는 4다(약 15m). 최대 깊이에서도 45를 넘으면 받은 45개의 ID를 기록하고 `tiles.saturated = 1`로 표시한다. 기록하는 것은 **장소 ID뿐**이고, 카테고리가 `dessert`인 장소는 기록하지 않는다(판단은 메모리에서만). 한 격자 안에서 id가 중복되면 한 번만 기록한다.
- **R3 격자 TTL.** `tiles.collected_at`이 7일 이내인 격자는 다시 수집하지 않는다.
- **R4 격자 ID 갱신.** 격자를 다시 수집하면 그 격자의 ID 목록을 새 결과로 바꾼다. D1 쓰기를 아끼려고 지금 기록된 ID를 읽어서 빠진 ID만 지우고(DELETE 한 문장) 새 ID만 넣는다(INSERT OR IGNORE 한 문장) — 바뀌지 않은 격자는 `tile_places`에 쓰지 않고 수집 시각만 갱신하며, ID가 바뀌었을 때만 `tiles_changed_at`(Cron의 미수집 확인을 깨우는 값)을 올린다. `places`의 상세 행은 지우지 않는다(폐업 판단은 범위 밖).
- **R5 카테고리 그룹.** `category_name`을 `>`로 나눈 두 번째 단계로 매핑한다.

  | 그룹 키 | 표시 | 카카오 2단계 |
  |---|---|---|
  | `korean` | 한식 | 한식 |
  | `chinese` | 중식 | 중식 |
  | `japanese` | 일식 | 일식 |
  | `western` | 양식 | 양식, 패밀리레스토랑 |
  | `asian` | 아시안 | 아시아음식 |
  | `snack` | 분식·패스트푸드 | 분식, 패스트푸드, 도시락 |
  | `bar` | 술집 | 술집 |
  | `dessert` | (항상 제외) | 간식 |
  | `etc` | 기타 | 위에 없는 모든 값 (뷔페, 샐러드, 치킨, 퓨전요리 등) |

  `dessert`는 수집 단계에서 기록하지 않고, 상세 카테고리가 `dessert`로 나온 장소도 API 응답에서 제외한다. 감사 리포트(Q4)는 `etc`로 떨어진 2단계 값 목록을 출력하고, 필요하면 이 표를 고친다.

### 5.2 수집: 상세 정보 (비공식 API)

- **R6 상세 파싱.** §3.2의 응답을 섹션별 zod 스키마로 검증해 `PlaceSummary`(이름, 카테고리 원문, 좌표, 주소, 전화)와 `PlaceDetail`로 변환한다. 요약에서 이름이나 좌표가 없으면 표시할 수 없으므로 `schema` 실패로 본다. 나머지 섹션은 optional이다.
  - `rating`: `average_score`. 리뷰가 0개면 null
  - `strengths`: `strength_counts`를 count 내림차순으로 정렬해 상위 2개 id를 `strength_description`의 이름으로 바꾼 것
  - `bookable`: `place_add_info`가 없으면 null이다. 있으면 두 `store_facility_icons` 목록 중 하나라도 text가 "예약가능"이면 true, 아니면 false다.
  - `tags`: `full_detail_infos[].items[].contents[].label`을 순서대로 중복 없이 모은다(최대 30개).
  - `menus`: 가격이 1 이상인 메뉴만, 최대 20개
  - JSON이 아니거나 최상위 구조가 다르면 `status='failed'`, `fail_reason='schema'`
- **R7 대표 가격.** 메뉴 가격 중 `5,000 ≤ price ≤ 30,000`인 값들의 중앙값을 100원 단위로 반올림한다. 해당 값이 없으면 null이다. 값이 짝수 개면 가운데 두 값의 평균을 쓴다.
  - 예: [14000, 16000, 16000, 67000] → [14000, 16000, 16000] → 16000
- **R8 영업시간 정규화.** §3.2의 day 목록을 `Hours = { [요일 0(일)-6(토)]: Array<[openMin, closeMin]> | "closed" }`로 정규화한다. 분 단위이고, 자정을 넘기면 close가 1440보다 크다(예: "16:00 ~ 02:00" → [960, 1560]). 브레이크타임은 구간에서 빼서 나눈다(예: "11:30 ~ 22:00" + "14:30 ~ 18:00" → [[690, 870], [1080, 1320]]). `off_days_desc`가 있으면 "closed"다. 요일은 `day_of_the_week_desc`의 첫 글자(일월화수목금토)로 정한다. 하나라도 파싱할 수 없으면 전체를 null로 한다.
- **R9 상세 TTL과 재시도.** `status='ok'`이면 3일 + id별 지터, `status='failed'`이면 6시간이 지나기 전에는 다시 가져오지 않는다. 지터는 id의 해시로 정하는 0~24시간 값이라 한꺼번에 수집한 가게들이 같은 시각에 만료되지 않고 하루에 걸쳐 흩어진다(만료 여부를 따지는 모든 곳에서 같은 값을 쓴다). 갱신에 실패해도 이전에 성공한 표시 정보는 지우지 않는다(상태만 failed로 바꾼다). 호출마다 네트워크 오류나 5xx가 나면 지수 백오프(250ms, 1000ms)로 최대 2번 재시도한다. 4xx는 재시도하지 않는다.
- **R10 배치 처리.** 한 번의 실행(요청 또는 Cron)에서 외부 호출 예산은 `SUBREQUEST_BUDGET`(기본 40, 무료 플랜 한도 50)이다. 격자 수집이 예산을 먼저 쓰고, 상세 보충은 남은 예산 안에서 기준점에서 가까운 순으로 동시성 3으로 처리한다. 대상은 기준점을 덮는 격자에 기록된 ID 중 상세가 없거나 만료된 것이고(ID 중복 제거), 격자 중심이 기준점(여러 거점이면 가장 가까운 거점)에 가까운 순서(같으면 id 오름차순)로 고른다. 배치 중에 403이나 429가 나오면 차단 신호로 보고 그 배치의 나머지 호출을 멈추고, `meta.place_blocked_until`에 지금 + 30분을 기록한다. 이 시각 전에는 어떤 실행(요청 보충, R13, Cron, R31)도 상세 API를 부르지 않는다(R13에서 403/429가 나와도 같이 기록한다). 한 번에 보충하는 가게 수는 `DETAIL_BATCH_SIZE`(기본 10)다. 응답이 커서 무료 플랜 CPU 한도(10ms)를 지키기 위해 작게 잡았다.
- **R44 상세 차단 시 강등 모드.** 비공식 상세 API가 막혀도 "어제까지의 정보로 잘 뽑히는 앱"이 되게 한다. R10 쿨다운이 새로 걸릴 때마다 `meta.block_count:{KST 날짜}`를 1 올리고(이전 쿨다운이 아직 걸려 있는 동안의 보고 — 요청 보충·Cron·R13이 겹친 같은 사고 — 는 쿨다운만 늘리고 세지 않는다), 같은 KST 날에 3번째가 되면 `meta.detail_mode`에 `{"mode":"frozen","since":지금,"until":지금 + 24시간}`을 기록한다(이미 frozen이면 since는 그대로 두고 until만 늘린다). `until` 전에는 frozen이다(24시간 뒤 자동 해제).
  - frozen이면 어떤 실행(요청 보충, R13, Cron, R31)도 상세 후보를 읽지도 상세 API를 부르지도 않는다(D1 읽기도 아낀다). 격자 수집(공식 API)은 그대로 한다. 기존 상세는 만료와 상관없이 그대로 보여준다. 새로 생긴 가게는 frozen 동안 목록에 못 들어온다(이름·좌표가 상세에서 오기 때문).
  - R12 응답에 `detailsFrozenSince`(frozen이면 since, 아니면 null)와 `detailsNewestAt`(응답에 실린 가게 중 가장 최근에 상세를 가져온 시각, 없으면 null)을 싣는다. frozen이면 `pending`이 줄지 않으므로 화면은 pending 때문에 다시 요청하지 않고, 서버는 pending이 남아 있어도 응답을 캐시한다.
  - 화면(R29 상태 줄): frozen이거나 가장 최근 상세가 4일보다 오래됐으면 "평점·메뉴는 N일 전 기준이에요"(N = 가장 최근 상세로부터 지난 날 수, frozen이면 최소 1)를 보여준다. 순수 함수 `shared/freshness.ts`.
  - 평점이 하나도 없어도(모든 detail의 평점·리뷰가 null) 거리·다양성·개인화만으로 3곳을 뽑는다(R21 테스트로 고정).
  - 런북: frozen이 이틀 넘게 이어지면(하루 3번 차단이 매일 반복) 로컬 수집 경로(§3.2, 브레인스토밍 H3)를 판단한다.

### 5.3 사전 수집 (Cron)

- **R11 거점 유지 수집.** Cron `*/5 * * * *`로 실행한다. `shared/hubs.ts`의 모든 거점의 반경 1000m(`PREWARM_RADIUS`)가 대상이고, 외부 호출 예산 하나를 거점끼리 나눠 쓴다.
  - 거점들이 덮는 격자의 합집합(중복 제거)을 한 번에 처리한다. 실행(5분)마다 시작 거점을 하나씩 돌려서 앞 거점이 예산을 다 써도 다음 실행에는 다른 거점이 먼저 쓴다. 겹치는 거점이 있어도 한 실행에서 같은 격자·장소를 두 번 확인하거나 부르지 않는다.
  - (1) 만료된 격자를 수집하고 (2) 남은 예산으로 상세 정보(없거나 만료된 것)를 보충한다. 만료된 상세의 갱신은 Cron만 한다(R12).
  - D1 읽기 절약: 만료 후보는 `places(status, fetched_at)` 인덱스로 "ok는 3일 전, failed는 6시간 전"보다 오래된 행을 상태마다 오래된 순 300행(`EXPIRED_SCAN_LIMIT`)까지만 읽고(행마다 `tile_places`를 place_id 인덱스로 붙여 거점 격자의 것만 후보로), 지터는 메모리에서 다시 확인한다. 거점 밖 행(예전 warm의 ASEM 1500m 고리, 격자 밖 단건 조회)은 갱신되지 않아 인덱스 맨 앞에 계속 남으므로 상태마다 커서 `meta.expired_from:{status}`(`{from, at}`)를 둔다: 첫 거점 행의 fetched_at, 거점 행이 없었으면 지나간 마지막 행(범위를 다 읽었으면 그 범위 끝). 다음 실행은 거기부터 읽는다. 거점 행은 갱신되면 앞으로 가므로 커서 앞에 새로 생기지 않고, 격자 ID가 바뀌었을 때(`tiles_changed_at > at`)만 처음부터 다시 읽는다. 그래서 실행당 만료 조회는 상태마다 최대 300행 + 붙인 격자 행(로컬 측정 약 900행/실행)이다. 갱신한 상세도 다음 만료에 id별 지터(0~24시간)가 그대로 붙어 3일 파도가 다시 몰리지 않는다. 미수집 ID(격자에는 있고 places 행이 없는 것)는 `meta.tiles_changed_at`(격자 ID가 실제로 바뀔 때만 갱신, R4)이 `meta.unfetched_cleared_at`(Cron이 미수집 0개를 확인한 시각) 이후일 때만 훑는다. 쿨다운 중이거나 예산이 없으면 상세 후보를 읽지 않는다. `pending`은 세지 않는다(R31 warm 응답에서만 센다).
  - 할 일이 없으면 D1 조회만 하고 끝난다. 새 거점의 최초 대량 수집은 R31로 한다.
  - R38: 그날(UTC 기준, 한국 시각 09시에 초기화 — D1 무료 한도와 같은 날짜) D1 읽기가 소프트 한도를 넘었으면 수집·보충을 건너뛰고(`skipped: "read_budget"`) 캐시된 데이터만 보여준다. KST 04:00~04:04에 걸리는 실행은 먼저 R35 보관 정리를 한다(한도를 넘은 날에도).

### 5.4 API

- **R12 `GET /api/places?hub&radius`.**
  - 검증: `hub`는 `shared/hubs.ts`의 거점 id, `radius`는 100~1000m의 50m 배수. 위반하거나(모르는 거점 포함) 임의 lat/lng를 보내면 400과 `{error: "invalid_params"}`를 반환한다. 좌표는 서버가 거점 목록에서 찾는다(남용과 비용 방지; 임의 좌표는 관리용 R31/R32만).
  - 화면은 반경과 상관없이 항상 `radius=1000`을 요청하고 반경은 브라우저에서 거른다(R42). 서버는 50m 단위 반경을 계속 검증하지만(호환), 어떤 반경이 와도 거점의 1000m 목록 하나만 계산·캐시해서 같은 본문(`radius: 1000`)을 준다 — 캐시 키가 거점당 하나라 반경을 바꾼 요청으로 캐시를 우회해 D1을 읽게 할 수 없다.
  - 캐시: Workers Cache API(`caches.default`)에 `https://cache.mmj/places?hub&v={응답 형식 버전}` 키(거점당 하나)로 저장하고, 다음 요청은 D1을 읽지 않고 캐시로 답한다. 시간은 `placesCacheTtl`: 공식 API 실패가 섞인 응답(`stale`)만 저장하지 않는다. `incompleteTiles > 0`(예산·요청 제한으로 격자를 다 못 모음)이면 10초. 그 밖에 `pending === 0`이거나 상세 가져오기가 멈췄으면(`detailsPaused` — R10 쿨다운·R44 frozen, 아무도 pending을 줄일 수 없다) 60초(`Cache-Control: public, max-age=60, s-maxage=60`), pending만 남았으면 10초 — 같은 거점을 폴링하는 여러 화면이 계산(과 요청 보충 시작) 하나를 나눠 쓴다. 요청 제한에 걸린 요청도 10초 캐시를 받으므로, IP 하나를 함께 쓰는 사무실이 분당 10회를 넘겨도 매번 D1을 읽지 않는다. 브라우저에 주는 응답은 항상 `no-store`다. 키는 거점 수(5개)뿐이다(예전에는 거점 × 반경 19단계 = 95개). 응답 형식 버전은 4(반경을 키에서 뺌, `detailsPaused` 추가).
  - 처리: `tilesCoveringCircle`로 격자를 구하고, 만료/미수집 격자를 예산 안에서 동기적으로 수집한다(ID만 기록). 격자-장소 상태(`tile_places` + places 메타)는 요청마다 한 번만 읽어서 목록 필터, `pending`, 보충 대상 고르기에 같이 쓴다. 그다음 D1에서 덮는 격자에 기록된 가게 중 상세가 있고 거리 ≤ radius인 것을 조회한다. R13 단건 조회로만 저장된 가게는 목록에 넣지 않는다. 상세가 아직 없는 장소는 좌표를 모르므로 응답에 넣지 않고 `pending`으로만 센다. 상세를 한 번도 가져오지 않은 가게가 있으면(쿨다운 중이 아니면) `ctx.waitUntil`로 그 가게들만 R10 배치를 시작한다. 만료된 상세는 그대로 보여주고 갱신은 Cron(R11)에 맡긴다.
  - 응답:
    ```ts
    {
      center: { lat, lng }, radius,
      places: Array<{
        id, name, group, category, lat, lng,
        distance,        // m, 정수
        walkMinutes,     // R26
        url, photoUrl,   // address, phone은 화면이 쓰지 않아서 목록에는 싣지 않는다 (R13 단건에는 있다)
        detail: null | {
          rating, reviewCount, price, menus /* 목록은 상위 3개 */, hours, strengths, bookable,
          soloFriendly, groupFriendly  // R19 판단 결과 (태그 원문은 보내지 않는다, 규칙은 shared/friendly)
        }
      }>,
      pending: number,   // 덮는 격자에 ID는 기록됐지만 상세를 아직 한 번도 가져오지 않은 장소 수 (반경이 아니라 격자 기준)
      incompleteTiles: number, // 예산 부족으로 이번에 못 수집한 격자 수
      stale: boolean,    // R14 공식 API 실패 (요청 제한으로 건너뛴 것은 아님)
      detailsPaused: boolean, // R10 쿨다운·R44 frozen으로 상세 가져오기가 멈춤 (화면은 pending 때문에 폴링하지 않는다)
      detailsFrozenSince: number | null, // R44 강등 모드 시작 시각 (epoch ms)
      detailsNewestAt: number | null     // R44 응답에 실린 가게 중 가장 최근 상세 시각
    }
    ```
  - `Cache-Control: no-store`
- **R13 `GET /api/places/:id`.** 단일 가게 정보를 반환한다(형식은 R12의 원소와 같고, distance와 walkMinutes는 빠지며 address·phone과 메뉴 전부(최대 20개), 상세를 가져온 시각 `fetchedAt`(epoch ms, R48)을 준다 — 목록 원소에는 없다). 거점 격자(모든 거점의 1000m 격자)에 기록되지 않은 ID는 상세를 가져와 보여주기만 하고 저장하지 않는다(성공이든 실패든 — 임의 숫자로 D1을 키울 수 없고, Cron이 갱신하지 않는 행이 만료 조회에 쌓이지 않게). 그래서 거점 밖 공유 링크는 열 때마다 R15 제한 안에서 상세를 한 번 부른다. 화면은 카드를 열 때 이것을 한 번 불러 목록 원소의 상세와 바꾼다. id는 숫자 1~15자리만 허용하고 아니면 404다. 표시 정보가 없으면 R15 제한 안에서 동기적으로 한 번 상세를 가져온다(최근 6시간 안에 실패했거나 R10 쿨다운 중이면 시도하지 않음). 그래도 없으면 404다.
- **R14 장애 대응.** 공식 API가 실패하고(쿼터 초과, 5xx, 타임아웃) 해당 격자에 만료된 캐시가 있으면 그 캐시로 응답하고 `stale: true`를 준다. 캐시도 없으면 502와 `{error: "upstream"}`을 반환한다.
- **R15 남용 방지.** 외부 호출을 일으키는 요청(만료/미수집 격자가 있는 R12, 동기 보충이 필요한 R13)은 IP당 분당 10회로 제한한다(Workers Rate Limiting 바인딩). 초과하면 외부 호출 없이 캐시로만 응답한다 — 못 모은 격자는 `incompleteTiles`, 못 채운 상세는 `pending`으로 남고 `stale`은 주지 않는다(`stale`은 R14 실패만). 이 응답은 10초 캐시된다(R12). 캐시로만 응답할 수 있는 요청은 제한하지 않는다.

### 5.5 추천 로직 (브라우저, `shared/recommend`)

- **R16 반경.** 반경 슬라이더 하나로 정한다: 100~1000m, 50m 단위, 기본 500m. 현재 값을 "반경 500m · 도보 약 10분"(R26)처럼 보여준다. 점심시간 프리셋(30/60/90분)은 없앴다. 상한 1000m는 Cron이 유지하는 반경(R11)과 같다. 슬라이더는 네트워크를 기다리지 않고 바로 반영된다(R42: 거점의 1000m 목록을 이미 갖고 있고 브라우저에서 거리로 거른다).
- **R17 영업 중 필터.** 기본 ON. 현재 시각 `now`(KST)와 `now + 30분`이 모두 같은 영업 구간 안에 있을 때만 영업 중으로 본다. 전날 밤부터 이어지는 구간(close > 24:00)도 고려한다. 자정에서 끝나는 구간이 다음 날 0시에 시작하는 구간과 맞닿아 있으면 하나의 연속된 구간으로 본다(다음 날이 휴무면 자정에서 끝난다). 오늘 요일의 정보 자체가 없으면 "영업 정보 없음"으로 취급한다. 영업시간이 null이면 "영업 정보 없음"으로 표시하고 필터를 통과시킨다.
- **R18 필터.**
  - 카테고리: 다중 선택, 아무것도 선택하지 않으면 전체(`bar` 제외). `bar`는 "술집 포함" 토글을 켰을 때만 들어간다(기본 OFF).
  - 1인 예산: 전체 / 1만 이하 / 1.5만 이하 / 2만 이하. "전체"가 아니면 price가 null인 곳은 제외한다.
  - 최소 평점: 무관 / 3.5+ / 4.0+. "무관"이 아니면 rating이 null인 곳은 제외한다.
  - 반경: 거리 ≤ radius
- **R19 인원 휴리스틱.** 인원 선택지는 1 / 2 / 3 / 4+이고 기본값은 2다.
  - 아래 두 판단은 서버가 `shared/friendly` 규칙으로 계산해 `soloFriendly`/`groupFriendly`로 내려준다.
  - 1명: 혼밥 친화(`category_name`에 국밥, 해장국, 라멘, 라면, 분식, 덮밥, 돈까스, 우동, 국수, 김밥, 패스트푸드 중 하나라도 포함하거나, tags에 "혼밥"이 있음)면 가중치 ×1.5
  - 4명 이상: `snack` 그룹 제외. tags에 "단체석", "회식장소", "모임맛집" 중 하나라도 있으면 ×1.3, `bookable === true`면 추가로 ×1.3
  - 2~3명: 보정 없음
- **R20 정렬.** 거리순(기본) / 평점순(null은 맨 뒤) / 가격순(오름차순, null은 맨 뒤).
- **R21 3곳 뽑기.** 필터를 통과한 후보에서 서로 다른 곳을 최대 3곳, 가중 랜덤으로 뽑는다(비복원 추출, `shared/recommend.ts`의 `drawTrio`).
  - 가중치 = `base × 인원 보정 × 개인화 배수(R37) × 시간대 배수(R50)`
  - `base = max(0.3, rating − 3) × log10(reviewCount + 10)`, rating이 null이면 `base = 0.5`
  - 다양성: 한 곳을 뽑을 때마다 같은 그룹(`group`)의 남은 후보는 다음 뽑기에서 가중치 ×0.35(같은 그룹이 2곳 뽑혔으면 ×0.35²). 강제가 아니라서 그룹이 하나뿐이어도 3곳을 채운다.
  - 개인화 배수가 0인 곳("여긴 빼줘")은 후보에서 뺀다.
  - "다시 뽑기"는 이번 세션에서 이미 보여준 곳을 빼고 뽑는다. 남은 곳이 3곳보다 적으면 남은 곳을 먼저 넣고, 제외 목록을 비운 뒤 나머지를 채운다(`reset: true`, "후보를 다 돌아서 처음부터 다시 뽑아요" 토스트; 후보가 3곳 이하이면 "조건에 맞는 곳이 N곳뿐이에요"). 한 결과 안에서는 중복이 없다. 거점을 바꾸면 제외 목록을 비운다.
  - 후보가 0~2곳이면 R41로 덜 중요한 조건부터 자동으로 풀어 3곳을 채운다. 풀어도 1~2곳이면 있는 만큼만 보여준다. 풀어도 0개면 "조건에 맞는 곳이 없어요" 토스트를 띄우고, 리스트 자리의 빈 상태(R29)에 지금 켜져 있는 조건만 푸는 버튼을 보여준다: "영업 중만 해제", "평점 무관", "예산 전체", "카테고리 전체", "반경 +300m"(최대 1000m).
  - 난수 함수는 주입받는다(테스트에서 결정적으로 검증하기 위해).
- **R22 슬롯 셔플과 3곳 결과.** "모먹죠?"를 누르면(재방문자는 R39로 열자마자 한 번 자동으로) 결과 시트(모바일은 바텀 시트, 데스크톱은 지도 위 오버레이) 이름 자리에 후보 이름이 약 0.8초 동안 바뀌다가 멈춘다. 이름이 바뀌는 간격은 50ms에서 140ms로 점점 늘어난다(감속). `prefers-reduced-motion`이면 셔플과 애니메이션 없이 바로 결과를 보여준다.
  - 멈추면 시트에 작은 후보 카드 3장이 쌓인다. 머리: `thumbsup` 마스코트 + "모먹죠가 고른 3곳"(공유 링크로 받았으면 "공유받은 후보 3곳"; 3곳보다 적으면 그 수) + "눌러서 메뉴와 영업시간을 볼 수 있어요". 카드: 56px 사진(없으면 크림 + 흐린 `dish`), 왼쪽 위 번호 1/2/3, 이름, 사실 줄 "도보 N분 · ★4.3 · 근처 상위 N%"(곧 마감·지금 닫힘이면 강조 글자), "[이유(R46)] · 카테고리 · 1인 가격".
  - 카드를 누르면 그 자리에서 펼친다(아코디언, 한 번에 하나): 영업 상태 · 오늘 영업시간 · 리뷰 수, 강점, 메뉴(R13을 그때 한 번 불러 전체 메뉴로; 데스크톱은 최대 5개), 조용한 "카카오맵에서 보기" 링크, "여기로 가요"(R47), "여긴 빼줘"(R37). 4명+면 맨 위에 "전화로 자리 확인"(R49), 맨 아래에 정보 확인 시점(R48).
  - 아래 행동: 주 버튼 "공유"(3곳 모두, R23), 보조 "다시 뽑기". 모바일은 시트 바로 아래 뽑기 바가 "다시 뽑기"(보조 모양)를 맡아서 시트 안의 "다시 뽑기"는 숨긴다. 작게 "정보 출처: 카카오맵". 시트가 화면 높이의 60%를 넘으면 안쪽만 스크롤하고 행동 영역은 아래에 붙어 있다.
  - 지도: 뽑힌 3곳은 번호(1/2/3)가 든 큰 마커와 이름표로 강조하고, 먼저 3곳이 모두 보이게 맞춘다(시트가 가리는 만큼 여백을 더 둔다). 카드를 펼치면 그 핀으로 이동하고 그 핀의 이름표만 남긴다. 결과 3곳 중 하나를 목록이나 핀에서 누르면 그 카드를 펼친다. 다른 곳을 누르면 그 한 곳의 상세 카드(R28)를 결과 위에 열고, 닫으면 결과 3곳으로 돌아간다.
  - 셔플이 끝나면 15ms 진동(`navigator.vibrate`)을 준다. 폴링으로 목록이 바뀌어도 결과 3곳은 그대로 두고 최신 객체(상세)로만 바꾼다. 뽑은 뒤 뽑기 버튼 문구는 "다시 뽑기"가 된다.
  - 경쟁 상태: 셔플 중에는 뽑기 버튼을 비활성화(`disabled`)하고 "고르는 중…"으로 표시하며, Esc·시트 닫기·목록/핀 선택을 받지 않는다. 거점이나 반경을 바꾸면 진행 중인 셔플을 취소하고 결과 3곳을 비운다(공유 링크 불러오기도 취소). 펼친 카드가 바뀌면 이전 R13 요청은 취소한다.
- **R23 공유.** "공유" 버튼을 누르면 보여주는 후보 전체(최대 3곳)를 아래 텍스트(`shareText`)로 공유한다. 터치 기기(`pointer: coarse`)이고 `navigator.share`가 있으면 클릭 핸들러 안에서 바로 `navigator.share({ title: "모먹죠", text })`를 호출하고, 사용자가 공유 시트를 닫으면(AbortError) 아무것도 하지 않는다. 그 밖의 경우(데스크톱, 미지원, 공유 실패)는 클립보드에 복사하고 "복사했어요" 토스트를 띄운다. 복사도 실패하면 "복사하지 못했어요"를 띄운다. 공유·복사에 성공하면 그 곳들을 R37 `shared` 신호로 남긴다.
  ```
  🍚 점심 고? ({인원}명 · {거점 이름} 반경 {radius}m)
  1. {가게명} · {카테고리 마지막 단계} · ★{rating} · 도보 {walkMinutes}분
  2. ...
  3. ...
  이 중에 어디 갈래요? 👉 https://mmj.itmz.me/{거점 id}?t={id1},{id2},{id3}&r={radius}
  ```
  평점이 null이면 `★` 부분을 생략한다. 인원이 4+이면 "4명+"로 쓴다. 3곳보다 적으면 그만큼만 줄을 쓰고, 한 곳만 공유하면(상세 카드의 "공유") 마지막 줄은 "여기 어때요? 👉 …"이다.
  - 공유 URL을 열면 해당 거점(경로 `/{거점 id}`(R43) 또는 예전 링크의 `h`, 거점 목록에 있는 id만)과 반경(`r`, 50m 단위만)을 적용하고, `t`(쉼표로 이은 숫자 1~15자리 id, 중복 제거, 최대 3개; 잘못된 칸은 무시)의 가게를 **목록 응답과 상관없이** R13으로 동시에 받아 "공유받은 후보 N곳" 시트로 보여준다(목록 요청이 실패해도 보여준다; 도보 시간은 현재 거점 기준). 일부를 찾지 못하면 찾은 곳만 보여주고 "N곳은 찾지 못했어요"를 한 번 띄우고, 하나도 못 찾으면 "공유된 가게를 찾지 못했어요". 공유받은 곳은 R37 `received` 신호로 남긴다(빼둔 곳이어도 보여준다).
  - 예전 링크 `p`(숫자 1~15자리 하나)도 읽는다(`t`가 있으면 `t` 우선). id가 하나뿐이면 "공유받은 곳" 상세 카드(R28)로 연다. 예전 링크의 `lat`/`lng`는 무시한다. 파라미터를 적용한 뒤에는 주소창에서 지운다(새로고침하면 저장값으로 돌아간다).
  - 링크 미리보기는 `index.html`의 정적 OG 태그로만 한다: `og:title` "모먹죠 - 점심 고?", `og:description`, `og:image` `https://mmj.itmz.me/og.png`(1200×630 PNG), `twitter:card` `summary_large_image`. 장소별 동적 OG와 카카오 SDK 공유는 하지 않는다.
- **R24 거점 선택.** 기준점은 `shared/hubs.ts`의 거점 목록 중 하나이고 기본은 봉은사역이다: 봉은사역(37.514255, 127.060234), 동대문역사문화공원역(37.565100, 127.007490), 판교역(37.394777, 127.111590; 신분당선·경강선 출구 사이), 내방역(37.487659, 126.993600), 정부과천청사역(37.426505, 126.989868). 거점 짧은 링크 `/{거점 id}`(R43)로 열면 그 거점으로 시작한다. 상단 바의 거점 칩을 누르면 거점 메뉴가 열리고, 고르면 목록·지도·뽑기가 그 거점 좌표를 쓴다. 거점을 바꾸면 열린 카드와 뽑기 상태(이미 뽑은 목록 포함)를 비운다. 내 위치·지도에서 찍기는 없다. 거점을 늘리려면 배열에 한 줄을 더하면 되고, 화면 메뉴·설정/공유 검증·Cron(R11)이 자동으로 따라간다.
- **R43 거점 짧은 링크.** `/{거점 id}`(`/bongeunsa`, `/ddp`, `/pangyo`, `/naebang`, `/gwacheon`; 끝 `/` 허용, 그 밖의 경로 조각이 더 있으면 무시)로 열면 그 거점으로 시작하고 저장한다(R25, 슬랙 채널 북마크·사내 위키용). 주소창은 그대로 두되, 그 뒤 손으로 거점을 바꾸면 주소를 `/`(쿼리 없이)로 돌린다(새로고침이 북마크 거점으로 되돌려 방금 고른 거점을 덮지 않게, `shared/settings.ts`의 `urlAfterHubChange`). 단, 공유 링크(`t`·`p`가 있음)의 경로 거점은 예전 `h`처럼 이번에만 적용하고 저장하지 않으며, 파라미터를 지울 때 주소를 `/`로 돌린다(받은 사람의 저장 거점을 덮지 않게). 모르는 경로(`/brand`, `/admin` 등)는 무시한다. 순수 함수 `shared/share.ts`의 `parseHubPath`. Worker는 `/api/*`만 먼저 처리하고 나머지는 정적 에셋 → 없으면 SPA 대체 응답(`index.html`, 200)이라 서버 변경은 없다. 거점 id는 `public/`의 최상위 파일·폴더 이름과 `admin`·`api`·`assets`와 겹치면 안 된다(테스트로 고정).
- **R25 설정 기억.** 필터(반경, 인원, 카테고리, 예산, 평점, 영업 중, 술집 포함, 정렬)와 거점 id(`hubId`, 목록에 없으면 기본 거점)를 localStorage에 저장한다. 예전 저장값의 `center`, `lunch`는 버린다. 읽기/쓰기는 try/catch로 감싸고, 실패하면 기본값을 쓴다. 공유 URL 파라미터가 있으면 저장값보다 우선한다(저장값을 덮어쓰지는 않음). R43 거점 경로(공유 링크가 아닐 때)는 저장값을 덮어쓴다.
- **R26 도보 시간.** `walkMinutes = ceil(직선거리 × 1.3 / 70)` (우회 계수 1.3, 분속 70m)

- **R37 자동 개인화 (기기 안에서만).** 서버로 보내지 않고 localStorage `mmj:personal:v1`에만 둔다(읽기·쓰기는 try/catch, 실패하면 이번 세션만). 관리 화면은 없다. 순수 함수는 `shared/personal.ts`, 저장은 `web/personal.ts`.
  - 신호(가게 id, 그룹, 시각, 세부 종류 `cat`(R40, 카테고리 마지막 단계; 예전 신호에는 없음)): `kakao_open`(카카오맵 링크를 엶, 강), `shared`(공유한 결과의 각 가게, 중), `received`(공유 링크로 받은 가게, 중), `shown`(뽑기 결과로 보여준 가게, 약). 30일 지난 신호는 버리고 최근 300개만 남긴다.
  - 가게별 배수 = `max(0.05, Π(1 − 강도 × 감쇠(경과)))` × 그룹 가산. 강도: kakao_open 0.85, shared 0.5, received 0.5, shown 0.25. 감쇠는 3일(shown은 1일)에 걸쳐 1 → 0 직선(미래 시각은 방금으로 본다). 방금 간 곳·보낸 곳은 며칠 덜 나오게 한다.
  - 그룹 가산: 최근 30일에 카카오맵을 열었거나 공유한 가게의 그룹은 1번마다 +0.15, 최대 ×1.45.
  - 최종 배수 = 최근 신호 배수 × 그룹 가산 × 종류 피로도(R40).
  - "여긴 빼줘": 펼친 결과 카드의 조용한 글자 버튼. 누르면 배수 0(목록·지도·뽑기 후보에서 모두 빠짐)이 되고 결과에서 그 카드가 사라진다. 5초 동안 "다음부터 빼고 골라요" + "되돌리기" 토스트를 보여주고, 되돌리면 원래대로 돌아온다.
- **R39 열자마자 3곳.** 재방문자는 "모먹죠?"를 누르지 않아도 목록이 오면 한 번 자동으로 뽑아 결과 시트를 띄운다(탭 1번 → 0번).
  - 조건(모두): 재방문자(첫 방문 안내를 닫았거나 R37 신호가 하나라도 있음), 공유 링크(`t`·`p`)로 열지 않음, 이번 탭 세션(sessionStorage `mmj:auto-draw:v1`)에서 아직 자동으로 뽑지 않음, 사용자가 아직 아무것도 하지 않음(문서의 첫 `pointerdown`·`keydown`·`wheel`·`touchstart`), 오늘(KST) 자동 뽑기를 끄지 않음(`mmj:auto-draw-off` ≠ 오늘), 거점 목록이 다 왔고(pending 폴링이 끝났거나 처음부터 다 찬 응답, 또는 24시간 안의 기기 저장본 — 폴링 중인 일부 목록으로는 뽑지 않고, 폴링으로 후보가 늘어도 다시 뽑지 않는다) 뽑을 후보(R41 완화 포함)가 1곳 이상.
  - 자동 뽑기는 보통 뽑기와 같지만 R37 `shown` 신호를 남기지 않고, 첫 방문 안내를 닫지 않으며, R35 `draw` 이벤트에 `props.auto: true`를 붙인다. `prefers-reduced-motion`이면 셔플 없이 바로 보여준다(R22와 같음).
  - 자동으로 뜬 시트를 (다시 뽑지 않고) 닫으면 오늘 날짜(KST)를 `mmj:auto-draw-off`에 저장해서 그날은 다시 자동으로 띄우지 않는다. localStorage·sessionStorage를 못 쓰면 이번 페이지에서만 기억한다.
- **R40 최근 먹은 종류 피로도.** 그룹 가산(R37)은 같은 종류를 더 자주 내놓는 방향으로만 작동해서, 짧은 반대 힘을 더한다. 최근 36시간 안에 카카오맵을 열었거나(`kakao_open`) 공유한(`shared`) 가게와 세부 종류(`cat` = 카테고리 마지막 단계, `shared/category.ts`의 `lastLevel`; 예: 국밥, 라멘)가 같은 가게는 그 1번(같은 시각은 1번)마다 ×0.6, 바닥 0.4. `cat`이 없는 예전 신호와 빈 종류는 세지 않는다. 그룹 단위로 하지 않는 이유: 봉은사역 1km 가게의 절반 가까이가 한식이라 너무 크게 흔들린다. 순수 함수 `shared/personal.ts`의 `categoryFatigue`.
- **R41 부족하면 알아서 완화.** 뽑을 때 후보(R37 빼둔 곳 제외)가 3곳보다 적으면 빈 상태 버튼을 고르게 하는 대신 덜 중요한 조건부터 하나씩 풀어 3곳을 채운다: 최소 평점 → 예산 → 카테고리 → 반경 +300m(최대 1000m). 켜져 있는 조건만 풀고, 3곳이 되면 멈춘다. **영업 중 조건과 인원(4명+ 분식 제외)·술집·디저트 제외는 풀지 않는다.** 순수 함수 `shared/recommend.ts`의 `relaxToFill`.
  - 뽑기는 원래 조건에 맞는 곳을 먼저 넣고(이미 보여준 곳 제외 규칙은 R21과 같음) 모자란 만큼 완화로 들어온 곳에서 채운다(`drawTrio`의 `extra`).
  - 결과에 실제로 뽑힌 완화 후보가 어긴 조건만(`relaxedBy`, 완화 후보 전체가 아니라) 한 줄 토스트로 알려준다: "조건에 맞는 곳이 적어서 평점·예산 조건을 풀었어요", 반경만이면 "조건에 맞는 곳이 적어서 반경을 300m 넓혔어요", 둘 다면 "… 평점 조건을 풀고 반경을 300m 넓혔어요". 원래 조건에 맞는 곳이 0곳이면 "적어서" 대신 "없어서"라고 한다. 완화로 들어온 결과 카드에는 옅은 "조건 밖" 표시를 단다.
  - 원래 조건의 후보가 0곳인데 조건 밖에서 고른 결과가 떠 있으면, 목록 자리의 빈 상태는 "조건에 딱 맞는 곳은 없어서 조건 밖에서 골랐어요"라고 하고 조건 풀기 버튼은 그대로 둔다.
  - 풀어도 0곳이면 기존 빈 상태(R29, 조건 풀기 버튼)를 그대로 쓴다. 목록(리스트·지도 핀)은 원래 조건 그대로다.
- **R46 3곳에 "왜" 한 단어.** 결과 카드마다 보여주는 곳들(2곳 이상) 안에서 글자 그대로 참인 이유를 최대 하나 붙인다(`shared/reasons.ts`의 `trioReasons`): "제일 가까워요"(도보 분이 혼자 가장 작음; 도보 분을 모르는 곳이 있으면 붙이지 않음), "평점 최고"(평점을 아는 곳 2곳 이상 중 혼자 가장 높고 4.0 이상), "가성비"(가격을 아는 곳 2곳 이상 중 가격대 — R18 예산 경계 1만/1.5만/2만 — 가 혼자 가장 낮고 평점 3.8 이상), "처음 보는 곳"(이 기기에서 본 곳이 15곳 이상(`NEW_PLACE_MIN_SEEN`)일 때, 본 적 없는 곳이 혼자). 이 순서대로 주인이 아직 이유가 없을 때만 붙여 같은 말이 두 카드에 나오지 않고, 동점이면 붙이지 않는다. R41 "조건 밖" 카드에는 이유를 붙이지 않는다(표시는 카드당 하나; 그 카드가 이긴 이유를 다른 카드에 넘기지도 않는다 — 참이 아니라서). "처음 보는 곳"은 R37 신호가 아니라 기기의 본 곳 기억으로만 판단한다: `web/seen.ts`(localStorage `mmj:seen:v1`, `{장소 id: 마지막으로 본 시각}`; 순수 함수 `shared/seen.ts`의 `markSeen`·`pruneSeen`·`isNew`)는 결과로 보여준 곳(직접 뽑기, R39 자동 뽑기, 공유받은 후보)과 목록·핀에서 연 카드(공유받은 한 곳 포함)를 모두 기억하고, 30일 지나면 잊으며, 최대 500곳(넘치면 가장 오래전에 본 곳부터 버림)이다. 판단은 그 결과를 기록하기 전의 기억으로 한다(이번 결과가 "처음 보는 곳"을 지우지 않게). 읽기·쓰기에 실패하면 조용히 이번 세션 메모리에만 둔다. 서버로 보내지 않는다. 배지가 아니라 카드 둘째 줄(카테고리·가격 줄) 맨 앞의 조용한 글자다 — 사실 줄은 375px에서 이미 꽉 차서(241px) 넣으면 R34 알약이 잘린다. 둘째 줄은 끝이 말줄임이라 이유는 늘 보인다.
- **R47 "여기로 가요" 확정 공유.** 펼친 결과 카드의 "카카오맵에서 보기" 옆에 조용한 보조 행동 "여기로 가요"를 둔다(아래 "공유" 줄은 그대로). 누르면 그 한 곳을 확정하는 문구를 R23과 같은 방식(폰은 시스템 공유 시트, 아니면 복사)으로 보낸다(`shared/share.ts`의 `shareConfirmText`):
  ```
  👉 {가게명}(으)로 가요! 도보 {walkMinutes}분
  {카카오맵 장소 URL}
  https://mmj.itmz.me/{거점 id}?t={id}&r={radius}
  ```
  조사는 이름 끝 글자(괄호·공백 같은 기호는 건너뜀)의 받침으로 고른다(받침이 있으면 "으로", 없거나 ㄹ이면 "로"; `toParticle`). 끝이 숫자·영문이면 읽는 소리의 받침으로: 숫자 0 영·3 삼·6 육은 "으로", 1 일·7 칠·8 팔(ㄹ)과 2·4·5·9는 "로"; 영문 M·N(엠·엔)은 "으로", L(엘)과 나머지는 "로"(대소문자 같음). 도보 시간을 모르면 도보 부분을 뺀다. 성공하면 R37 `shared` 신호를 그 한 곳에만 남기고 R35 `share`에 `placeId`와 `props.confirm: true`(`picks`는 그 한 곳)를 붙인다.
- **R48 정보 확인 시점.** 펼친 결과 카드(R22)는 R13 응답의 `fetchedAt`으로 맨 아래에 조용한 글자 "N일 전 확인"(24시간 안이면 "오늘 확인", 내림)만 작게 보여준다(`shared/freshness.ts`의 `checkedText`). 출처("정보 출처: 카카오맵")는 시트 아래 줄에 이미 있어서 카드에서는 되풀이하지 않는다. 단건을 아직 받지 못했으면 보여주지 않는다. 오래된 정보를 숨기지 않고 솔직하게 알린다. 시트 아래 "정보 출처: 카카오맵"은 그대로 둔다.
- **R49 4명+면 전화 먼저.** 인원이 4명+이고 펼친 결과 카드의 가게에 전화번호가 있으면(R13 단건에만 있다 — 카드를 펼칠 때 이미 부르므로 추가 비용 없음) 펼친 내용 맨 위에 틴트 버튼 "전화로 자리 확인"(`tel:`, 숫자와 `+`만 남김; `web/format.ts`의 `telHref`·`callFirst`)을 첫 행동으로 보여준다. 4명+이면 단건을 받는 동안 그 자리에 같은 높이의 스켈레톤을 두어 버튼이 들어올 때 아래 내용이 밀리지 않게 하고, 받은 뒤 전화번호가 없거나 받지 못하면 그 자리만 빠진다. 그 밖에는 예전과 같다.
- **R50 시간대 반영 (아주 약하게).** 뽑는 순간의 KST 시각으로 가중치(R21)에 배수를 하나 더 곱한다(`shared/recommend.ts`의 `timeOfDayFactor`, `drawTrio`의 `now`). 11:55 ≤ 시각 < 13:30이면 `1 + 0.25 × (1 − 도보 분 / 이번 뽑기 후보(완화 후보 포함) 중 가장 먼 도보 분)`(가까울수록 조금 더), 11:20 전이면 `1 + 0.15 × clamp(평점 − 3.5, 0, 1.5) / 1.5`(평점 높을수록 조금 더). 그 밖의 시간, 도보·평점을 모르면 1이라 예전과 같다. 웨이팅 데이터는 없으므로 화면 문구는 없다.

### 5.5.1 관리 기능

- **R31 워밍 엔드포인트.** `POST /api/admin/warm?lat&lng&radius`(관리용이라 임의 좌표를 받는다)는 `Authorization: Bearer {ADMIN_TOKEN}`이 맞을 때만 동작하고, 틀리면 401이다. R10 예산 안에서 격자 수집과 상세 보충을 한 번 수행하고 `{incompleteTiles, pending, enriched, failed}`를 반환한다. `pending`을 세려고 격자 전체를 다시 훑지 않는다(R38): 이번에 처리한 상세가 배치(`DETAIL_BATCH_SIZE`)보다 적고 예산이 남았고 쿨다운 중이 아니면 `0`, 아니면 `"more"`다. `?count=1`일 때만 남은 수를 정확히 센다(전체 스캔). 그날 D1 읽기가 소프트 한도를 넘었으면 아무것도 하지 않고 429 `{error: "read_budget"}`를 준다. `scripts/warm.mjs`는 이 엔드포인트를 `incompleteTiles === 0 && pending === 0`이 될 때까지(최대 300회, 호출 간 1초) 반복 호출하고, 429 `rate_limited`(R36 관리자 제한)를 받으면 30초 기다렸다 같은 요청을 다시 하고(연속 3번까지, 넘으면 종료 코드 2), 429 `read_budget`(R38)이나 알 수 없는 429는 안내를 출력하고 종료 코드 2로 바로 멈춘다(`scripts/warmRetry.mjs`). 요청이 매번 새 실행이라 무료 플랜 한도 안에서 빠르게 채울 수 있다. 인자: 없으면 기본 거점(봉은사역) 1000m, `--hub <id>`, `--all`(모든 거점 차례로), 또는 `lat lng [radius]`. `scripts/audit.mjs`도 같은 인자를 받는다(`--all` 제외).
- **R35 익명 사용 이벤트.** 로그인 없이 브라우저마다 무작위 id(`crypto.randomUUID()`, localStorage `mmj:anon:v1`, 저장 불가면 이번 페이지만)와 탭 세션 id(sessionStorage `mmj:session:v1`, 30분 무활동이면 새로)만 쓴다. IP, User-Agent, 정확한 위치, 자유 입력 글자는 받지도 저장하지도 않는다. R37 개인화 상태는 여전히 서버로 보내지 않는다(이벤트는 그와 별개인 익명 집계용).
  - 이벤트(`shared/events.ts`, zod strict — 다른 키가 있으면 그 이벤트를 버림): `{t, ts, hub(거점 id), placeId?(숫자 1~15자리), props?}`. `props`는 `radius`(50m 단위), `party`(1~4), `groups`(필터 그룹 id), `priceCap`("all"|"10000"|"15000"|"20000"), `minRating`(0|3.5|4), `openOnly`, `candidates`(0~5000), `picks`(장소 id 최대 3개), `rank`(1~3), `auto`(`true`만; R39 자동 뽑기의 `draw`), `confirm`(`true`만; R47 "여기로 가요"의 `share`)만.
  - 타입: `app_open`(세션마다 한 번), `draw`/`redraw`(결과가 떠 있을 때 다시 뽑기; `candidates`, `picks`), `share`(공유·복사 성공 뒤; `picks`, R47 확정 공유는 `placeId`와 `confirm`), `open_kakao`(`rank`), `select_place`(목록·핀), `expand_card`(`rank`), `exclude_place`("여긴 빼줘"; `rank`), `undo_exclude`, `share_open`(받은 `t=` 링크를 엶; `picks`), `hub_change`, `filter_change`(1초 디바운스, 바뀐 뒤의 필터 스냅숏; 정렬만 바꾼 것은 제외), `empty_result`(필터를 바꾼 뒤 후보 0곳).
  - 브라우저(`web/analytics.ts`): 메모리 큐에 쌓아 10초마다, 10개가 차면, `visibilitychange → hidden`·`pagehide`에 `navigator.sendBeacon`(안 되면 `fetch(..., {keepalive: true})`)으로 보낸다. 요청당 최대 20개, 큐는 100개까지. 예외를 던지지 않고 실패는 버린다. 운영 빌드에서만 보내고 개발 서버는 `?track=1`일 때만. `/admin`은 세지 않는다.
  - `POST /api/events` 본문 `{anon, session, events}`(anon·session은 `^[0-9a-f-]{36}$`, 1~20개, 8KB 이하; 아니면 400). 이벤트는 하나씩 검증해 틀린 것만 버리고 `x-mmj-dropped` 헤더로 센다. 클라이언트 시각이 서버 시각 ±10분 밖이면 서버 시각을 쓰고, KST 날짜·시를 미리 계산해 `db.batch` 한 번으로 넣는다. 항상 204.
  - 남용: 익명 id별 `RATE_LIMITER`(분당 10회 × 20개)를 넘으면 조용히 버린다(204). 익명 id는 브라우저가 고르는 값이라 우회되므로, 그와 상관없는 상한으로 오늘(UTC) D1 쓰기 추정치(`meta.d1_written:{UTC 날짜}`, R38)가 `D1_WRITE_SOFT_CAP`(기본 60,000, 하루 한도 100,000의 60%) 이상이면 저장하지 않고 204를 준다(meta 2행 조회). 하루 개수 상한(익명 id당 300개)은 두지 않는다 — 세려면 요청마다 그날 이벤트를 훑어야 해서 R38 읽기 예산에 맞지 않는다. 사무실은 IP 하나를 함께 쓰고 `RATE_LIMITER`는 분당 10회라 IP 기준 제한은 쓰지 않는다. 저장이 실패해도 `console.error`만 남기고 204다(500을 주지 않는다).
  - 보관: Cron이 KST 04:00~04:04 실행에서 `day < 오늘 − 90일`인 이벤트를 지운다(`ts` 대신 `day`로 지워 인덱스 범위만 읽음).
- **R36 관리자 통계.** `GET /api/admin/stats?days=1..30&hub=all|{거점 id}`(R31과 같은 인증, 기본 7일·전체; 틀리면 400). KST 기준 오늘 포함 최근 N일의 일별 사용자(app_open의 익명 id 수)·세션(app_open 수)·뽑기·다시 뽑기·공유·카카오맵·공유 링크 열림(빈 날은 0), 시간대(0~23시)별 뽑기, 거점별 사용자·세션·뽑기·공유, 많이 뽑힌 가게 10곳(`picks` 기준, 이름은 places에서), 결과 카드 번호(1~3)별 펼침·카카오맵·빼줘, 뽑기한 세션 중 공유·카카오맵까지 간 세션 비율, 세션당 뽑기, 오늘(UTC 기준) D1 읽기·쓰기 추정치와 소프트 한도(R38)를 준다. R39 자동 뽑기(`props.auto`)는 사용자가 한 행동이 아니라서 뽑기·다시 뽑기·시간대·거점·많이 뽑힌 가게·전환율·세션당 뽑기에서 빼고 `totals.autoDraws`로 따로 준다(화면은 뽑기 카드에 "자동 N"). R47 확정 공유(`share`의 `props.confirm`)는 공유 수에 그대로 넣고 `totals.confirmShares`로 따로도 준다(화면은 공유 합계 옆에 "확정 N"). 집계는 `(type, day)` 인덱스로 타입을 좁힌 쿼리 5개 + 이름 1개.
  - 요청 제한(R31·R36 공통): 모든 `/api/admin/*` 요청은 토큰을 비교하기 **전에** 관리자 전용 Rate Limiting 바인딩 `ADMIN_LIMITER`(분당 120회)를 `admin:{cf-connecting-ip}` 키로 센다. 넘으면 토큰이 맞아도 429 `{error: "rate_limited"}`(그 다음이 401 비교). 화면용 `RATE_LIMITER`(분당 10회)는 쓰지 않는다 — warm.mjs가 초당 ~1회(분당 ~60회) 부르므로 같은 바인딩이면 수집이 멈춘다. IP는 제한 키로만 쓰고 저장하지 않는다. 관리 화면은 429면 토큰을 지우지 않고 "요청이 너무 많아요. 1분 뒤에 다시 해 주세요"를 보인다.
  - 화면 `/admin`(메인 화면에서 링크하지 않음, 따로 불러오는 청크; Worker의 SPA 대체 응답이 index.html을 준다): 토큰 입력(이 탭의 sessionStorage에만, 주소에는 넣지 않음, 401이면 지우고 "토큰이 맞지 않아요"), 기간 세그먼트(오늘/7일/30일), 거점 선택, 요약 카드(사용자, 세션, 뽑기, 공유율), 시간대별·일별 막대(차트 라이브러리 없이 CSS, 누르거나 가리키면 값; 일별은 "표로 보기"), 많이 뽑힌 가게·카드 번호별·거점별 표, 오늘 D1 읽기 막대. 앱과 같은 토큰을 쓴다. D1 막대 제목은 "오늘(UTC 기준, 09시 초기화)"이다. 이 화면에서는 `<meta name="robots" content="noindex, nofollow">`를 넣는다(Worker는 `/api/*`만 먼저 처리해서 Worker 헤더 대신 메타 태그). 정적 자산 쪽에서도 `public/_headers`로 `/admin`에 `X-Robots-Tag: noindex`를 붙이고, `public/robots.txt`는 `/admin`과 `/api/`를 막는다.
  - Cloudflare Web Analytics는 코드가 아니라 대시보드에서 켠다(비콘 토큰이 필요하면 그때 `index.html`에 넣는다).
- **R38 D1 읽기 예산 가드.** 무료 플랜은 하루 읽기 5,000,000행을 넘으면 그날 D1이 멈춘다(2026-10-05 밤, 대량 warm 반복으로 실제로 소진). API 요청과 Cron 실행마다 D1 결과의 `meta.rows_read`/`rows_written`을 메모리에 모으고(`worker/d1Usage.ts`의 계측 DB, `waitUntil`로 이어지는 보충까지 포함), 끝날 때 UPSERT 한 문장으로 `meta.d1_read:{UTC 날짜}`·`d1_written:{...}`에 더한다(기록 자체의 몇 행은 세지 않는 추정치). D1 무료 한도는 UTC 자정(KST 09:00)에 초기화되므로("wait until tomorrow (midnight UTC)") 사용량 날짜와 가드는 UTC 날짜를 쓴다(이벤트의 `day`/`hour`와 보관 정리는 KST 그대로). 그날 읽기가 `D1_READ_SOFT_CAP`(기본 3,000,000) 이상이면 R31 warm은 429 `{error: "read_budget"}`, Cron(R11)은 수집·보충을 건너뛴다. 목록·단건 API는 그대로 동작한다. `/api/events`(읽기가 거의 0행)는 요청마다 하는 사용량 UPSERT(2키)를 하지 않고, 이벤트 삽입 배치 끝에 `d1_written:{UTC 날짜}` += 이벤트 수 × 4(한 개 = 4행, 로컬 측정) 한 문장만 넣는다 — R35 쓰기 상한이 이벤트 쓰기를 셀 수 있게 하면서 쓰기를 줄인다.
- **R32 감사 엔드포인트.** `GET /api/admin/audit?lat&lng&radius`(같은 인증)는 §7의 Q1~Q4 수치를 JSON으로 반환한다. `scripts/audit.mjs`는 이를 표로 출력하고, Q1 또는 Q2를 통과하지 못하면 종료 코드 1로 끝난다.

- **R33 대표 사진.** 상세 응답의 `summary.main_photo_url`이 카카오 CDN(`*.kakaocdn.net`) 주소면(http/https만, 사용자 정보나 포트가 붙은 주소는 거부) https로 바꿔 `places.photo_url`에 기록한다(사진 파일은 저장하지 않음). 다른 호스트(네이버 블로그 등 외부 사이트에서 막히는 이미지)는 기록하지 않는다. 화면에서는 카카오 썸네일 서버(`img1.kakaocdn.net/cthumb/local/C{px}x{px}.q50/?fname=`)를 거쳐 결과 카드 상단과 목록 썸네일로 보여주고, 사진이 없거나 불러오지 못하면 사진 자리를 숨긴다.
- **R34 근처 상위 N%.** 지금 거점·반경의 전체 목록(R12 1000m 응답 중 화면 반경 안, 사용자 필터 적용 전)에서 평점이 있는 가게끼리 리뷰 수로 보정한 평점(R51) 순위를 매긴다(같은 점수는 더 좋은 순위를 함께 쓴다). `top = max(1, ceil(순위 / 대상 수 × 100))`이 30 이하인 가게만 목록 행과 결과 카드의 사실 줄에 옅은 포인트 알약 "근처 상위 15%"를 단다. 순수 함수 `shared/rank.ts`의 `topPercents`.
- **R51 리뷰 수 보정 평점 (순위 계산에만).** R34 순위는 원래 평점 대신 베이지안 평균 `(v × R + m × C) / (v + m)`으로 매긴다: v = 리뷰 수(없으면 0), R = 평점, C = 같은 대상(반경 안, 평점 있는 곳)의 평점 평균, m = 20(`RANK_PRIOR_REVIEWS`). 리뷰 6개짜리 5.0점이 리뷰 300개짜리 4.6점보다 위에 오지 않게 한다. 예전의 "리뷰 5개 이상" 문턱은 이 보정이 대신한다(리뷰가 적은 곳은 빼지 않고 지역 평균 쪽으로 끌어당긴다). 리뷰 수가 없거나 0개인 곳은 대상 수·평균 C·순위 자리에는 들어가지만 자기 "근처 상위 N%" 알약은 달지 않는다(근거가 별점 하나뿐이라). 화면에 보이는 별점은 원래 값 그대로이고, 뽑기 가중치(R21)는 바꾸지 않는다.
- **R42 거점당 1000m 한 번만 받기.** 화면은 반경과 상관없이 거점의 1000m 목록(`/api/places?hub&radius=1000`)을 거점마다 한 번 받고, 반경은 `filterPlaces`가 거리로 거른다. 반경을 바꿔도 다시 요청하지 않아 슬라이더가 즉시 반응한다. 서버도 다른 반경 요청을 같은 1000m 본문·같은 캐시 키로 답해서(R12) 캐시 키가 거점 수(5개)뿐이다. 대신 첫 응답이 커진다(§9.1). R34 순위는 반경 안 목록으로 브라우저에서 다시 계산한다(서버는 순위를 계산하지 않는다). 반경을 바꾸면 결과 3곳은 지금처럼 비운다(R22).

### 5.6 UI

- **R27 레이아웃 (모바일 우선).** 대부분 폰으로 열기 때문에 375×812를 기준으로 설계하고, 900px 이상에서 데스크톱 배치로 바꾼다. 상단 바에는 로고와 거점 칩이 있다.
  - 모바일: 상단 바 → 지도(화면 높이의 40%) → 패널(필터, 상태 줄, 리스트; 패널만 스크롤). 뽑기 버튼은 화면 하단에 고정된 바에 있고 `env(safe-area-inset-bottom)`만큼 띄운다. `viewport-fit=cover`를 쓰고 노치와 홈 인디케이터 영역을 피한다.
  - 데스크톱(≥ 900px): 왼쪽 패널(400px; 필터, 상태 줄, 리스트, 패널 아래에 붙는 뽑기 버튼) + 오른쪽 지도.
  - 반경 슬라이더("거리"), 인원, 카테고리("전체" 칩 포함)는 항상 보인다. 1인 예산, 최소 평점, 영업 중만, 술집 포함은 접이식 "상세 조건"(`<details>`)에 넣고, 접힌 줄에 현재 값을 한 줄로 요약한다(예: "예산 전체 · 평점 무관 · 영업 중만").
  - 터치 대상은 44px 이상, 입력과 선택 상자의 글자는 16px 이상이다(iOS 자동 확대 방지). 마우스 hover에만 기대는 동작은 없다.
- **R28 지도와 상세 카드.** 카카오맵 JS SDK를 쓴다. 거점 핀, 반경 원(점선 `dash`), 후보 가게 핀(필터를 통과한 곳만, HTML 버튼 CustomOverlay, 탭 순서에서는 뺀다 — 같은 가게를 목록에서 키보드로 고를 수 있다)을 보여준다. 거점이나 반경이 바뀌면 원이 여백을 두고 화면에 들어오게 맞춘다. 선택된 핀은 커지면서 한 번 퍼지고 가게 이름 라벨을 단다. SDK는 한 번만 불러오고 10초 안에 준비되지 않으면 "지도를 불러오지 못했어요"와 "다시 시도"를 보여준다.
  - 칩 겹침: 가까이 본 지도(레벨 3 이하는 전부, 레벨 4는 평점 4.0 이상·선택한 핀만)에서 화면 안 칩이 서로 덮으면 선택한 핀 → 평점 높은 순 → 리뷰 많은 순으로 하나만 남기고 나머지는 점으로 그린다. 뽑힌 핀의 번호 배지와 보이는 이름표, 선택한 핀의 이름표도 피한다. 단, 선택한 핀의 칩은 번호 배지나 이름표 위에 걸쳐도 점으로 바꾸지 않고 남긴다. 확대·이동이 끝났을 때와 핀·결과가 바뀔 때 다시 계산한다(`shared/labels.ts` `keptChips`).
  - 핀이나 리스트 항목을 누르면 그 한 곳의 상세 카드를 열고 지도가 그 핀으로 이동한다(뽑기 결과 3곳은 R22). 모바일은 뽑기 바 바로 위에 붙는 바텀 시트(최대 화면 높이의 60%, 내부 스크롤, 스크롤해도 위에 붙어 있는 손잡이(끌어 내리면 닫힘), 닫기 버튼)이고, 데스크톱은 지도 위 오버레이다. 카드가 열리면 닫기 버튼으로 초점을 옮기고 Esc로 닫는다(카드 자체는 `aria-live`가 아니다). 목록 응답에는 메뉴가 3개뿐이라 카드를 열면 R13을 한 번 불러 전체 메뉴로 바꾼다.
  - 카드 정보 순서: 이름 → 도보 N분 · ⭐평점(리뷰 수) · 영업 상태("영업 중" / "곧 마감" / "지금 닫힘" / "영업 정보 없음"; 닫혔거나 30분 안에 닫으면 포인트 컬러) → 카테고리 · 대표 가격 · 강점 → 메뉴(모바일은 3개 + "메뉴 더보기", 데스크톱은 최대 5개) → 행동("공유"(이 한 곳, R23), "카카오맵" 링크) → 작게 "정보 출처: 카카오맵". 상세 정보가 없는 가게(R13)는 평점과 메뉴 대신 "평점과 메뉴 정보를 아직 불러오지 못했어요"를 보여준다.
- **R29 로딩과 상태 표시.** 거점이 바뀌면 250ms 디바운스 후 요청하고(반경은 다시 요청하지 않는다, R42), 다시 불러오는 동안 이전 리스트를 흐리게 보여준다.
  - 첫 응답 전에는 리스트 자리에 스켈레톤 4줄과 "주변 식당을 찾고 있어요"를 보여준다.
  - `pending > 0`(`detailsPaused` — R10 쿨다운·R44 frozen — 이면 제외) 또는 `incompleteTiles > 0`이면 3초 → 6초 → 12초(이후 12초) 간격으로 최대 6번(약 57초) 다시 요청하고(`web/pollSchedule.ts`), 리스트 위 상태 줄에 "주변 가게를 더 찾는 중이에요"(incompleteTiles) 또는 "평점 정보 불러오는 중 (n곳)"(pending)을 표시한다. 6번이 끝났는데도 남아 있으면 "주변 가게를 다 찾지 못했어요" 또는 "n곳은 아직 정보를 못 불러왔어요"로 바꾼다. 다시 요청하는 중에 후보가 0개면 빈 상태 대신 스켈레톤을 유지한다.
  - `stale`이면 "정보가 오래됐을 수 있어요"를 표시한다.
  - R44: frozen이거나 가장 최근 상세가 4일보다 오래됐으면 "평점·메뉴는 N일 전 기준이에요"(frozen이면 pending 안내보다 먼저).
  - 첫 요청이 실패하면 "가게 정보를 불러오지 못했어요"와 "다시 시도" 버튼을 보여준다. 이미 리스트가 있는데 다시 요청이 실패하면 리스트는 두고 상태 줄에 "최신 정보를 불러오지 못했어요"와 "다시 시도"를 보여준다.
  - 후보가 0개면 "점심시간이 코앞인데 후보가 없네요"와 조건 풀기 버튼(R21)을 보여준다.

## 7. 데이터 품질 수용 기준

`npm run audit`(D1 원격 또는 로컬 대상)은 거점(기본 봉은사역, `--hub <id>`) 반경 1000m 데이터에 대한 리포트를 출력한다.

- **Q1 누락 없음.** `saturated = 1`인 격자가 0개.
- **Q2 상세 커버리지.** 덮는 격자에 기록된 장소 ID 중 표시 정보를 가진 장소가 95% 이상. 실패한 장소는 목록과 `fail_reason`을 출력한다. Q3, Q4도 같은 ID 집합을 기준으로 한다.
- **Q3 필드 결측률.** ok인 가게 중 rating, price, hours가 각각 null인 비율을 출력한다. 기준치는 없고, 하나라도 50%를 넘으면 파서 버그를 의심해서 픽스처와 대조한다.
- **Q4 분포와 이상치.** 그룹별 가게 수, `etc`로 떨어진 카테고리 2단계 값 목록, 좌표가 유효 범위(lat 33~39, lng 124~132) 밖인 가게 수, 이름과 좌표(소수 5자리)가 같은 중복 의심 묶음 수를 출력한다.
- **Q5 표본 검증.** 직접 고른 근처 가게 10곳을 카카오맵 화면과 대조해 평점(소수 첫째 자리), 메뉴 가격, 영업시간이 일치하는지 확인한다(수동, 결과를 `docs/audit/`에 기록).

Q1, Q2, Q5를 통과해야 UI 마일스톤으로 넘어간다.

## 9.1 무료 플랜 운영 예산

무료 플랜 한도: Workers 하루 요청 100,000회, 실행당 CPU 10ms, 실행당 외부 호출 50회 / D1 하루 읽기 5,000,000행, 쓰기 100,000행, 저장 5GB.

| 항목 | 예상 사용량 (거점 3곳, 반경 1000m) | 한도 대비 |
|---|---|---|
| Cron | 하루 288회. 평소(할 일 적음) 실행당 수백 행(로컬 측정: 거점 2곳 269행), 상세 만료 지터 구간에 든 행까지 합쳐 실행당 ~1,500행 이하 → 하루 ~0.4M행. 격자를 다시 모은 직후 몇 시간은 미수집 확인으로 실행당 +5,000행 안팎 | 읽기 10% 안팎 |
| `/api/places` 캐시 미스 | 봉은사역 1000m 응답 ~0.6MB(gzip ~110KB), 읽기 ~3,600행. 동대문 1000m ~1.0MB(gzip ~180KB), ~6,200행 | 미스 하루 500회면 ~2.5M행 |
| `/api/places` 캐시 적중 | D1 0행, CPU 최소 (화면은 거점마다 1000m만 요청해서 키 5개, 60초; R42 전에는 거점 × 반경 19단계) | — |
| 상세 갱신 쓰기 | 장소 ~4,500곳 × (3일 + 평균 12시간)마다 1번 → 하루 ~1,300곳, 인덱스 포함 수천 행 | 쓰기 5% 안팎 |
| 외부 호출 | 실행당 최대 40회(`SUBREQUEST_BUDGET`), 상세 보충 10곳(`DETAIL_BATCH_SIZE`) | 50회 한도 안 |
| R31 warm | 호출마다 격자 상태 + 덮는 격자의 `tile_places`(1000m면 수천 행)를 한 번 읽는다. 예전에는 `pending`을 세려고 한 번 더 훑었다(R38에서 제거, `?count=1`일 때만) | 반복 호출 300회면 수백만 행 → 소프트 한도에서 429 |
| R35 이벤트 쓰기 | 사용자 50명 × 하루 5세션 × 세션당 ~6.4개 ≈ 1,600개/일. 한 개 = 4행(표 + 인덱스 2 + 일련번호; 로컬 측정). 요청(세션당 ~3번, ~750회)마다 같은 배치의 쓰기 추정치 UPSERT 1행(R38, 일반 사용량 UPSERT 2키는 하지 않음) | 쓰기 ~6,400 + ~750행/일 ≈ 7%. 90일 뒤부터 정리 DELETE가 비슷한 만큼 더 |
| R35 이벤트 읽기 | 수집은 읽기 0에 가깝다 (하루 개수 상한을 세지 않는 이유) | — |
| R36 통계 | 위 트래픽에서 한 번 볼 때 오늘 ~8,000행, 7일 ~53,000행, 30일 ~229,000행(로컬 측정; GROUP BY 임시 B-트리와 `json_each`도 읽기로 센다) | 7일을 하루 5번 보면 ~0.27M행(5%) |
| R38 기록 | 요청·실행마다 UPSERT 1문장(읽기 1~2행), 가드 확인 2행 | 무시할 수준 |
| Rate Limiting | `RATE_LIMITER`(화면, 분당 10회)와 `ADMIN_LIMITER`(관리자, 분당 120회) 두 바인딩. 별도 요금 없음(Workers 요청 수에는 포함), 콜로마다 따로 센다. warm.mjs는 분당 ~60회라 `ADMIN_LIMITER` 안이고, 걸려도 30초 기다렸다 다시 한다 | — |

R38 가드는 그날 읽기가 3,000,000행(60%)을 넘으면 수집을 멈춰서 목록 서비스에 2,000,000행을 남긴다. 집계는 요청이 끝난 뒤에 더하므로 동시에 도는 warm 몇 회만큼 넘칠 수 있다.

캐시 미스 응답의 CPU는 JSON 크기에 비례한다. 큰 거점(동대문)에서 10ms를 넘기 쉬우므로 캐시 적중을 기본으로 보고, 더 줄일 때는 목록의 영업시간·메뉴 표현을 압축한다.
