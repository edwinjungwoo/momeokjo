# 모먹죠 (mmj.itmz.me) 설계 스펙

- 작성일: 2026-10-05
- 상태: 리뷰 대기
- 형태: 하루짜리 해커톤 프로젝트, 완전 공개 웹앱

## 1. 개요

선약 없는 평일 점심, 점심시간 5~10분 전에 "점심 고?" "ㅇㅇ"로 즉석에서 꾸려진 일행이 **어디 갈지 1분 안에 정하도록** 돕는 지도 + 큐레이션 앱.

- 기준점은 미리 정한 거점(`shared/hubs.ts`: 봉은사역(기본), 동대문역사문화공원역, 판교역) 중 하나를 고른다. 임의 위치는 받지 않는다.
- 반경(100~1000m), 인원, 카테고리, 1인 예산, 평점, 영업 여부로 후보를 좁히고 "모먹죠?" 버튼으로 서로 다른 후보 3곳을 가중 랜덤으로 뽑아 함께 보여준다. 일행에게는 3곳을 한 번에 공유해서 고르게 한다.
- 원칙: **최대한 덜 선택하고 최대한 좋은 결과.** 새 필수 입력은 늘리지 않고, 이 기기에서의 행동(카카오맵 열기, 공유)으로 다음 뽑기를 조용히 개인화한다(R37).
- 데이터는 카카오 로컬 API(공식)와 카카오맵 장소 상세(비공식)를 쓴다.

### 개발 원칙

- **데이터가 최우선이다.** 데이터 파이프라인을 먼저 만들고, 데이터 품질 수용 기준(§7)을 통과한 뒤에 UI를 만든다.
- **SDD:** 이 문서가 기준이다. 요구사항은 `R*`(기능), `Q*`(데이터 품질) 번호로 추적한다. 구현하다가 스펙과 다른 판단이 필요하면 스펙을 먼저 고친다.
- **TDD:** 모든 `R*`는 실패하는 테스트로 시작한다. 테스트 이름은 요구사항 번호로 시작한다(예: `R7: 전골(중) 67,000원은 대표가격 계산에서 제외`).

## 2. 아키텍처

```
[브라우저 React SPA]
  │  GET /api/places?hub&radius            GET /api/places/:id
  ▼
[Worker: Hono]
  ├─ 정적 에셋 (Vite 빌드 결과)
  ├─ PlacesService ── TileCollector ──▶ 카카오 로컬 API (공식, REST 키)
  │                └─ DetailEnricher ─▶ 카카오맵 장소 상세 (비공식)
  ├─ D1: places, place_details, tiles
  └─ scheduled(): 모든 거점 반경 1km 사전 수집 (5분마다)

필터링, 정렬, 뽑기는 전부 브라우저에서 한다 (반경 내 가게는 수백 곳 이하라 전송 가능).
```

## 3. 외부 데이터 소스

### 3.1 카카오 로컬 API (공식)

- `GET https://dapi.kakao.com/v2/local/search/category.json`
- 파라미터: `category_group_code=FD6`, `rect=minLng,minLat,maxLng,maxLat`, `page=1..3`, `size=15`, `sort=accuracy`
- 헤더: `Authorization: KakaoAK {KAKAO_REST_KEY}`
- 한 번의 검색으로 최대 45개(15 × 3페이지)까지만 받을 수 있다. 응답의 `meta.total_count`로 실제 개수를 확인한다.
- **저장 금지 정책 (2026-10-05 확인):** 카카오맵 API FAQ(2022-10-18)는 "로컬 API 등을 호출하여 응답받은 결과 데이터를 별도로 저장하여 사용하는 것은 허용하지 않습니다"라고 한다. 2026-08-24 답변에 따르면 임시 저장도 불허다. 2026-08-26 답변에 따르면 "장소ID만 기록하고 나머지 표시 정보는 실시간 호출하는 방향은 운영 정책상 허용 가능"하다 (https://devtalk.kakao.com/t/faq-api/125610, https://devtalk.kakao.com/t/api-20/151271). 그래서 **로컬 API 응답에서는 장소 ID만 저장한다.** 이름, 좌표, 카테고리는 요청을 처리하는 동안 메모리에서만 쓴다(간식 제외 판단).
- 보수적으로 읽어서, 화면이 기기에 두는 목록 저장본(R45, IndexedDB에 `/api/places` 응답 원문 — 표시 정보는 상세 응답에서 온 것)도 3일(예전 서버 상세 유지 기간 — R63 주 1회 갱신 뒤에도 기기 쪽은 3일 그대로)보다 오래 쓰지 않는다(`shared/placesCache.ts`의 `PLACES_CACHE_MAX_AGE_MS`; 24시간 넘으면 흐리게 보여주고 자동 뽑기는 새 목록을 기다린다). R65 "내 가게"도 같다: 즐겨찾기·뺀 곳·최근 신호는 가게 id와 시각만 오래 남기고, 이름·종류·좌표 기억(`snapshots`)은 같은 3일(`SNAPSHOT_MAX_AGE_MS = PLACES_CACHE_MAX_AGE_MS`)이 지나면 쓰지도 남기지도 않으며 그 뒤에는 단건(R13)으로 다시 불러온다.

### 3.2 카카오맵 장소 상세 (비공식)

- `GET https://place-api.map.kakao.com/places/panel3/{id}`
- 필수 헤더: `pf: PC`, `Origin: https://place.map.kakao.com`, `Referer: https://place.map.kakao.com/`, 브라우저 User-Agent, `Accept: application/json`. 헤더가 없으면 406이 반환된다(2026-10-05 로컬에서 확인).
- **Cloudflare 엣지에서 호출 가능 확인 (2026-10-05, `wrangler dev --remote`, 3건 모두 200).** 응답 크기는 가게당 50~120KB다.
- 사용하는 필드 (2026-10-05 id 27531028 "중앙해장" 응답으로 확인):
  - 평점: `kakaomap_review.score_set.average_score`, `kakaomap_review.score_set.review_count`
  - 강점: `kakaomap_review.score_set.strength_counts[{id,count}]` + `kakaomap_review.strength_description[{id,name}]`
  - 메뉴: `menu.menus.items[{name, price}]`
  - 영업시간: `open_hours.week_from_today.week_periods[].days[]`. 각 day는 `day_of_the_week_desc`("월(10/5)")와 함께 `on_days.start_end_time_desc`("11:30 ~ 22:00", 자정을 넘기면 "16:00 ~ 02:00"), `on_days.break_times_desc`(["14:30 ~ 18:00 브레이크타임"]) 또는 `off_days_desc`("휴무일")를 가진다.
  - 예약/태그: `place_add_info.ai_mate.store_facility_icons[].text`와 `place_add_info.store_facility_icons[].text`(예: "예약가능"), `place_add_info.full_detail_infos[].items[].contents[].label`(예: "혼밥", "단체석", "회식장소", "점심특선")
  - 메뉴 가격은 -1이나 0일 수 있다(가격 미표기).
  - **장소 요약 (표시 정보의 출처):** `summary.name`, `summary.category.{name1,name2,name3}`, `summary.point.{lat,lon}`, `summary.address.road`(없으면 `disp`), `summary.phone_numbers[0].tel`
- 형식이 바뀌거나 막힐 수 있으므로 **모든 필드는 optional로 파싱**하고, 하나가 실패해도 나머지는 살린다.
- **차단 시 대안:** Worker IP에서 호출이 막히면, 로컬 Node 스크립트로 수집해서 `wrangler d1 execute --remote`로 D1에 적재한다. 이 경우 Cron 상세 수집은 끈다.

## 4. 데이터 모델 (D1)

```sql
CREATE TABLE tiles (
  key TEXT PRIMARY KEY,           -- R1 격자 키
  collected_at INTEGER NOT NULL,
  place_count INTEGER NOT NULL,
  saturated INTEGER NOT NULL DEFAULT 0  -- 최대 깊이에서도 45 초과면 1
);

-- 로컬 API 응답에서는 격자별 장소 ID만 기록한다 (§3.1 저장 금지 정책)
CREATE TABLE tile_places (
  tile_key TEXT NOT NULL,
  place_id TEXT NOT NULL,
  PRIMARY KEY (tile_key, place_id)
);
CREATE INDEX idx_tile_places_place ON tile_places(place_id);

-- 장소 상세(§3.2) 응답에서 얻은 정보. 상세를 한 번도 성공하지 못한 장소는 name 등이 NULL이다
CREATE TABLE places (
  id TEXT PRIMARY KEY,
  status TEXT NOT NULL,            -- 마지막 시도 결과 'ok' | 'failed'
  name TEXT, category_name TEXT, category_group TEXT, lat REAL, lng REAL, address TEXT, phone TEXT,
  rating REAL, review_count INTEGER, price INTEGER,
  menus_json TEXT, hours_json TEXT, strengths_json TEXT, tags_json TEXT, bookable INTEGER,
  fail_reason TEXT,
  fetched_at INTEGER NOT NULL
);
CREATE INDEX idx_places_lat_lng ON places(lat, lng);
-- 0005: R12 목록 원소를 미리 직렬화한 JSON(거리·도보 분 없음)을 판 접두어와 함께 `v1:{...}`로 둔다 (LIST_JSON_VERSION, shared/constants.ts).
-- saveDetail이 같은 행에 같이 쓰고, 목록은 지금 판이고 '{'로 시작하는 조각만 쓴다 — NULL·예전 판·깨진 값이면 열에서 만든다(본문은 같다).
-- Cron이 rowid 순으로 실행마다 200행씩 지금 판이 아닌 조각을 다시 쓰고(meta list_json_backfill:v{판} = 마지막 rowid, 끝나면 "done")
-- 다 쓰면 meta 1행만 읽는다. 목록 원소 출력이 바뀌면 판을 올린다 → 커서 키도 바뀌어 처음부터 다시 쓴다
ALTER TABLE places ADD COLUMN list_json TEXT;

-- 앱 전역 상태 (0003). place_blocked_until = 상세 API 쿨다운이 끝나는 시각(epoch ms, R10),
-- tiles_changed_at = 격자 ID가 바뀔 때마다 커지는 값(R4·R11 커서들이 "본 값과 같은지"로 격자 변화를 알아본다), unfetched_from = Cron 미수집 앞선 커서(R11)
-- (unfetched_cleared_at은 Task 34 수정 뒤 쓰지 않는다 — 남아 있어도 무시)
-- detail_mode = R44 강등 모드 {"mode":"frozen","since","until"}, block_count:{KST 날짜} = 그날 쿨다운 횟수(차단이 있는 날만, 기록할 때 지난 날 키를 지움)
-- hub_refreshed:{hub} = R63 거점 갱신 완료 {"start": 끝낸 갱신의 시작(그 요일 00:00 KST), "at": 끝낸 시각} (갱신 중에는 지난 완료가 남는다)
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
CREATE INDEX idx_places_status_fetched_at ON places(status, fetched_at); -- R11 만료 후보
-- meta에는 R38 날짜별 D1 사용량도 둔다: d1_read:{UTC yyyy-mm-dd}, d1_written:{...} (90일 뒤 R35 정리 때 지움)

-- R35 익명 사용 이벤트 (0004). IP·User-Agent·위치·자유 입력은 저장하지 않는다. 90일 보관
CREATE TABLE events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts INTEGER NOT NULL,   -- 서버가 확인한 epoch ms (클라이언트 시각 ±10분 밖이면 서버 시각)
  day TEXT NOT NULL,     -- KST yyyy-mm-dd
  hour INTEGER NOT NULL, -- KST 0–23
  anon TEXT NOT NULL, session TEXT NOT NULL, hub TEXT NOT NULL, type TEXT NOT NULL,
  place_id TEXT, props TEXT  -- 검증한 props의 짧은 JSON
);
CREATE INDEX idx_events_day ON events(day);
CREATE INDEX idx_events_type_day ON events(type, day);

-- R59 관리자 대시보드 일별 집계 (0006). hub = 거점 id 또는 '*'(모든 거점), 값이 0인 지표는 쓰지 않는다. 지표 정의는 R58.
-- 코호트는 day = 첫 방문 주의 월요일, metric = cohort_* 행. 400일 보관(익명 집계만). WITHOUT ROWID라 한 행 = 쓰기 1행
CREATE TABLE daily_stats (day TEXT NOT NULL, hub TEXT NOT NULL, metric TEXT NOT NULL, value INTEGER NOT NULL,
  PRIMARY KEY (day, hub, metric)) WITHOUT ROWID;
-- R58 재방문: 익명 id별 첫 방문일·그날 처음 연 거점·재방문 비트(ret 1=D1, 2=D7, 4=D14, 8=D28)·마지막 방문일. Cron 집계만 쓴다
-- (이벤트 수집 경로는 그대로). last_day가 90일 지나면 R35 정리 창에서 지운다
CREATE TABLE anon_first_seen (anon TEXT PRIMARY KEY, day TEXT NOT NULL, hub TEXT NOT NULL, ret INTEGER NOT NULL DEFAULT 0,
  last_day TEXT NOT NULL) WITHOUT ROWID;
-- meta에 더: rollup_through = 집계를 마친 마지막 KST 날, cron_last = 마지막 Cron 요약 JSON {at, collected, incomplete, enriched, failed, calls, rolled, skipped?}
-- R56 거점 스냅샷 (0007; 0006은 feat/admin-ops). Cron이 만든 거점 1000m 목록 응답 본문(/api/places와 글자까지 같음)의 gzip을 base64로 둔다.
-- version = HUB_SNAPSHOT_VERSION, source_at = 만들기 전에 읽은 거점 표시(meta snapshot_dirty:{hub}), etag = 본문(gzip)의 SHA-256 앞 16자로 정한 ETag.
-- body는 BLOB이 아니라 base64 텍스트다 (D1은 BLOB을 숫자 배열로 돌려줘서 읽는 쪽 CPU가 4배 넘게 든다)
CREATE TABLE hub_snapshots (
  hub TEXT PRIMARY KEY, version INTEGER NOT NULL, built_at INTEGER NOT NULL, source_at INTEGER NOT NULL,
  encoding TEXT NOT NULL, etag TEXT NOT NULL, body TEXT NOT NULL
);
-- meta snapshot_dirty:{hub} = 그 거점 목록이 바뀐 표시 (바뀔 때마다 커지는 정수, R56)
```

카카오맵 링크는 `https://place.map.kakao.com/{id}`로 만든다.

## 5. 기능 요구사항

### 5.1 수집: 가게 목록 (공식 API)

- **R1 고정 격자.** 위도 간격 `0.00225°`(약 250m), 경도 간격 `0.0028°`(위도 37.5° 기준 약 250m)로 지도를 나눈다. 격자 키는 `"{floor(lat/0.00225)}:{floor(lng/0.0028)}"`이다. `tilesCoveringCircle(center, radius)`는 원과 겹치는 모든 격자 키를 반환한다.
  - 예: 반경 0이면 중심이 속한 격자 1개, 반경이 격자 경계를 넘으면 인접 격자 포함
- **R2 쿼드트리 분할.** 격자(또는 하위 사각형)를 rect 검색했을 때 `meta.total_count > 45`이면 4등분해서 각각 다시 검색한다. 최대 깊이는 5다(약 8m — 한 건물의 가게가 같은 좌표에 몰려 깊이 4 칸(약 15m)이 46곳 넘게 나와도 깊이 5에서 나뉘는 경우를 받는다). 최대 깊이에서도 45를 넘으면(같은 좌표에 45곳 넘게 찍힌 건물) 받은 45개의 ID를 기록하고 `tiles.saturated = 1`로 표시한다. 기록하는 것은 **장소 ID뿐**이고, 카테고리가 `dessert`인 장소는 기록하지 않는다(판단은 메모리에서만). 한 격자 안에서 id가 중복되면 한 번만 기록한다.
- **R3 격자 TTL.** 거점 격자(어느 거점의 1000m 격자)는 R63 갱신 요일에 맞춘다: 그 격자를 덮는 거점들의 가장 늦은 갱신 시작(그 요일 00:00 KST) 이후에 수집했으면 다시 수집하지 않고, 그 전에 수집했으면 다시 수집한다(시작은 언제나 7일 안이라 7일보다 늦게 다시 모으는 일은 없다). 거점 밖 격자(관리자 warm의 임의 좌표)는 `tiles.collected_at`이 7일 이내면 다시 수집하지 않는다. 판단은 `isTileDue(key, state, now)`·`dueTileKeys`(격자마다 `[key, 기준]`을 SQL에 넘긴다, `worker/refreshSchedule.ts` `tileFreshFrom`).
- **R4 격자 ID 갱신.** 격자를 다시 수집하면 그 격자의 ID 목록을 새 결과로 바꾼다. D1 쓰기를 아끼려고 지금 기록된 ID를 읽어서 빠진 ID만 지우고(DELETE 한 문장) 새 ID만 넣는다(INSERT OR IGNORE 한 문장) — 바뀌지 않은 격자는 `tile_places`에 쓰지 않고 수집 시각만 갱신하며, ID가 바뀌었을 때만 `tiles_changed_at`(Cron의 만료·미수집 커서를 버리게 하는 값)을 `MAX(이전 값 + 1, now)`로 올린다 — 같은 ms에 두 번 바뀌거나 더 이른 now가 늦게 기록돼도 값이 언제나 달라진다. `places`의 상세 행은 지우지 않는다(폐업 판단은 범위 밖).
- **R5 카테고리 그룹.** `category_name`을 `>`로 나눈 두 번째 단계로 매핑한다.

  | 그룹 키 | 표시 | 카카오 2단계 |
  |---|---|---|
  | `korean` | 한식 | 한식 |
  | `chinese` | 중식 | 중식 |
  | `japanese` | 일식 | 일식 |
  | `western` | 양식 | 양식, 패밀리레스토랑 |
  | `asian` | 아시안 | 아시아음식 |
  | `snack` | 분식·패스트푸드 | 분식, 패스트푸드, 도시락 |
  | `bar` | 술집 | 술집 |
  | `dessert` | (항상 제외) | 간식 |
  | `etc` | 기타 | 위에 없는 모든 값 (뷔페, 샐러드, 치킨, 퓨전요리 등) |

  `dessert`는 수집 단계에서 기록하지 않고, 상세 카테고리가 `dessert`로 나온 장소도 API 응답에서 제외한다. 감사 리포트(Q4)는 `etc`로 떨어진 2단계 값 목록을 출력하고, 필요하면 이 표를 고친다.

### 5.2 수집: 상세 정보 (비공식 API)

- **R6 상세 파싱.** §3.2의 응답을 섹션별 zod 스키마로 검증해 `PlaceSummary`(이름, 카테고리 원문, 좌표, 주소, 전화)와 `PlaceDetail`로 변환한다. 요약에서 이름이나 좌표가 없으면 표시할 수 없으므로 `schema` 실패로 본다. 나머지 섹션은 optional이다.
  - `rating`: `average_score`. 리뷰가 0개면 null
  - `strengths`: `strength_counts`를 count 내림차순으로 정렬해 상위 2개 id를 `strength_description`의 이름으로 바꾼 것
  - `bookable`: `place_add_info`가 없으면 null이다. 있으면 두 `store_facility_icons` 목록 중 하나라도 text가 "예약가능"이면 true, 아니면 false다.
  - `tags`: `full_detail_infos[].items[].contents[].label`을 순서대로 중복 없이 모은다(최대 30개).
  - `menus`: 가격이 1 이상인 메뉴만, 최대 20개
  - JSON이 아니거나 최상위 구조가 다르면 `status='failed'`, `fail_reason='schema'`
- **R7 대표 가격.** 메뉴 가격 중 `5,000 ≤ price ≤ 30,000`인 값들의 중앙값을 100원 단위로 반올림한다. 해당 값이 없으면 null이다. 값이 짝수 개면 가운데 두 값의 평균을 쓴다.
  - 예: [14000, 16000, 16000, 67000] → [14000, 16000, 16000] → 16000
- **R8 영업시간 정규화.** §3.2의 day 목록을 `Hours = { [요일 0(일)-6(토)]: Array<[openMin, closeMin]> | "closed" }`로 정규화한다. 분 단위이고, 자정을 넘기면 close가 1440보다 크다(예: "16:00 ~ 02:00" → [960, 1560]). 브레이크타임은 구간에서 빼서 나눈다(예: "11:30 ~ 22:00" + "14:30 ~ 18:00" → [[690, 870], [1080, 1320]]). `off_days_desc`가 있으면 "closed"다. 요일은 `day_of_the_week_desc`의 첫 글자(일월화수목금토)로 정한다. 하나라도 파싱할 수 없으면 전체를 null로 한다.
- **R9 상세 TTL과 재시도.** 거점 격자에 기록된 가게의 `status='ok'` 상세는 R63 주 1회 갱신을 따른다: 그 격자를 덮는 거점들의 가장 늦은 갱신 시작(그 요일 00:00 KST) 전에 가져왔으면 다시 가져올 때다(`isPlaceDue(meta, tileKey, now, id)`). 거점 밖 격자(관리자 warm의 임의 좌표)의 ok는 예전처럼 3일 + id별 지터(0~24시간, id 해시 — 한꺼번에 수집한 가게들이 하루에 걸쳐 흩어진다, `isDetailDue`). `status='failed'`는 어디서나 6시간이 지나기 전에는 다시 가져오지 않는다. 갱신에 실패해도 이전에 성공한 표시 정보는 지우지 않는다(상태만 failed로 바꾼다). 호출마다 네트워크 오류나 5xx가 나면 지수 백오프(250ms, 1000ms)로 최대 2번 재시도한다. 4xx는 재시도하지 않는다.
- **R10 배치 처리.** 한 번의 실행(요청 또는 Cron)에서 외부 호출 예산은 `SUBREQUEST_BUDGET`(기본 40, 무료 플랜 한도 50)이다. 격자 수집이 예산을 먼저 쓰고, 상세 보충은 남은 예산 안에서 기준점에서 가까운 순으로 동시성 3으로 처리한다. 대상은 기준점을 덮는 격자에 기록된 ID 중 상세가 없거나 갱신할 때가 된 것(R9·R63)이고(ID 중복 제거), 격자 중심이 기준점(여러 거점이면 가장 가까운 거점)에 가까운 순서(같으면 id 오름차순)로 고른다. Cron(R11)은 순서가 다르다 — 미수집 먼저, 그다음 갱신 시작이 오래된 거점부터, 거점 안에서는 가까운 순(R63). 배치 중에 403이나 429가 나오면 차단 신호로 보고 그 배치의 나머지 호출을 멈추고, `meta.place_blocked_until`에 지금 + 30분을 기록한다. 이 시각 전에는 어떤 실행(요청 보충, R13, Cron, R31)도 상세 API를 부르지 않는다(R13에서 403/429가 나와도 같이 기록한다). 한 번에 보충하는 가게 수는 `DETAIL_BATCH_SIZE`다(운영 4, 2026-10-07 채우기 부스트 동안 6 — wrangler.jsonc. 천장 8(`MAX_DETAIL_BATCH_SIZE`) — 더 크면 8로 자르고, 변수가 없으면 8. Cron은 실행마다 남은 D1 호출에서 만료·격자·미수집·집계 몫을 먼저 남기고 보충 최악이 들어가는 만큼으로 다시 줄인다(`cronBatchFor`, 결과의 `batch`)). 응답이 커서 무료 플랜 CPU 한도(10ms)를 지키기 위해 작게 잡았다. 상세 본문(50~95KB JSON)을 푸는 CPU가 커서, 한 번에 읽는 본문 글자 수도 `DETAIL_CHAR_BUDGET`(운영 200,000자 ≈ 보통 상세 3곳, 코드 기본 600,000)으로 제한한다: 읽은 글자가 이 값 이상이면 새 상세를 시작하지 않고 남긴다(이미 시작한 곳은 끝낸다 — 동시 3곳. 남긴 곳(`deferred`)은 실패가 아니라 다음 실행이 같은 순서로 이어 한다). 둘 다 운영 cpuTime을 보고 설정만 바꿔 올린다. 결과(상세·실패)는 받는 대로 작은 묶음으로 저장한다: 첫 결과는 혼자 바로(실행이 CPU 한도로 죽어도 적어도 한 곳은 나아간다), 그다음은 3곳씩, 남은 것은 끝에 — 묶음마다 D1 batch 하나(거점 스냅샷 표시는 그 batch 맨 앞 한 문장, R56). 묶음의 batch가 실패하면 그 묶음을 한 곳씩 다시 저장해서 문제 있는 한 곳이 다른 곳을 막지 않고, 오류는 다른 결과를 다 저장한 뒤 알린다. 보충 후보는 SQL이 (칸 거리 순위, id)로 줄 세워 쪽(100행, 다음 쪽은 4배씩, 많아야 3쪽 = 2,100행)씩만 Worker로 보낸다. 칸마다 ok 기준을 같이 넘겨 거점 칸은 SQL이 갱신 시작으로 정확히 거르고(R63), 거점 밖 칸의 ok 지터만 Worker가 본다(모자라면 다음 쪽). 3쪽 안에서 못 채우면 그때까지 고른 것으로 하고 warm은 `pending: "more"`·`truncated: true`다(`scripts/warm.mjs`는 아무것도 못 한 truncated 응답이 3번 이어지면 멈춘다) — 덮는 격자의 상태 수천 행을 받아 오지 않는다(Task 34). warm·Cron 결과에는 `deferred`와 읽은 본문 글자 수 `chars`를 싣는다.
- **R44 상세 차단 시 강등 모드.** 비공식 상세 API가 막혀도 "어제까지의 정보로 잘 뽑히는 앱"이 되게 한다. R10 쿨다운이 새로 걸릴 때마다 `meta.block_count:{KST 날짜}`를 1 올리고(이전 쿨다운이 아직 걸려 있는 동안의 보고 — 요청 보충·Cron·R13이 겹친 같은 사고 — 는 쿨다운만 늘리고 세지 않는다), 같은 KST 날에 3번째가 되면 `meta.detail_mode`에 `{"mode":"frozen","since":지금,"until":지금 + 24시간}`을 기록한다(이미 frozen이면 since는 그대로 두고 until만 늘린다). `until` 전에는 frozen이다(24시간 뒤 자동 해제).
  - frozen이면 어떤 실행(요청 보충, R13, Cron, R31)도 상세 후보를 읽지도 상세 API를 부르지도 않는다(D1 읽기도 아낀다). 격자 수집(공식 API)은 그대로 한다. 기존 상세는 만료와 상관없이 그대로 보여준다. 새로 생긴 가게는 frozen 동안 목록에 못 들어온다(이름·좌표가 상세에서 오기 때문).
  - R12 응답에 `detailsFrozenSince`(frozen이면 since, 아니면 null)와 `detailsNewestAt`(응답에 실린 가게 중 가장 최근에 상세를 가져온 시각, 없으면 null)을 싣는다. frozen이면 `pending`이 줄지 않으므로 화면은 pending 때문에 다시 요청하지 않고, 서버는 pending이 남아 있어도 응답을 캐시한다.
  - 화면(R29 상태 줄): frozen이거나 가장 최근 상세가 8일(`STALE_DETAIL_DAYS` — R63 주 1회 갱신 + 하루 여유, 2026-10-06 결정으로 8일 유지. 갱신 요일 직전에는 가장 최근 상세도 5~7일 전이라 그때는 알리지 않는다)보다 오래됐으면 "평점·메뉴는 N일 전 기준이에요"(N = 가장 최근 상세로부터 지난 날 수, frozen이면 최소 1)를 보여준다. 순수 함수 `shared/freshness.ts`.
  - 평점이 하나도 없어도(모든 detail의 평점·리뷰가 null) 거리·다양성·개인화만으로 3곳을 뽑는다(R21 테스트로 고정).
  - 런북: frozen이 이틀 넘게 이어지면(하루 3번 차단이 매일 반복) 로컬 수집 경로(§3.2, 브레인스토밍 H3)를 판단한다.

### 5.3 사전 수집 (Cron)

- **R11 거점 유지 수집.** Cron `*/5 * * * *`로 실행한다. `shared/hubs.ts`의 모든 거점의 반경 1000m(`PREWARM_RADIUS`)가 대상이고, 외부 호출 예산 하나를 거점끼리 나눠 쓴다.
  - 거점들이 덮는 격자의 합집합(중복 제거)을 한 번에 처리한다. 실행(5분)마다 시작 거점을 하나씩 돌려서 앞 거점이 예산을 다 써도 다음 실행에는 다른 거점이 먼저 쓴다. 겹치는 거점이 있어도 한 실행에서 같은 격자·장소를 두 번 확인하거나 부르지 않는다.
  - (1) 수집할 때가 된 격자(R3·R63)를 수집하고 (2) 남은 예산으로 상세 정보(없거나 갱신할 때가 된 것 — R9·R63)를 보충한다. 상세 갱신은 Cron만 한다(R12). 순서는 미수집 먼저, 그다음 갱신 시작이 오래된 거점부터, 거점 안에서는 가까운 순(`pickCronIds`).

- **R63 거점별 주 1회 갱신.** 거점마다 가게 정보를 일주일에 한 번, 자기 요일(KST)에 다시 가져오고 화면에 마지막 업데이트를 보여준다(2026-10-06 사용자 결정). `shared/hubs.ts`의 `Hub.refreshDay`(0=일 ~ 6=토): 월 봉은사역·선정릉역 · 화 동대문역사문화공원역 · 수 판교역·내방역 · 목 정부과천청사역·광화문역 · 금 강남역·역삼역 · 토 여의도역 · 일 없음(여유 날). 역삼역·선정릉역은 많이 겹치는 거점(강남·봉은사)과 같은 요일이다. 새 거점은 같은 줄에 요일을 넣는다 — 거점이 적은 요일로(docs/deploy.md). 모든 거점의 요일이 0..6인지 테스트가 본다.

R52 읽기 전용이면 아무것도 하지 않는다. 본 Cron과 같은 분에 돌지 않고, 오래 걸려 겹쳐도 같은 상세를 두 번 쓸 뿐이다(같은 값, 커서는 언제나 대상 행이나 지나간 행 — 테스트). 관리 화면 운영 탭에 "마지막 상세만 보충"(시각·상세·외부 호출 수·건너뜀)을 따로 보인다. 처리량: (본 288 + 상세만 432)번/일 × 4곳 ≈ 하루 2,800곳(격자 수집이 몰리는 실행은 덜) vs 수요 ~1,560곳.
  - 채우기 부스트(2026-10-07, 임시 — 준비 중 거점 3곳 미수집 ~3,300곳): `DETAIL_ONLY_EXTRA` `"1"` + `DETAIL_BATCH_SIZE` 6. 상세만 실행 시간당 42번(홀수 18 + 짝수 24) × 6 + 본 Cron 12 × 6 ≈ 시간당 ~330곳이 상한이다 — 글자 예산(`DETAIL_CHAR_BUDGET` 200,000자, 상세 50~95KB)에서는 실행당 3~4곳쯤이라 실제는 시간당 ~160~220곳(`deferred`). 카카오 상세 호출 분당 ~5~6번, D1 읽기 하루 +~0.5M행(상세만 실행 +576번/일 × ~1천 행 — 읽기 몫 `DETAIL_ONLY_READ_SHARE`·R38·R44·R52·D1 호출 예산·유효 배치는 그대로). D1 호출 예산: 배치 6은 천장(8) 안이라 보통 본 Cron과 상세만 실행 최악(저장 실패 한 곳씩 다시 + 차단 기록) 모두 50번 안이다(테스트). 끄기: `DETAIL_ONLY_EXTRA` `"0"` + `DETAIL_BATCH_SIZE` `"4"`로 배포(트리거는 그대로). 롤백 주의: 부스트 앞 버전은 모르는 cron(`* * * * *`)을 본 Cron으로 돌리므로 둘째 트리거를 `1-59/2`로(R63 앞이면 `2-59/5`로) 되돌린다 — `npm run release`가 설정의 `crons`에서 이를 알아보고 종료 코드 3.
  - 화면 날짜: 응답의 `refreshedAt`은 끝낸 시각이 아니라 마지막으로 끝낸 갱신의 시작(갱신 요일 00:00 KST)이다 — "가게 정보 10월 9일(금) 업데이트 · 매주 금요일"은 이틀 걸려 끝나도 갱신 요일 날짜로 보인다(관리 화면은 끝낸 시각도 보인다). `refreshedAt`·`refreshDay`는 타입에서 선택 필드다(예전 기기 저장본에는 없다 — 화면은 `?? null`·`isRefreshDay`로 거른다).
  - R38: 그날(UTC 기준, 한국 시각 09시에 초기화 — D1 무료 한도와 같은 날짜) D1 읽기가 소프트 한도를 넘었으면 수집·보충을 건너뛰고(`skipped: "read_budget"`) 캐시된 데이터만 보여준다. KST 04:00~04:04에 걸리는 실행은 먼저 R35 보관 정리를 한다(한도를 넘은 날에도).

### 5.4 API

- **R12 `GET /api/places?hub&radius`.**
  - 검증: `hub`는 `shared/hubs.ts`의 거점 id, `radius`는 100~1000m의 50m 배수. 위반하거나(모르는 거점 포함) 임의 lat/lng를 보내면 400과 `{error: "invalid_params"}`를 반환한다. 좌표는 서버가 거점 목록에서 찾는다(남용과 비용 방지; 임의 좌표는 관리용 R31/R32만).
  - 화면은 반경과 상관없이 항상 `radius=1000`을 요청하고 반경은 브라우저에서 거른다(R42). 서버는 50m 단위 반경을 계속 검증하지만(호환), 어떤 반경이 와도 거점의 1000m 목록 하나만 계산·캐시해서 같은 본문(`radius: 1000`)을 준다 — 캐시 키가 거점당 하나라 반경을 바꾼 요청으로 캐시를 우회해 D1을 읽게 할 수 없다.
  - 캐시: Workers Cache API(`caches.default`)에 `https://cache.mmj/places?hub&v={응답 형식 버전}` 키(거점당 하나)로 저장하고, 다음 요청은 D1을 읽지 않고 캐시로 답한다. 시간은 `placesCacheTtl`: 공식 API 실패가 섞인 응답(`stale`)만 저장하지 않는다. `incompleteTiles > 0`(예산·요청 제한으로 격자를 다 못 모음)이면 10초. 그 밖에 `pending === 0`이거나 상세 가져오기가 멈췄으면(`detailsPaused` — R10 쿨다운·R44 frozen, 아무도 pending을 줄일 수 없다) 60초(`Cache-Control: public, max-age=60, s-maxage=60`), pending만 남았으면 10초 — 같은 거점을 폴링하는 여러 화면이 계산(과 요청 보충 시작) 하나를 나눠 쓴다. 요청 제한에 걸린 요청도 10초 캐시를 받으므로, IP 하나를 함께 쓰는 사무실이 분당 10회를 넘겨도 매번 D1을 읽지 않는다. 브라우저에 주는 응답은 항상 `no-store`다. 키는 거점 수(5개)뿐이다(예전에는 거점 × 반경 19단계 = 95개). 응답 형식 버전은 8(4: 반경을 키에서 뺌·`detailsPaused` 추가, 5: `list_json` 조각, 6: `list_json` 판, 7: R56 스냅샷 — 엣지 항목이 gzip 바이트일 수 있고 거리가 같으면 id순, 8: R63 `refreshedAt`·`refreshDay`; 스냅샷 판 `HUB_SNAPSHOT_VERSION`은 2). 엣지 캐시 미스는 먼저 R56 거점 스냅샷(D1 1행)으로 답하고, 그 응답은 엣지에 10분 둔다.
  - 처리: `tilesCoveringCircle`로 격자를 구하고, 만료/미수집 격자를 예산 안에서 동기적으로 수집한다(ID만 기록). 격자-장소 상태(`tile_places` + places 메타)는 요청마다 한 번만 읽어서 목록 필터, `pending`, 보충 대상 고르기에 같이 쓴다. 그다음 D1에서 덮는 격자에 기록된 가게 중 상세가 있고 거리 ≤ radius인 것을 조회한다. R13 단건 조회로만 저장된 가게는 목록에 넣지 않는다. 목록 원소는 `places.list_json`(0005, 상세를 저장할 때 같이 만든 조각)에 거리·도보 분만 앞에 붙여 이어 붙인다 — 행마다 JSON 열 4개를 parse하고 다시 stringify하지 않는다(동대문 1000m 2,000곳: node 중앙값 8.8ms → 0.65ms, Workers는 ×3으로 어림잡아 ~26ms → ~2ms). 지금 판(`LIST_JSON_VERSION`)의 `list_json`이 없는 행(NULL·예전 판·깨진 값)만 열에서 만들고 본문은 글자까지 같다. 지금 판 조각이 있는 행은 D1에서 무거운 열을 받지 않는다(`CASE WHEN substr(list_json, 1, 4) = 'v1:{'`). 상세가 아직 없는 장소는 좌표를 모르므로 응답에 넣지 않고 `pending`으로만 센다. 상세를 한 번도 가져오지 않은 가게가 있으면(쿨다운 중이 아니면) `ctx.waitUntil`로 그 가게들만 R10 배치를 시작한다. 만료된 상세는 그대로 보여주고 갱신은 Cron(R11)에 맡긴다.
  - 응답:
    ```ts
    {
      center: { lat, lng }, radius,
      places: Array<{
        id, name, group, category, lat, lng,
        distance,        // m, 정수
        walkMinutes,     // R26
        url, photoUrl,   // address, phone은 화면이 쓰지 않아서 목록에는 싣지 않는다 (R13 단건에는 있다)
        detail: null | {
          rating, reviewCount, price, menus /* 목록은 상위 3개 */, hours, strengths, bookable,
          soloFriendly, groupFriendly  // R19 판단 결과 (태그 원문은 보내지 않는다, 규칙은 shared/friendly)
        }
      }>,
      pending: number,   // 덮는 격자에 ID는 기록됐지만 상세를 아직 한 번도 가져오지 않은 장소 수 (반경이 아니라 격자 기준)
      incompleteTiles: number, // 예산 부족으로 이번에 못 수집한 격자 수
      stale: boolean,    // R14 공식 API 실패 (요청 제한으로 건너뛴 것은 아님)
      detailsPaused: boolean, // R10 쿨다운·R44 frozen으로 상세 가져오기가 멈춤 (화면은 pending 때문에 폴링하지 않는다)
      detailsFrozenSince: number | null, // R44 강등 모드 시작 시각 (epoch ms)
      detailsNewestAt: number | null,    // R44 응답에 실린 가게 중 가장 최근 상세 시각
      refreshedAt: number | null,        // R63 마지막으로 다 끝낸 주간 갱신의 시작 = 갱신 요일 00:00 KST (없으면 null, 갱신 중에는 지난번 것)
      refreshDay: number                 // R63 거점의 주 1회 갱신 요일 (KST, 0=일 ~ 6=토)
    }
    ```
  - `Cache-Control: no-store`
- **R13 `GET /api/places/:id`.** 단일 가게 정보를 반환한다(형식은 R12의 원소와 같고, distance와 walkMinutes는 빠지며 address·phone과 메뉴 전부(최대 20개), 상세를 가져온 시각 `fetchedAt`(epoch ms, R48)을 준다 — 목록 원소에는 없다). 거점 격자(모든 거점의 1000m 격자)에 기록되지 않은 ID는 상세를 가져와 보여주기만 하고 저장하지 않는다(성공이든 실패든 — 임의 숫자로 D1을 키울 수 없고, Cron이 갱신하지 않는 행이 만료 조회에 쌓이지 않게). 대신 성공한 응답은 Workers Cache API에 id별 키(`https://cache.mmj/place?id&v={응답 형식 버전}`)로 60초(`PLACE_TRANSIENT_CACHE_MS`) 두어서, 같은 공유 링크를 여럿이 연달아 열어도 상세 API는 60초에 한 번(R15 제한 안)만 부른다. 거점 격자 안의 id는 D1에 저장하므로 엣지에 두지 않는다. 브라우저에 주는 응답은 언제나 `no-store`다. 화면은 카드를 열 때 이것을 한 번 불러 목록 원소의 상세와 바꾼다. id는 숫자 1~15자리만 허용하고 아니면 404다. 표시 정보가 없으면 R15 제한 안에서 동기적으로 한 번 상세를 가져온다(최근 6시간 안에 실패했거나 R10 쿨다운 중이면 시도하지 않음). 그래도 없으면 404다.
- **R56 거점 스냅샷.** 엣지 캐시 미스의 CPU·D1 읽기를 줄인다(운영 측정: 미스 CPU 22~53ms, 읽기 2~6천 행).
  - 만들기(둘째 트리거 `1-59/2 * * * *`의 7·17·27·37·47·57분(UTC) — 시간당 6번, 실행마다 한 거점. R63 전에는 `2-59/5`): 본 Cron(`*/5`, 수집·보충)과 다른 실행이라 CPU 한도와 D1 사용량 기록을 따로 쓴다 — 만들다 CPU 초과로 죽어도 본 Cron 기록은 잃지 않는다(scheduled가 `controller.cron`과 `controller.scheduledTime`의 분으로 나눈다 — `secondCronJob`, 모르는 cron 값은 본 Cron). 외부 호출은 없다. 요청 경로와 같은 읽기·조립(`readListRows`, `placesPayload`, `placesBody`)으로 거점 1000m 본문을 만들어 gzip(`CompressionStream`) → base64로 `hub_snapshots`에 한 행 둔다. 거리가 같은 가게는 id순으로 정해서(R12도 같다) 같은 데이터면 본문이 글자까지 같다. 만들지 않는 때: 상세가 없는 가게가 있음(`pending > 0` — 지금 경로가 보충을 시작하고 알린다. 격자-장소 상태만 보고 판단해서 무거운 목록 조회 전에 멈춘다), 거점 격자 중 만료·미수집 격자가 있음(`incompleteTiles`·`stale`은 수집하는 지금 경로가 정한다), 쿨다운·frozen이 쓰는 동안(2시간) 안에 끝남(`detailsPaused`·`detailsFrozenSince`가 틀린 채로 남지 않게), base64가 1.5MB 초과.
  - 고르는 순서: 스냅샷이 없거나 판이 다른 거점(실행마다 돌아가는 거점 순서) → 더러운데 만든 지 60분이 지났거나, 깨끗해도 만료 15분 전인 것 중 가장 오래된 것. 할 일이 없으면 메타 몇 행만 읽는다. R38 읽기 예산을 넘은 날에는 만들지 않는다(그날은 미스가 지금 경로로 답한다).
  - 비용 상한: 만들기 전에 `meta snapshot_skip:{hub}` = `{until, attempts}`(attempts = 이어서 끝나지 못한 시도 수 + 1)를 써 두고, until 전의 거점은 고르지 않는다. 시도가 CPU 초과로 죽으면 표시가 남고, 이어서 죽을수록 기다림이 두 배씩 는다(20 → 40 → 80분 … 최대 6시간 — 죽은 실행은 사용량도 기록하지 못해서 이것이 헛읽기의 유일한 상한이다). 만들었거나 기다릴 필요가 없는 건너뜀(쿨다운·경쟁 — 무거운 읽기 전에 판단해서 싸다)이면 지우고, pending·만료 격자면 20분, 크기 초과면 2시간을 attempts 0으로 쓴다 — 만들 수 없는 거점(예: R44 frozen 동안 pending이 줄지 않음)이 실행마다 수천 행을 다시 읽지 않는다. 쓸 수 있는 스냅샷이 있는 거점은 그 만료 5분 전 너머로 기다리지 않는다(스냅샷이 끊기기 전에 한 번 더 해 본다). 실행마다 처음에 그 실행이 넘겨받은 거점 목록(운영은 `shared/hubs.ts` 전체)에 없는 거점과 2시간이 지난 행을 지운다.
  - 더러움 표시(`meta snapshot_dirty:{hub}`, 바뀔 때마다 커지는 정수): 상세 저장·실패 기록은 같은 batch에서 그 가게의 옮기기 전·후 좌표가 거점 1000m 상자 안인 거점을, 격자 ID 변경(R4)은 그 격자를 덮는 거점을 올린다. 스냅샷은 만들기 전에 읽은 표시를 `source_at`에 두고, 저장은 표시가 그대로일 때만 한다(만드는 사이 바뀌면 다음 실행이 다시 만든다).
  - 무효화(행 삭제 + 표시): 격자에 새 ID가 들어오면(pending이 생긴다) 그 격자를 덮는 거점, R10 쿨다운이 새로 걸리면(R44 frozen 포함) 모든 거점. R63 거점 갱신 완료 기록은 표시만 올린다(본문의 `refreshedAt`이 바뀐다 — 늦어도 60분 뒤 다시 만든다).
  - 내보내기: 엣지 캐시 미스면 먼저 스냅샷 한 행을 읽는다(D1 1행). 판이 같고 만든 지 2시간 안이면 그대로 답한다 — gzip을 받는 화면에는 `Content-Encoding: gzip` + `encodeBody: "manual"`(Workers가 다시 압축하지 않는다), gzip을 받지 않으면(값이 없거나 거절) `DecompressionStream`으로 풀어서 준다. 판단은 `request.cf.clientAcceptEncoding`(운영 Cloudflare가 Worker로 오는 `Accept-Encoding`을 바꿨을 때 남기는 원래 값)을 먼저, 없으면 `Accept-Encoding` 헤더를 본다. 스냅샷 200 응답에는 `Vary: Accept-Encoding`을 싣는다. 판·인코딩·나이(2시간)는 SQL `WHERE`에서 걸러 쓸 수 없는 행의 본문은 받지 않는다. 아니면 지금 경로(R12)로 답한다. 응답 헤더 `x-mmj-source`: `edge` | `snapshot` | `live`.
  - ETag와 304: 스냅샷 응답은 약한 ETag `W/"{판}-{거점}-{gzip SHA-256 앞 16자}"`를 싣는다(본문이 같으면 다시 만들어도 같다). `If-None-Match`가 같으면(약한 비교, 목록, `*`) 본문 없이 304 — 스냅샷 경로는 본문 열을 받지 않고(`CASE WHEN`), 엣지 적중도 304로 답한다. 지금 경로 응답에는 ETag가 없다. 화면(R45)은 기기 저장본과 함께 ETag를 두고, ETag만 localStorage 작은 키(`mmj-places-etag:{hub}`)에도 둬서 첫 요청을 저장본(~1MB) 읽기·해석을 기다리지 않고 바로 `If-None-Match`로 보낸다. 304면 그때 저장본의 ETag가 같은지 보고 새 목록으로 쓰고(전송 ~0바이트), 저장본이 없거나 다르면 조건 없이 다시 받는다. 폴링에는 보내지 않는다.
  - 엣지 캐시: 스냅샷으로 답한 응답은 gzip 바이트로 10분(스냅샷을 쓸 수 있는 남은 시간이 더 짧으면 그만큼) 둔다. 지금 경로 응답의 10초/60초 규칙(R12)은 그대로다. Cache API 삭제는 Cron이 도는 콜로 하나에만 듣기 때문에 쓰지 않는다 — 다시 만들거나 무효화한 스냅샷은 늦어도 10분 뒤 모든 콜로에 보인다(무효화된 pending·쿨다운 상태도 최대 10분 늦다).
  - 늦게 보이는 최대 시간: 상세 갱신(평점·메뉴) 약 60분 + Cron 5분 + 엣지 10분. 새 가게는 격자 변경이 스냅샷을 지우므로 엣지 10분 뒤 지금 경로로 바로 보인다.
  - 판: `HUB_SNAPSHOT_VERSION`(worker/hubSnapshot.ts). 주의: `/api/places` 본문이 바뀌면(`PLACES_CACHE_VERSION`·`LIST_JSON_VERSION`을 올리는 변화) 같이 올린다.
- **R14 장애 대응.** 공식 API가 실패하고(쿼터 초과, 5xx, 타임아웃) 해당 격자에 만료된 캐시가 있으면 그 캐시로 응답하고 `stale: true`를 준다. 캐시도 없으면 502와 `{error: "upstream"}`을 반환한다.
- **R15 남용 방지.** 외부 호출을 일으키는 요청(만료/미수집 격자가 있는 R12, 동기 보충이 필요한 R13)은 IP당 분당 10회로 제한한다(Workers Rate Limiting 바인딩). 초과하면 외부 호출 없이 캐시로만 응답한다 — 못 모은 격자는 `incompleteTiles`, 못 채운 상세는 `pending`으로 남고 `stale`은 주지 않는다(`stale`은 R14 실패만). 이 응답은 10초 캐시된다(R12). 캐시로만 응답할 수 있는 요청은 제한하지 않는다.

### 5.5 추천 로직 (브라우저, `shared/recommend`)

- **R16 반경.** 반경 슬라이더 하나로 정한다: 100~1000m, 50m 단위, 기본 500m. 현재 값을 "반경 500m · 도보 약 10분"(R26)처럼 보여준다. 점심시간 프리셋(30/60/90분)은 없앴다. 상한 1000m는 Cron이 유지하는 반경(R11)과 같다. 슬라이더는 네트워크를 기다리지 않고 바로 반영된다(R42: 거점의 1000m 목록을 이미 갖고 있고 브라우저에서 거리로 거른다).
- **R17 영업 중 필터.** 기본 ON. 현재 시각 `now`(KST)와 `now + 30분`이 모두 같은 영업 구간 안에 있을 때만 영업 중으로 본다. 전날 밤부터 이어지는 구간(close > 24:00)도 고려한다. 자정에서 끝나는 구간이 다음 날 0시에 시작하는 구간과 맞닿아 있으면 하나의 연속된 구간으로 본다(다음 날이 휴무면 자정에서 끝난다). 오늘 요일의 정보 자체가 없으면 "영업 정보 없음"으로 취급한다. 영업시간이 null이면 "영업 정보 없음"으로 표시하고 필터를 통과시킨다.
- **R18 필터.**
  - 카테고리: 다중 선택, 아무것도 선택하지 않으면 전체(`bar` 제외). `bar`는 "술집 포함" 토글을 켰을 때만 들어간다(기본 OFF).
  - 1인 예산: 전체 / 1만 이하 / 1.5만 이하 / 2만 이하. "전체"가 아니면 price가 null인 곳은 제외한다.
  - 최소 평점: 무관 / 3.5+ / 4.0+. "무관"이 아니면 rating이 null인 곳은 제외한다.
  - 반경: 거리 ≤ radius
- **R19 인원 휴리스틱.** 인원 선택지는 1 / 2 / 3 / 4+이고 기본값은 2다.
  - 아래 두 판단은 서버가 `shared/friendly` 규칙으로 계산해 `soloFriendly`/`groupFriendly`로 내려준다.
  - 1명: 혼밥 친화(`category_name`에 국밥, 해장국, 라멘, 라면, 분식, 덮밥, 돈까스, 우동, 국수, 김밥, 패스트푸드 중 하나라도 포함하거나, tags에 "혼밥"이 있음)면 가중치 ×1.5
  - 4명 이상: `snack` 그룹 제외. tags에 "단체석", "회식장소", "모임맛집" 중 하나라도 있으면 ×1.3, `bookable === true`면 추가로 ×1.3
  - 2~3명: 보정 없음
- **R20 정렬.** 거리순(기본) / 평점순(null은 맨 뒤) / 가격순(오름차순, null은 맨 뒤).
- **R21 3곳 뽑기.** 필터를 통과한 후보에서 서로 다른 곳을 최대 3곳, 가중 랜덤으로 뽑는다(비복원 추출, `shared/recommend.ts`의 `drawTrio`).
  - 가중치 = `base × 인원 보정 × 개인화 배수(R37) × 시간대 배수(R50)`
  - `base = max(0.3, rating − 3) × log10(reviewCount + 10)`, rating이 null이면 `base = 0.5`
  - 다양성: 한 곳을 뽑을 때마다 같은 그룹(`group`)의 남은 후보는 다음 뽑기에서 가중치 ×0.35(같은 그룹이 2곳 뽑혔으면 ×0.35²). 강제가 아니라서 그룹이 하나뿐이어도 3곳을 채운다.
  - 개인화 배수가 0인 곳("다음부터 안 보기")은 후보에서 뺀다.
  - "다시 뽑기"는 이번 세션에서 이미 보여준 곳을 빼고 뽑는다. 남은 곳이 3곳보다 적으면 남은 곳을 먼저 넣고, 제외 목록을 비운 뒤 나머지를 채운다(`reset: true`, "후보를 다 돌아서 처음부터 다시 뽑아요" 토스트; 후보가 3곳 이하이면 "조건에 맞는 곳이 N곳뿐이에요"). 한 결과 안에서는 중복이 없다. 거점을 바꾸면 제외 목록을 비운다.
  - 후보가 0~2곳이면 R41로 덜 중요한 조건부터 자동으로 풀어 3곳을 채운다. 풀어도 1~2곳이면 있는 만큼만 보여준다. 풀어도 0개면 "조건에 맞는 곳이 없어요" 토스트를 띄우고, 리스트 자리의 빈 상태(R29)에 지금 켜져 있는 조건만 푸는 버튼을 보여준다: "영업 중만 해제", "평점 무관", "예산 전체", "카테고리 전체", "반경 +300m"(최대 1000m).
  - 난수 함수는 주입받는다(테스트에서 결정적으로 검증하기 위해).
- **R22 슬롯 셔플과 3곳 결과.** "모먹죠?"를 누르면(재방문자는 R39로 열자마자 한 번 자동으로) 결과 시트(모바일은 바텀 시트, 데스크톱은 지도 위 오버레이) 이름 자리에 후보 이름이 약 0.8초 동안 바뀌다가 멈춘다. 이름이 바뀌는 간격은 50ms에서 140ms로 점점 늘어난다(감속). `prefers-reduced-motion`이면 셔플과 애니메이션 없이 바로 결과를 보여준다.
  - 멈추면 시트에 작은 후보 카드 3장이 쌓인다. 머리: `thumbsup` 마스코트 + "모먹죠가 고른 3곳"(공유 링크로 받았으면 "공유받은 후보 3곳"; 3곳보다 적으면 그 수) + "눌러서 메뉴와 영업시간을 볼 수 있어요". 카드: 56px 사진(없으면 크림 타일 + 그룹 아이콘 `GROUP_GLYPH`), 왼쪽 위 번호 1/2/3, 이름, 사실 줄 "도보 N분 · ★4.3 · 근처 상위 N%"(곧 마감·지금 닫힘이면 강조 글자), "[이유(R46)] · 카테고리 · 1인 가격".
  - 카드를 누르면 그 자리에서 펼친다(아코디언, 한 번에 하나). 순서: 영업 상태 · 오늘 영업시간 · 리뷰 수 → 강점 → 행동(4명+면 맨 위에 "전화로 자리 확인"(R49), 그 아래 한 줄에 조용한 "카카오맵에서 보기" 링크 · "여기로 가자고 공유"(R47) · "다음부터 안 보기"(R37)) → 메뉴(R13을 그때 한 번 불러 전체 메뉴로; 모바일·데스크톱 모두 처음 5개, 더 있으면 조용한 "메뉴 N개 더 보기"/"메뉴 접기", `web/format.ts` `menuPreview`) → 맨 아래 정보 확인 시점(R48). 메뉴가 길어도 행동이 폰 첫 화면(375·360px)에 보이게 행동을 메뉴 위에 둔다.
  - 아래 행동: 주 버튼 "공유"(3곳 모두, R23), 보조 "다시 뽑기". 모바일은 시트 바로 아래 뽑기 바가 "다시 뽑기"(보조 모양)를 맡아서 시트 안의 "다시 뽑기"는 숨긴다. 작게 "정보 출처: 카카오맵". 시트가 화면 높이의 60%를 넘으면 안쪽만 스크롤하고 행동 영역은 아래에 붙어 있다.
  - 지도: 뽑힌 3곳은 번호(1/2/3)가 든 큰 마커와 이름표로 강조하고, 먼저 3곳이 모두 보이게 맞춘다(시트가 가리는 만큼 여백을 더 둔다). 카드를 펼치면 그 핀으로 이동하고 그 핀의 이름표만 남긴다. 결과 3곳 중 하나를 목록이나 핀에서 누르면 그 카드를 펼친다. 다른 곳을 누르면 그 한 곳의 상세 카드(R28)를 결과 위에 열고, 닫으면 결과 3곳으로 돌아간다.
  - 셔플이 끝나면 15ms 진동(`navigator.vibrate`)을 준다. 폴링으로 목록이 바뀌어도 결과 3곳은 그대로 두고 최신 객체(상세)로만 바꾼다. 뽑은 뒤 뽑기 버튼 문구는 "다시 뽑기"가 된다.
  - 경쟁 상태: 셔플 중에는 뽑기 버튼을 비활성화(`disabled`)하고 "고르는 중…"으로 표시하며, Esc·시트 닫기·목록/핀 선택을 받지 않는다. 거점이나 반경을 바꾸면 진행 중인 셔플을 취소하고 결과 3곳을 비운다(공유 링크 불러오기도 취소). 펼친 카드가 바뀌면 이전 R13 요청은 취소한다.
- **R23 공유.** "공유" 버튼을 누르면 보여주는 후보 전체(최대 3곳)를 아래 텍스트(`shareText`)로 공유한다. 터치 기기(`pointer: coarse`)이고 `navigator.share`가 있으면 클릭 핸들러 안에서 바로 `navigator.share({ title: "모먹죠", text })`를 호출하고, 사용자가 공유 시트를 닫으면(AbortError) 아무것도 하지 않는다. 그 밖의 경우(데스크톱, 미지원, 공유 실패)는 클립보드에 복사하고 "복사했어요" 토스트를 띄운다. 복사도 실패하면 "복사하지 못했어요"를 띄운다. 공유·복사에 성공하면 그 곳들을 R37 `shared` 신호로 남긴다.
  ```
  🍚 점심 고? ({인원}명 · {거점 이름} 반경 {radius}m)
  1. {가게명} · {카테고리 마지막 단계} · ★{rating} · 도보 {walkMinutes}분
  2. ...
  3. ...
  이 중에 어디 갈래요? 👉 https://mmj.itmz.me/{거점 id}?t={id1},{id2},{id3}&r={radius}
  ```
  평점이 null이면 `★` 부분을 생략한다. 인원이 4+이면 "4명+"로 쓴다. 3곳보다 적으면 그만큼만 줄을 쓰고, 한 곳만 공유하면(상세 카드의 "공유") 마지막 줄은 "여기 어때요? 👉 …"이다.
  - 공유 URL을 열면 해당 거점(경로 `/{거점 id}`(R43) 또는 예전 링크의 `h`, 거점 목록에 있는 id만)과 반경(`r`, 50m 단위만)을 적용하고, `t`(쉼표로 이은 숫자 1~15자리 id, 중복 제거, 최대 3개; 잘못된 칸은 무시)의 가게를 **목록 응답과 상관없이** R13으로 동시에 받아 "공유받은 후보 N곳" 시트로 보여준다(목록 요청이 실패해도 보여준다; 도보 시간은 현재 거점 기준). 일부를 찾지 못하면 찾은 곳만 보여주고 "N곳은 찾지 못했어요"를 한 번 띄우고, 하나도 못 찾으면 "공유된 가게를 찾지 못했어요". 공유받은 곳은 R37 `received` 신호로 남긴다(빼둔 곳이어도 보여준다).
  - 예전 링크 `p`(숫자 1~15자리 하나)도 읽는다(`t`가 있으면 `t` 우선). id가 하나뿐이면 "공유받은 곳" 상세 카드(R28)로 연다. 예전 링크의 `lat`/`lng`는 무시한다. 파라미터를 적용한 뒤에는 주소창에서 지운다(새로고침하면 저장값으로 돌아간다).
  - 링크 미리보기는 `index.html`의 정적 OG 태그로만 한다: `og:title` "모먹죠 - 점심 고?", `og:description`, `og:image` `https://mmj.itmz.me/og.png`(1200×630 PNG), `twitter:card` `summary_large_image`. 장소별 동적 OG와 카카오 SDK 공유는 하지 않는다.

  - "다음부터 안 보기": 펼친 결과 카드의 조용한 글자 버튼. 누르면 배수 0(목록·지도·뽑기 후보에서 모두 빠짐)이 되고 결과에서 그 카드가 사라진다. "{가게 이름}은/는 다음부터 안 뽑아요"(조사는 이름 끝소리로 — `shared/share.ts`의 `topicParticle`·`excludeToastText`; 숫자·영문은 읽는 소리로) + "되돌리기" 토스트를 8초 동안 보여주고, 되돌리면 원래대로 돌아온다. 버튼 이름은 무엇을 하는지(동사)와 결과를 말한다 — 예전 "여긴 빼줘"·"여기로 가요"는 뜻이 모호하다는 의견이 있어 바꿨다.
- **R39 열자마자 3곳.** 재방문자는 "모먹죠?"를 누르지 않아도 목록이 오면 한 번 자동으로 뽑아 결과 시트를 띄운다(탭 1번 → 0번).
  - 조건(모두): 재방문자(첫 방문 안내를 닫았거나 R37 신호가 하나라도 있음), 공유 링크(`t`·`p`)로 열지 않음, 이번 탭 세션(sessionStorage `mmj:auto-draw:v1`)에서 아직 자동으로 뽑지 않음, 사용자가 아직 아무것도 하지 않음(문서의 첫 `pointerdown`·`keydown`·`wheel`·`touchstart`), 오늘(KST) 자동 뽑기를 끄지 않음(`mmj:auto-draw-off` ≠ 오늘), 거점 목록이 다 왔고(pending 폴링이 끝났거나 처음부터 다 찬 응답, 또는 24시간 안의 기기 저장본 — 폴링 중인 일부 목록으로는 뽑지 않고, 폴링으로 후보가 늘어도 다시 뽑지 않는다) 뽑을 후보(R41 완화 포함)가 1곳 이상.
  - 자동 뽑기는 보통 뽑기와 같지만 R37 `shown` 신호를 남기지 않고, 첫 방문 안내를 닫지 않으며, R35 `draw` 이벤트에 `props.auto: true`를 붙인다. `prefers-reduced-motion`이면 셔플 없이 바로 보여준다(R22와 같음).
  - 자동으로 뜬 시트를 (다시 뽑지 않고) 닫으면 오늘 날짜(KST)를 `mmj:auto-draw-off`에 저장해서 그날은 다시 자동으로 띄우지 않는다. localStorage·sessionStorage를 못 쓰면 이번 페이지에서만 기억한다.
- **R40 최근 먹은 종류 피로도.** 그룹 가산(R37)은 같은 종류를 더 자주 내놓는 방향으로만 작동해서, 짧은 반대 힘을 더한다. 최근 36시간 안에 카카오맵을 열었거나(`kakao_open`) 공유한(`shared`) 가게와 세부 종류(`cat` = 카테고리 마지막 단계, `shared/category.ts`의 `lastLevel`; 예: 국밥, 라멘)가 같은 가게는 그 1번(같은 시각은 1번)마다 ×0.6, 바닥 0.4. `cat`이 없는 예전 신호와 빈 종류는 세지 않는다. 그룹 단위로 하지 않는 이유: 봉은사역 1km 가게의 절반 가까이가 한식이라 너무 크게 흔들린다. 순수 함수 `shared/personal.ts`의 `categoryFatigue`.
- **R41 부족하면 알아서 완화.** 뽑을 때 후보(R37 빼둔 곳 제외)가 3곳보다 적으면 빈 상태 버튼을 고르게 하는 대신 덜 중요한 조건부터 하나씩 풀어 3곳을 채운다: 최소 평점 → 예산 → 카테고리 → 반경 +300m(최대 1000m). 켜져 있는 조건만 풀고, 3곳이 되면 멈춘다. **영업 중 조건과 인원(4명+ 분식 제외)·술집·디저트 제외는 풀지 않는다.** 순수 함수 `shared/recommend.ts`의 `relaxToFill`.
  - 뽑기는 원래 조건에 맞는 곳을 먼저 넣고(이미 보여준 곳 제외 규칙은 R21과 같음) 모자란 만큼 완화로 들어온 곳에서 채운다(`drawTrio`의 `extra`).
  - 결과에 실제로 뽑힌 완화 후보가 어긴 조건만(`relaxedBy`, 완화 후보 전체가 아니라) 한 줄 토스트로 알려준다: "조건에 맞는 곳이 적어서 평점·예산 조건을 풀었어요", 반경만이면 "조건에 맞는 곳이 적어서 반경을 300m 넓혔어요", 둘 다면 "… 평점 조건을 풀고 반경을 300m 넓혔어요". 원래 조건에 맞는 곳이 0곳이면 "적어서" 대신 "없어서"라고 한다. 완화로 들어온 결과 카드에는 옅은 "조건 밖" 표시를 단다.
  - 원래 조건의 후보가 0곳인데 조건 밖에서 고른 결과가 떠 있으면, 목록 자리의 빈 상태는 "조건에 딱 맞는 곳은 없어서 조건 밖에서 골랐어요"라고 하고 조건 풀기 버튼은 그대로 둔다.
  - 풀어도 0곳이면 기존 빈 상태(R29, 조건 풀기 버튼)를 그대로 쓴다. 목록(리스트·지도 핀)은 원래 조건 그대로다.
- **R46 3곳에 "왜" 한 단어.** 결과 카드마다 보여주는 곳들(2곳 이상) 안에서 글자 그대로 참인 이유를 최대 하나 붙인다(`shared/reasons.ts`의 `trioReasons`): "제일 가까워요"(도보 분이 혼자 가장 작음; 도보 분을 모르는 곳이 있으면 붙이지 않음), "평점 최고"(평점을 아는 곳 2곳 이상 중 혼자 가장 높고 4.0 이상이며 리뷰 20개 이상 — `REASON_MIN_REVIEWS`; 리뷰 몇 개짜리 5.0을 최고라 하지 않는다), "가성비"(가격을 아는 곳 2곳 이상 중 가격대 — R18 예산 경계 1만/1.5만/2만 — 가 혼자 가장 낮고 평점 3.8 이상이며 리뷰 20개 이상), "처음 보는 곳"(이 기기에서 본 곳이 15곳 이상(`NEW_PLACE_MIN_SEEN`)일 때, 본 적 없는 곳이 혼자). 이 순서대로 주인이 아직 이유가 없을 때만 붙여 같은 말이 두 카드에 나오지 않고, 동점이면 붙이지 않는다. R41 "조건 밖" 카드에는 이유를 붙이지 않는다(표시는 카드당 하나; 그 카드가 이긴 이유를 다른 카드에 넘기지도 않는다 — 참이 아니라서). "처음 보는 곳"은 R37 신호가 아니라 기기의 본 곳 기억으로만 판단한다: `web/seen.ts`(localStorage `mmj:seen:v1`, `{장소 id: 마지막으로 본 시각}`; 순수 함수 `shared/seen.ts`의 `markSeen`·`pruneSeen`·`isNew`)는 결과로 보여준 곳(직접 뽑기, R39 자동 뽑기, 공유받은 후보)과 목록·핀에서 연 카드(공유받은 한 곳 포함)를 모두 기억하고, 30일 지나면 잊으며, 최대 500곳(넘치면 가장 오래전에 본 곳부터 버림)이다. 판단은 그 결과를 기록하기 전의 기억으로 한다(이번 결과가 "처음 보는 곳"을 지우지 않게). 읽기·쓰기에 실패하면 조용히 이번 세션 메모리에만 둔다. 서버로 보내지 않는다. 배지가 아니라 카드 둘째 줄(카테고리·가격 줄) 맨 앞의 조용한 글자다 — 사실 줄은 375px에서 이미 꽉 차서(241px) 넣으면 R34 알약이 잘린다. 둘째 줄은 끝이 말줄임이라 이유는 늘 보인다.
- **R47 "여기로 가자고 공유" 확정 공유.** 펼친 결과 카드의 "카카오맵에서 보기" 옆에 조용한 보조 행동 "여기로 가자고 공유"를 둔다(아래 "공유" 줄은 그대로). 누르면 그 한 곳을 확정하는 문구를 R23과 같은 방식(폰은 시스템 공유 시트, 아니면 복사)으로 보낸다(`shared/share.ts`의 `shareConfirmText`):
  ```
  👉 {가게명}(으)로 가요! 도보 {walkMinutes}분
  {카카오맵 장소 URL}
  https://mmj.itmz.me/{거점 id}?t={id}&r={radius}
  ```
  조사는 이름 끝 글자(괄호·공백 같은 기호는 건너뜀)의 받침으로 고른다(받침이 있으면 "으로", 없거나 ㄹ이면 "로"; `toParticle`). 끝이 숫자·영문이면 읽는 소리의 받침으로: 숫자 0 영·3 삼·6 육은 "으로", 1 일·7 칠·8 팔(ㄹ)과 2·4·5·9는 "로"; 영문 M·N(엠·엔)은 "으로", L(엘)과 나머지는 "로"(대소문자 같음). 도보 시간을 모르면 도보 부분을 뺀다. 성공하면 R37 `shared` 신호를 그 한 곳에만 남기고 R35 `share`에 `placeId`와 `props.confirm: true`(`picks`는 그 한 곳)를 붙인다.
- **R48 정보 확인 시점.** 펼친 결과 카드(R22)는 R13 응답의 `fetchedAt`으로 맨 아래에 조용한 글자 "N일 전 확인"(24시간 안이면 "오늘 확인", 내림)만 작게 보여준다(`shared/freshness.ts`의 `checkedText`). 출처("정보 출처: 카카오맵")는 시트 아래 줄에 이미 있어서 카드에서는 되풀이하지 않는다. 단건을 아직 받지 못했으면 보여주지 않는다. 오래된 정보를 숨기지 않고 솔직하게 알린다. 시트 아래 "정보 출처: 카카오맵"은 그대로 둔다.
- **R49 4명+면 전화 먼저.** 인원이 4명+이고 펼친 결과 카드의 가게에 전화번호가 있으면(R13 단건에만 있다 — 카드를 펼칠 때 이미 부르므로 추가 비용 없음) 펼친 내용의 행동 맨 위(상태·강점 바로 아래, 링크 줄 위)에 틴트 버튼 "전화로 자리 확인"(`tel:`, 숫자와 `+`만 남김; `web/format.ts`의 `telHref`·`callFirst`)을 첫 행동으로 보여준다. 4명+이면 단건을 받는 동안 그 자리에 같은 높이의 스켈레톤을 두어 버튼이 들어올 때 아래 내용이 밀리지 않게 하고, 받은 뒤 전화번호가 없거나 받지 못하면 그 자리만 빠진다. 그 밖에는 예전과 같다.
- **R50 시간대 반영 (아주 약하게).** 뽑는 순간의 KST 시각으로 가중치(R21)에 배수를 하나 더 곱한다(`shared/recommend.ts`의 `timeOfDayFactor`, `drawTrio`의 `now`). 11:55 ≤ 시각 < 13:30이면 `1 + 0.25 × (1 − 도보 분 / 이번 뽑기 후보(완화 후보 포함) 중 가장 먼 도보 분)`(가까울수록 조금 더), 11:20 전이면 `1 + 0.15 × clamp(평점 − 3.5, 0, 1.5) / 1.5`(평점 높을수록 조금 더). 그 밖의 시간, 도보·평점을 모르면 1이라 예전과 같다. 웨이팅 데이터는 없으므로 화면 문구는 없다.

### 5.5.1 관리 기능

- **R31 워밍 엔드포인트.** `POST /api/admin/warm?lat&lng&radius`(관리용이라 임의 좌표를 받는다)는 `Authorization: Bearer {ADMIN_TOKEN}`이 맞을 때만 동작하고, 틀리면 401이다. R10 예산 안에서 격자 수집과 상세 보충을 한 번 수행하고 `{incompleteTiles, pending, enriched, failed}`를 반환한다. `pending`을 세려고 격자 전체를 다시 훑지 않는다(R38): 이번에 처리한 상세가 배치(`DETAIL_BATCH_SIZE`)보다 적고 글자 예산(R10 `DETAIL_CHAR_BUDGET`)으로 남긴 곳이 없고 예산이 남았고 쿨다운 중이 아니면 `0`, 아니면 `"more"`다. `?count=1`일 때만 남은 수를 정확히 센다(전체 스캔). 그날 D1 읽기가 소프트 한도를 넘었으면 아무것도 하지 않고 429 `{error: "read_budget"}`를 준다. `scripts/warm.mjs`는 이 엔드포인트를 `incompleteTiles === 0 && pending === 0`이 될 때까지(최대 300회, 호출 간 1초) 반복 호출하고, 429 `rate_limited`(R36 관리자 제한)를 받으면 30초 기다렸다 같은 요청을 다시 하고(연속 3번까지, 넘으면 종료 코드 2), 429 `read_budget`(R38)이나 알 수 없는 429는 안내를 출력하고 종료 코드 2로 바로 멈춘다(`scripts/warmRetry.mjs`). 요청이 매번 새 실행이라 무료 플랜 한도 안에서 빠르게 채울 수 있다. 인자: 없으면 기본 거점(봉은사역) 1000m, `--hub <id>`, `--all`(모든 거점 차례로), 또는 `lat lng [radius]`. `scripts/audit.mjs`도 같은 인자를 받는다(`--all` 제외).
- **R35 익명 사용 이벤트.** 로그인 없이 브라우저마다 무작위 id(`crypto.randomUUID()`, localStorage `mmj:anon:v1`, 저장 불가면 이번 페이지만)와 탭 세션 id(sessionStorage `mmj:session:v1`, 30분 무활동이면 새로)만 쓴다. IP, User-Agent, 정확한 위치, 자유 입력 글자는 받지도 저장하지도 않는다. R37 개인화 상태는 여전히 서버로 보내지 않는다(이벤트는 그와 별개인 익명 집계용).
  - 이벤트(`shared/events.ts`, zod strict — 다른 키가 있으면 그 이벤트를 버림): `{t, ts, hub(거점 id), placeId?(숫자 1~15자리), props?}`. `props`는 `radius`(50m 단위), `party`(1~4), `groups`(필터 그룹 id), `priceCap`("all"|"10000"|"15000"|"20000"), `minRating`(0|3.5|4), `openOnly`, `candidates`(0~5000), `picks`(장소 id 최대 3개), `rank`(1~3), `auto`(`true`만; R39 자동 뽑기의 `draw`), `confirm`(`true`만; R47 "여기로 가자고 공유"의 `share` — R58부터 결과 카드 번호 `rank`도 같이), `relaxed`(`true`만; R41 완화로 조건 밖 가게가 섞인 `draw`·`redraw`, R58), `onboarding`(`true`만; R61 첫 접속 거점 고르기의 `hub_change`)만.
  - 타입: `app_open`(세션마다 한 번), `draw`/`redraw`(결과가 떠 있을 때 다시 뽑기; `candidates`, `picks`), `share`(공유·복사 성공 뒤; `picks`, R47 확정 공유는 `placeId`와 `confirm`), `open_kakao`(`rank`), `select_place`(목록·핀), `expand_card`(`rank`), `exclude_place`("다음부터 안 보기"; `rank`), `undo_exclude`, `share_open`(받은 `t=` 링크를 엶; `picks`), R65 `favorite_add`·`favorite_remove`(♡; `placeId`)·`restore_exclude`(내 가게 "다시 보기"; `placeId`)·`open_mine`(내 가게 열기), `hub_change`, `filter_change`(1초 디바운스, 바뀐 뒤의 필터 스냅숏; 정렬만 바꾼 것은 제외), `empty_result`(필터를 바꾼 뒤 후보 0곳).

- **R59 무료 플랜용 집계.** 30·90일 화면이 events를 매번 훑지 않게 Cron이 일별 집계(`daily_stats`, 0006)를 쓴다. 매 Cron 실행(R11 수집 뒤, 읽기 예산을 넘은 날은 건너뜀)에서 `meta.rollup_through` 다음 날부터 "지금 집계해도 되는 마지막 날"(KST 04시 이후면 어제, 전이면 그저께 — 늦게 오는 이벤트 ±10분과 R35 보관 창에 맞춤)까지, 오래된 날부터 실행마다 최대 3일(`ROLLUP_DAYS_PER_RUN`)을 집계한다. 속도 조절: 오늘(UTC) 읽기가 소프트 한도의 30%(`ROLLUP_BUDGET_SHARE`) 이상이면 하지 않고, UTC 하루에 7일(`ROLLUP_MAX_DAYS_PER_UTC_DAY`, meta `rollup_days:{UTC 날짜}`를 같은 batch에서 올림)까지만, 실패한 시도는 되돌려진 batch 밖에서 meta `rollup_failed` `{day, at, attempts, utc, utcAttempts}`를 남기고 오늘(UTC) 집계 횟수도 올리며(실패도 하루 상한에 센다), 같은 날 실패가 이어지면 1→2→4시간…(최대 24시간, `rollupRetryMs`) 뒤에 다시 하고, UTC 하루에 3번(`ROLLUP_MAX_FAILURES_PER_UTC_DAY`) 실패하면 그날은 더 하지 않는다(성공하면 같은 batch에서 지운다). 30% 가드는 하루 중 읽기가 쌓인 뒤에 자주 걸리므로, 어제 집계는 흔히 09:00 KST(UTC 자정) 초기화 뒤 첫 실행으로 미뤄진다 — 그동안 어제는 최근 2일 실시간 창 안이라 대시보드가 실시간으로 센다(04시 전과 같다). 처음이면 보관 중인 가장 오래된 이벤트 날(최대 90일 전)부터, 이벤트가 없으면 커서만 둔다. 따라잡은 뒤에는 meta 한 문장(4키)만 읽는다. 하루 = D1 batch 한 번(그날 행 지우기(코호트 제외) → `anon_first_seen` 갱신 → 지표 4문장 `INSERT … SELECT` → 수집 시작일 표시 → (마지막 날이면) 코호트 다시 세기 → 커서 → 집계 횟수·실패 기록 정리). 코호트는 첫 방문 기록이 하나도 정리되지 않은 주(월요일 ≥ 오늘 − 90일인 첫 주부터)만 다시 세고, 그보다 오래된 주는 마지막 값을 그대로 둔다(정리로 인원이 줄어든 값으로 덮지 않게) — 중간에 실패하면 그날 전체가 되돌아간다. `anon_first_seen`은 그날 `app_open`한 id마다 없으면 넣고, 있으면 (첫 방문일 + n일 이후) 재방문 비트와 `last_day`만 바뀔 때 쓴다(`ON CONFLICT … WHERE`). 이벤트 수집 경로(R35)에는 아무것도 더하지 않는다. 보관: R35 정리 창에서 `last_day`가 90일 지난 첫 방문 기록, 400일(`DAILY_STATS_RETENTION_DAYS`) 지난 집계, 지난 UTC 날의 집계 횟수 키를 지운다. D1은 `UNION ALL` 한 덩어리에 SELECT 5개까지만 받아서 열을 행으로 펼 때는 VALUES × CASE, 이벤트 하나에서 여러 행을 낼 때는 `json_each(json_array(…))`를 쓴다.
  - Cron 마지막 실행 요약(`meta.cron_last`)은 R38 사용량 UPSERT와 같은 한 문장으로 쓴다(사용량은 더하고 요약은 바꿔 쓴다, 실행당 쓰기 +1행).
  - `GET /api/admin/dashboard?tab=overview|behavior|ops&from&to&hub=all|{id}&compare=0|1&fresh=0|1`(R31·R36과 같은 인증·`ADMIN_LIMITER`; 틀린 탭·날짜·거점, 미래, 뒤집힘, 90일 초과, 1년 전보다 앞이면 400 `invalid_params`; 기본 최근 7일·전체·비교 켬). 탭 하나에 필요한 것을 한 응답으로 준다(`shared/dashboard.ts`의 `OverviewData`·`BehaviorData`·`OpsData`, 날마다 출처 `sources`: `rollup` | `live` | `missing`). 읽는 것: 집계를 마친 날은 `daily_stats`를 기본 키로 콕 집어(`day IN json_each`, `hub IN …`, 필요하면 `metric IN …`) — 행태 탭은 일별 행을 가져오지 않고 SQL이 지표마다 합치고(`sum(value) … GROUP BY metric`) 가게는 종류마다 접두어 범위로 상위 30곳만 받는다(90일이어도 Worker로 오는 행은 ~100개, 로컬 workerd 측정 3ms), 아직 집계하지 않은 최근 2일(오늘, 새벽 4시 전이면 어제도)만 같은 SQL로 실시간, 그보다 밀린 날은 `missing`(세지 않는다). 실시간 집계는 core(세션·이벤트 수 — 개요·행태)와 detail(필터·가게 — 행태만)로 나눠 날·부분마다 5분 엣지 캐시(탭·거점 공용), 오늘 D1 읽기가 소프트 한도의 절반 이상이면 새로 세지 않는다 — 그 날·부분이 이미 캐시에 있으면 그대로 쓰고(읽기 0), 없으면 `missing`. 거점별 데이터 상태는 15분 엣지 캐시이고 같은 가드를 넘으면 캐시에 없을 때 계산하지 않는다(`hubs: null`), 운영 탭의 오늘 이벤트 수는 `idx_events_day` count. 응답 전체는 (탭, 기간, 거점, 비교)마다 60초 엣지 캐시(`fresh=1`이면 응답·거점 상태 캐시를 건너뛴다), 브라우저에는 `no-store`. 캐시 판(`DASHBOARD_CACHE_VERSION`)은 응답 모양이 바뀌면 올린다(지금 2). 내부 캐시 키(`https://cache.mmj/admin/…`)에 넣는 응답은 `cache-control: public, max-age=N, s-maxage=N`이어야 한다 — Workers Cache API는 `private` 응답을 저장하지 않는다(만료는 `x-mmj-expires`로 직접 본다). R52 개발 서버(읽기 전용)에서도 이 API는 읽기만 해서 그대로 동작한다.
- **R60 운영 조작과 예산.** 관리 화면 조작은 기존 관리 API(R31 warm, R12 backfill)만 부른다(새 쓰기 엔드포인트 없음). 화면이 잠그는 선(90%)과 서버의 429(소프트 한도)가 겹으로 막는다. 대시보드 읽기 추정은 §9.1.
- **R32 감사 엔드포인트.** `GET /api/admin/audit?lat&lng&radius`(같은 인증)는 §7의 Q1~Q4 수치를 JSON으로 반환한다. `scripts/audit.mjs`는 이를 표로 출력하고, Q1 또는 Q2를 통과하지 못하면 종료 코드 1로 끝난다.

- **R33 대표 사진.** 상세 응답의 `summary.main_photo_url`이 카카오 CDN(`*.kakaocdn.net`) 주소면(http/https만, 사용자 정보나 포트가 붙은 주소는 거부) https로 바꿔 `places.photo_url`에 기록한다(사진 파일은 저장하지 않음). 다른 호스트(네이버 블로그 등 외부 사이트에서 막히는 이미지)는 기록하지 않는다. 화면에서는 카카오 썸네일 서버(`img1.kakaocdn.net/cthumb/local/C{px}x{px}.q50/?fname=`)를 거쳐 결과 카드 상단과 목록 썸네일로 보여주고, 사진이 없거나 불러오지 못하면 사진 자리를 숨긴다.
- **R34 근처 상위 N%.** 지금 거점·반경의 전체 목록(R12 1000m 응답 중 화면 반경 안, 사용자 필터 적용 전)에서 평점이 있는 가게끼리 리뷰 수로 보정한 평점(R51) 순위를 매긴다(같은 점수는 더 좋은 순위를 함께 쓴다). `top = max(1, ceil(순위 / 대상 수 × 100))`이 30 이하이고 **리뷰가 20개 이상**(`REASON_MIN_REVIEWS`, R46 "평점 최고"와 같은 문턱)인 가게만 목록 행과 결과 카드의 사실 줄에 옅은 포인트 알약 "근처 상위 15%"를 단다. 리뷰가 20개 미만이거나 수를 모르는 가게도 대상 수·평균·순위 자리에는 그대로 들어가고(R51) 알약만 달지 않는다. 순수 함수 `shared/rank.ts`의 `topPercents`.
- **R51 리뷰 수 보정 평점 (순위 계산에만).** R34 순위는 원래 평점 대신 베이지안 평균 `(v × R + m × C) / (v + m)`으로 매긴다: v = 리뷰 수(없으면 0), R = 평점, C = 같은 대상(반경 안, 평점 있는 곳)의 평점 평균, m = 20(`RANK_PRIOR_REVIEWS`). 리뷰 6개짜리 5.0점이 리뷰 300개짜리 4.6점보다 위에 오지 않게 한다. 예전의 "리뷰 5개 이상" 문턱은 이 보정이 대신한다(리뷰가 적은 곳은 빼지 않고 지역 평균 쪽으로 끌어당긴다). 리뷰가 20개 미만(없거나 0개 포함)인 곳은 대상 수·평균 C·순위 자리에는 들어가지만 자기 "근처 상위 N%" 알약은 달지 않는다(근거가 별점 몇 개뿐이라; 리뷰 6개짜리 5.0이 순위 안에 들어도 알약은 없다). 화면에 보이는 별점은 원래 값 그대로이고, 뽑기 가중치(R21)는 바꾸지 않는다.
- **R64 "모먹죠는 이렇게 골라요" 설명.** 결과 시트(직접 뽑은 3곳과 공유받은 후보 시트 모두) 제목 옆에 조용한 ⓘ 버튼(보이는 아이콘 18px, 누르는 영역 44px, `aria-label="모먹죠가 고르는 방법"`)을 둔다. 누르면 같은 모양의 작은 바텀 시트(데스크톱은 가운데 창)가 "모먹죠는 이렇게 골라요"와 해요체 다섯 줄을 보여준다(`web/pickInfo.ts`, `web/components/PickInfo.tsx`): ① 고른 조건(반경·인원·카테고리·예산·평점·영업 중)에 맞는 곳만 후보 — `filterPlaces`, ② 평점이 높고 리뷰가 많을수록 더 잘 뽑히고 인원(혼밥·단체)과 점심 시간대도 조금 반영 — `weightOf`·`timeOfDayFactor`(R50), ③ 최근 보거나 간 곳과 최근 고른 종류는 잠시 덜 나오고 3곳은 되도록 서로 다른 종류 — R37 배수·R40 피로도·`SAME_GROUP_FACTOR`, ④ 맞는 곳이 3곳보다 적으면 평점→예산→카테고리→반경 순으로 조건을 풀고 '조건 밖'으로 표시 — R41 `relaxToFill`(테스트가 문구 순서와 `RELAX_ORDER`의 일치를 고정), ⑤ 추천에 쓰는 기록(본 곳·고른 종류)은 이 기기에만 남고, 익명 사용 통계(R35, 가게 id 포함)는 따로 모은다고 밝힘 — R37·R35. (Safari는 버튼 클릭에 포커스를 주지 않아 닫은 뒤 ⓘ로 포커스가 돌아가지 않을 수 있다 — 알려진 한계) 닫기는 ✕·바깥(어두운 배경)·Esc·아래로 끌기이고, 열면 제목에 포커스를 두고 뒤 화면은 `inert`, 닫으면 ⓘ로 포커스를 돌려준다. 설명 시트가 떠 있는 동안 Esc는 그 시트만 닫는다(결과 시트는 그대로). 움직임 줄이기 설정은 기존 시트 규칙을 따른다. 새 분석 이벤트는 없다.
- **R65 "내 가게" — 즐겨찾기·최근 열어 본 곳·뺀 곳 되살리기 (기기 안에서만).** 필수 입력은 늘리지 않고 주 흐름(역 → 모먹죠? → 3곳)에 단계를 더하지 않는다. 저장은 R37과 같은 localStorage `mmj:personal:v1`에 `favorites`(id → 넣은 시각만, 최대 100곳 — 넘치면 오래된 것부터)와 `snapshots`(id → `{name, group, cat?, lat, lng, at}` 이름 기억)를 더한다(예전 저장값은 빈 값으로 읽는다). 즐겨찾기·뺀 곳·최근 신호는 id와 시각만 오래 남는다. 이름 기억은 §3.1 기기 저장본 규칙대로 3일(`SNAPSHOT_MAX_AGE_MS = PLACES_CACHE_MAX_AGE_MS`, 테스트로 묶음)이 지나면 쓰지도 남기지도 않는다(읽을 때·바꿀 때마다 정리, `pruneSnapshots`·`freshSnapshot`; 읽을 때 버린 것이 있으면 정리한 값을 바로 한 번 저장한다 — `tidyPersonal`). 이름 기억의 시각은 그 정보를 받은 때다: 기기 목록 저장본(R45)에서 온 이름이면 그 저장 시각(`placesDataAt`, 2.9일 된 저장본이면 0.1일 뒤에 지난다), 새로 받은 목록·단건이면 받은 때 — 오래된 정보로 더 새 이름을 덮거나 3일을 다시 늘리지 않는다. ♡로 넣을 때·카카오맵 열기·공유·"다음부터 안 보기" 때 남기고, 그 곳이 새로 받은 거점 목록이나 단건(R13 — 카드·공유·내 가게) 응답에 나오면 새로 한다(내 가게가 가리키는 곳만, 1시간 안에 같은 값으로 새로 했으면 그대로 — `refreshSnapshots`, 요청을 더 하지 않는다). 즐겨찾기·뺀 곳·최근 30일 카카오맵/공유 어디에서도 가리키지 않으면 버리고 200곳을 넘으면 즐겨찾기는 지키고 오래된 것부터 버린다. 파싱은 R37처럼 틀린 항목만 버린다(id 숫자 1~15자리, 좌표·시각 유한수, 이름 80자, cat 30자). 뽑기: 즐겨찾기는 ×1.3(`FAVORITE_BOOST`, 최근 신호·그룹 가산·피로도와 곱한다 — 방금 간 즐겨찾기도 며칠은 쉰다), 뺀 곳은 0, 뺀 곳을 ♡로 넣으면 "다음부터 안 보기"가 풀린다. 즐겨찾기에서 "다음부터 안 보기"를 하면 즐겨찾기에서도 빠지고(두 목록에 함께 있지 않다), 8초 "되돌리기"는 빼기를 풀고 즐겨찾기도 원래 시각 그대로 돌려 놓는다(`undoExclude`). 내 가게 "다시 보기"는 빼기만 푼다. 순수 함수 `shared/personal.ts`·`shared/mine.ts`.
  - ♡(`HeartButton`, 44px, 빈 하트 `aria-label="즐겨찾기에 넣기"` / 찬 포인트색 하트 "즐겨찾기에서 빼기", `aria-pressed`): 목록·핀 카드는 제목 덩어리 오른쪽, 결과 카드는 펼쳤을 때 첫 줄(영업·시간·리뷰) 끝(접힌 줄은 이미 꽉 차서). 행동 줄은 그대로. 누르면 "즐겨찾기에 넣었어요" / "즐겨찾기에서 뺐어요".
  - 헤더 거점 칩 왼쪽에 조용한 하트 버튼(`aria-label="내 가게"`, 44px). 거점 칩은 남은 폭 안에서 말줄임한다(360px에서 동대문역사문화공원역은 그대로 다 보인다). 누르면 거점 고르기와 같은 바텀 시트(데스크톱은 가운데 창, 위쪽은 토스트 자리로 비움) "내 가게": "즐겨찾기"(최근 넣은 것부터), "최근 열어 본 곳"(30일 안 카카오맵·공유, 최근 것부터 한 번씩, 즐겨찾기·뺀 곳 빼고 최대 20곳; 설명 "카카오맵을 열었거나 공유한 곳이에요"), "뺀 곳"(최근 것부터, "다시 보기" → 되돌리고 "{이름}을/를 다시 뽑아요" — `objectParticle`). 빈 묶음은 숨기고, 셋 다 비면 마스코트 + "아직 모은 가게가 없어요" / "카드의 ♡를 누르면 여기 모여요". 줄: 이름 + "{세부 종류} · {1.2km 안 가장 가까운 공개 역} 근처"(멀면 종류만). 이름은 지금 목록 → 3일 안의 이름 기억 순. 둘 다 없는 곳은 시트를 열 때 한 시각이 최근인 것부터 최대 30곳(`unresolvedIds`)을 단건(`GET /api/places/:id`)으로 3곳씩 불러와 이름을 기억하고(실패는 조용히 넘김, 닫으면 멈춤), 이번 세션에 못 찾은 곳은 메모리에 기억해 다시 부르지 않는다. 그동안 이름 자리는 뼈대(읽기 도구에 "불러오는 중", 누르면 기다림, 뺀 곳의 "다시 보기"는 누를 수 없음), 못 찾으면 즐겨찾기·최근은 "이전에 담은 가게", 뺀 곳은 "이전에 뺀 가게".
  - 줄을 누르면: 지금 거점 목록에 있으면 닫고 그 카드를 연다(목록·핀과 같다). 없으면 1km 안의 공개 역으로 옮기고 그 목록이 오면 연다(그 목록에도 없으면 R13 단건, 실패하면 "가게 정보를 불러오지 못했어요"). 가까운 역이 없으면 카카오맵 장소 페이지를 새 탭으로. 닫기는 ✕·바깥·Esc(이 시트만)·아래로 끌기, 열면 제목에 포커스·뒤 화면 `inert`, 닫으면 하트 버튼으로 포커스. ♡ 빼기·"다시 보기"로 누른 줄이 사라지면 포커스는 그 묶음의 다음 줄 → 묶음 제목 → 시트 제목.
- **R42 거점당 1000m 한 번만 받기.** 화면은 반경과 상관없이 거점의 1000m 목록(`/api/places?hub&radius=1000`)을 거점마다 한 번 받고, 반경은 `filterPlaces`가 거리로 거른다. 반경을 바꿔도 다시 요청하지 않아 슬라이더가 즉시 반응한다. 서버도 다른 반경 요청을 같은 1000m 본문·같은 캐시 키로 답해서(R12) 캐시 키가 거점 수(5개)뿐이다. 대신 첫 응답이 커진다(§9.1). R34 순위는 반경 안 목록으로 브라우저에서 다시 계산한다(서버는 순위를 계산하지 않는다). 반경을 바꾸면 결과 3곳은 지금처럼 비운다(R22).

### 5.6 UI

- **R27 레이아웃 (모바일 우선).** 대부분 폰으로 열기 때문에 375×812를 기준으로 설계하고, 900px 이상에서 데스크톱 배치로 바꾼다. 상단 바에는 로고와 거점 칩이 있다.
  - 모바일: 상단 바 → 지도(화면 높이의 40%) → 패널(필터, 상태 줄, 리스트; 패널만 스크롤). 뽑기 버튼은 화면 하단에 고정된 바에 있고 `env(safe-area-inset-bottom)`만큼 띄운다. `viewport-fit=cover`를 쓰고 노치와 홈 인디케이터 영역을 피한다.
  - 데스크톱(≥ 900px): 왼쪽 패널(400px; 필터, 상태 줄, 리스트, 패널 아래에 붙는 뽑기 버튼) + 오른쪽 지도.
  - 반경 슬라이더("거리"), 인원, 카테고리("전체" 칩 포함)는 항상 보인다. 1인 예산, 최소 평점, 영업 중만, 술집 포함은 접이식 "상세 조건"(`<details>`)에 넣고, 접힌 줄에 현재 값을 한 줄로 요약한다(예: "예산 전체 · 평점 무관 · 영업 중만").
  - 터치 대상은 44px 이상, 입력과 선택 상자의 글자는 16px 이상이다(iOS 자동 확대 방지). 마우스 hover에만 기대는 동작은 없다.
- **R28 지도와 상세 카드.** 카카오맵 JS SDK를 쓴다. 거점 핀, 반경 원(점선 `dash`), 후보 가게 핀(필터를 통과한 곳만, HTML 버튼 CustomOverlay, 탭 순서에서는 뺀다 — 같은 가게를 목록에서 키보드로 고를 수 있다)을 보여준다. 거점이나 반경이 바뀌면 원이 여백을 두고 화면에 들어오게 맞춘다. 선택된 핀은 커지면서 한 번 퍼지고 가게 이름 라벨을 단다. SDK는 한 번만 불러오고 10초 안에 준비되지 않으면 "지도를 불러오지 못했어요"와 "다시 시도"를 보여준다.
  - 카카오 로고·축척(약관상 가리면 안 된다): 모바일 바텀 시트(결과 3곳·상세 카드)가 지도 칸 아래쪽을 덮으면 지도 컨테이너를 시트 윗변까지 줄여(`relayout`; 그 뒤 선택한 핀·펼친 후보가 있으면 그 핀으로 다시 `panTo`, 3곳 맞추기 중이면 다시 맞추고, 사용자가 끌었거나 따라가던 곳이 없으면 지도 내용은 위쪽 기준으로 제자리 — `coverFollow`. 바꾸기 전 가운데로 `setCenter`하면 진행 중인 `panTo`가 끊긴다) 로고·축척이 시트 바로 위에 보인다. 지도는 최소 40px 남긴다(`web/mapCover.ts`). 데스크톱은 결과·상세 오버레이가 지도 왼쪽 아래를 덮으므로 로고·축척을 오른쪽 아래로 옮긴다(`setCopyrightPosition(BOTTOMRIGHT)`).
  - 평점 색(목록 행·결과 카드·상세 카드·지도 칩): 4.0 이상만 강조색(별 `#FF683D`, 숫자 `#B93D14`), 그 아래는 칭찬처럼 보이지 않게 차분한 글자색(별 `#7A6758`, 숫자 `#6B5A4C`; 별 기호는 그대로). 기준은 `web/format.ts` `RATING_HIGH`·`ratingTone`(지도 `.pin--top`과 같은 기준).
  - 칩 겹침: 가까이 본 지도(레벨 3 이하는 전부, 레벨 4는 평점 4.0 이상·선택한 핀만)에서 화면 안 칩이 서로 덮으면 선택한 핀 → 평점 높은 순 → 리뷰 많은 순으로 하나만 남기고 나머지는 점으로 그린다. 뽑힌 핀의 번호 배지와 보이는 이름표, 선택한 핀의 이름표도 피한다. 단, 선택한 핀의 칩은 번호 배지나 이름표 위에 걸쳐도 점으로 바꾸지 않고 남긴다. 확대·이동이 끝났을 때와 핀·결과가 바뀔 때 다시 계산한다(`shared/labels.ts` `keptChips`).
  - 핀이나 리스트 항목을 누르면 그 한 곳의 상세 카드를 열고 지도가 그 핀으로 이동한다(뽑기 결과 3곳은 R22). 모바일은 뽑기 바 바로 위에 붙는 바텀 시트(최대 화면 높이의 60%, 내부 스크롤, 스크롤해도 위에 붙어 있는 손잡이(끌어 내리면 닫힘), 닫기 버튼)이고, 데스크톱은 지도 위 오버레이다. 카드가 열리면 닫기 버튼으로 초점을 옮기고 Esc로 닫는다(카드 자체는 `aria-live`가 아니다). 목록 응답에는 메뉴가 3개뿐이라 카드를 열면 R13을 한 번 불러 전체 메뉴로 바꾼다.
  - 카드 정보 순서: 이름 → 도보 N분 · ⭐평점(리뷰 수) · 영업 상태("영업 중" / "곧 마감" / "지금 닫힘" / "영업 정보 없음"; 닫혔거나 30분 안에 닫으면 포인트 컬러) → 카테고리 · 대표 가격 · 강점 → 메뉴(모바일은 3개 + "메뉴 더보기", 데스크톱은 최대 5개) → 행동("공유"(이 한 곳, R23), "카카오맵" 링크) → 작게 "정보 출처: 카카오맵". 상세 정보가 없는 가게(R13)는 평점과 메뉴 대신 "평점과 메뉴 정보를 아직 불러오지 못했어요"를 보여준다.
- **R29 로딩과 상태 표시.** 거점이 바뀌면 250ms 디바운스 후 요청하고(반경은 다시 요청하지 않는다, R42), 다시 불러오는 동안 이전 리스트를 흐리게 보여준다.
  - 첫 응답 전에는 리스트 자리에 스켈레톤 4줄과 "주변 식당을 찾고 있어요"를 보여준다.
  - `pending > 0`(`detailsPaused` — R10 쿨다운·R44 frozen — 이면 제외) 또는 `incompleteTiles > 0`이면 10초 → 12초 → 15초(이후 15초) 간격으로 최대 5번(약 67초) 다시 요청하고(첫 폴링은 pending 응답의 10초 엣지 캐시가 끝난 뒤)(`web/pollSchedule.ts`), 리스트 위 상태 줄에 "주변 가게를 더 찾는 중이에요"(incompleteTiles) 또는 "평점 정보 불러오는 중 (n곳)"(pending)을 표시한다. 5번이 끝났는데도 남아 있으면 "주변 가게를 다 찾지 못했어요" 또는 "n곳은 아직 정보를 못 불러왔어요"로 바꾼다. 다시 요청하는 중에 후보가 0개면 빈 상태 대신 스켈레톤을 유지한다.
  - `stale`이면 "정보가 오래됐을 수 있어요"를 표시한다.
  - R44: frozen이거나 가장 최근 상세가 8일보다 오래됐으면 "평점·메뉴는 N일 전 기준이에요"(frozen이면 pending 안내보다 먼저).
  - R63: 상태 줄 아래에 조용한 한 줄 "가게 정보 10월 6일(월) 업데이트 · 매주 월요일"(응답의 `refreshedAt` 날짜(KST)와 `refreshDay`, 한 번도 다 갱신하지 않았으면 "매주 월요일 업데이트"). 갱신 중에는 지난 완료 날짜 그대로다. 펼친 카드의 "N일 전 확인"(R48)은 그대로. 다른 거점 목록이 남아 있는 동안은 숨긴다.
  - 첫 요청이 실패하면 "가게 정보를 불러오지 못했어요"와 "다시 시도" 버튼을 보여준다. 이미 리스트가 있는데 다시 요청이 실패하면 리스트는 두고 상태 줄에 "최신 정보를 불러오지 못했어요"와 "다시 시도"를 보여준다.
  - 후보가 0개면 "점심시간이 코앞인데 후보가 없네요"와 조건 풀기 버튼(R21)을 보여준다.
- **R30 시각 스타일.** 라이트 모드만 지원한다. 웹 페이지가 아니라 앱처럼 보이게 한다(`.superpowers/research/app-feel.md`): 테두리 대신 옅은 면과 구분선, 주 행동은 화면에 하나, 이모지 대신 마스코트와 선 아이콘.

## 6. 에러 처리 요약

| 상황 | 동작 | 요구사항 |
|---|---|---|
| 비공식 API 실패 | 재시도 2회 → `failed` 기록 → 6시간 후 재시도. UI는 "평점 정보 없음" | R9 |
| 비공식 API 구조 변경 | zod 실패 → `failed/schema`, 계약 테스트로 조기 발견 | R6 |
| 비공식 API 차단 | 로컬 수집 스크립트 + D1 원격 적재로 전환 | §3.2 |
| 공식 API 실패 | 만료된 캐시로 응답, `stale: true` / 캐시도 없으면 502 | R14 |
| 요청 과다 | 캐시로만 응답 | R15 |
| 후보 0개 | 안내 + 켜진 조건 풀기 버튼(반경 +300m 포함) | R21, R29 |
| 공유된 가게 일부 없음 | 찾은 곳만 보여주고 "N곳은 찾지 못했어요" 한 번 | R23 |
| localStorage 불가 | 기본값으로 동작, 개인화는 이번 세션만 | R25, R37 |

## 7. 데이터 품질 수용 기준

`npm run audit`(D1 원격 또는 로컬 대상)은 거점(기본 봉은사역, `--hub <id>`) 반경 1000m 데이터에 대한 리포트를 출력한다.

- **Q1 누락 없음.** `saturated = 1`인 격자가 0개.
- **Q2 상세 커버리지.** 덮는 격자에 기록된 장소 ID 중 표시 정보를 가진 장소가 95% 이상. 실패한 장소는 목록과 `fail_reason`을 출력한다. Q3, Q4도 같은 ID 집합을 기준으로 한다.
- **Q3 필드 결측률.** ok인 가게 중 rating, price, hours가 각각 null인 비율을 출력한다. 기준치는 없고, 하나라도 50%를 넘으면 파서 버그를 의심해서 픽스처와 대조한다.
- **Q4 분포와 이상치.** 그룹별 가게 수, `etc`로 떨어진 카테고리 2단계 값 목록, 좌표가 유효 범위(lat 33~39, lng 124~132) 밖인 가게 수, 이름과 좌표(소수 5자리)가 같은 중복 의심 묶음 수를 출력한다.
- **Q5 표본 검증.** 직접 고른 근처 가게 10곳을 카카오맵 화면과 대조해 평점(소수 첫째 자리), 메뉴 가격, 영업시간이 일치하는지 확인한다(수동, 결과를 `docs/audit/`에 기록).

Q1, Q2, Q5를 통과해야 UI 마일스톤으로 넘어간다.

- 바인딩: D1 `DB`, Rate Limiting `RATE_LIMITER`(namespace 1001, 분당 10회)·`ADMIN_LIMITER`(namespace 1002, 분당 120회, R36), 시크릿 `KAKAO_REST_KEY`·`ADMIN_TOKEN`, 변수 `SUBREQUEST_BUDGET`, `DETAIL_BATCH_SIZE`(운영 4, 채우기 부스트 동안 6), `DETAIL_ONLY_EXTRA`(R63 채우기 부스트, `"1"`이면 짝수 분도 상세만 보충), `DETAIL_CHAR_BUDGET`(운영 200000, 없으면 600000 — R10), `D1_READ_SOFT_CAP`(R38, 기본 3000000), `D1_WRITE_SOFT_CAP`(R35, 기본 60000)
- `compatibility_date`는 `2026-08-01`(로컬 workerd가 지원하는 최신 날짜 이하)
- 프론트엔드 환경 변수: `VITE_KAKAO_JS_KEY` (공개 키)
- Custom Domain: `mmj.itmz.me`
- D1 마이그레이션 `0001`~`0007`은 배포 전에 운영 D1에 적용한다(`npm run db:migrate:remote`). `0005`(places.list_json)는 열 추가뿐이고, 코드는 값이 NULL인 행을 그대로 처리한다(열 자체는 있어야 한다). `0006`(R59 `daily_stats`·`anon_first_seen`)은 표 추가뿐이고 기존 표는 그대로다 — 없으면 Cron 집계(로그만 남기고 넘어감)와 대시보드 API가 실패하니 코드보다 먼저 적용한다. `0007`은 표 추가뿐이다 — 표가 없으면 상세 저장(같은 batch의 표시)과 목록 미스가 실패하므로 코드보다 먼저 적용한다. 배포 뒤 스냅샷은 스냅샷 Cron(`2-59/5`, wrangler.jsonc `triggers.crons`의 두 번째 — 무료 플랜 계정당 Cron 5개 중 하나를 더 쓴다)이 실행마다 한 거점씩 채운다(거점 5곳이면 약 25분).
- **R52 개발 서버는 운영 D1을 읽기만 한다.** D1 바인딩이 `"remote": true`라서 `npm run dev`(vite dev)도 운영 D1에 붙는다. `vite.config.ts`가 dev 서버(`command === "serve"`)에서만 Worker 변수 `READ_ONLY=1`을 더하고(`wrangler.jsonc` `vars`에는 없다 — `vite build` 결과 `dist/momeokjo/wrangler.json`과 운영에는 이 값이 없다), Worker 입구(`worker/index.ts`)가 그때 `DB`를 `readOnlyDb`(`worker/readOnly.ts`)로 감싼다. 감싸개는 문장의 첫 키워드(주석·공백·`WITH ...` CTE를 건너뛰고)가 SELECT·VALUES·EXPLAIN·읽기 PRAGMA가 아니면 `prepare`·`batch`에서 실행 전에 오류를 낸다(빠뜨린 쓰기의 안전망). `exec`는 분류하지 않고 항상 막는다 — D1 `exec`는 줄바꿈으로 문장을 나눠 실행하므로 SQL 분류를 믿을 수 없고, 앱은 `exec`를 쓰지 않는다. `READ_ONLY`는 비어 있지 않고 `0`·`false`가 아닌 값이면 켠다(실패하면 닫힘). 켜져 있으면 격리(isolate)마다 첫 요청에서 `[read-only] 운영 D1 읽기 전용 모드`를 한 번 로그에 남긴다. 앱은 쓰기 경로를 먼저 건너뛴다: 목록은 만료된 격자를 수집하지 않고 상세 보충도 하지 않으며(`incompleteTiles` 0, `detailsPaused` true — 화면이 폴링하지 않는다), 단건은 저장된 행이 없으면 상세를 받아 보여주기만 하고 성공·실패를 저장하지 않는다. 요청별 D1 사용량 UPSERT(R38)를 하지 않고, `/api/events`는 아무것도 저장하지 않고 204, 관리자 쓰기(`/api/admin/warm`·`/api/admin/backfill`)는 403 `{error: "read_only"}`, Cron은 로그 한 줄만 남기고 아무것도 하지 않는다. 목록·단건·통계 읽기와 응답 캐시는 그대로다. **dev 서버가 읽은 행도 운영 계정의 하루 읽기 한도(5,000,000행)에 그대로 들어가고, 사용량 기록을 하지 않으므로 R38 소프트 한도 집계에는 잡히지 않는다.** `vite preview`는 빌드 결과 설정을 쓰므로 이 값이 없고, 그대로면 `"remote": true`로 운영 D1에 쓰기까지 붙으므로 `vite.config.ts`가 preview(`isPreview`)에서 `cloudflare({ remoteBindings: false })`로 원격 바인딩을 끈다(비어 있는 로컬 D1을 쓴다; 플러그인은 preview 분기보다 먼저 `remoteBindings`를 읽는다). 옵션 선택은 `scripts/cloudflareOptions.mjs`에 있고 단위 테스트한다(serve=READ_ONLY, build=없음, preview=원격 끔). **`wrangler dev`는 이 설정을 거치지 않고 `"remote": true` 그대로 운영 D1에 읽기·쓰기로 붙는다 — `--local`을 붙여서만 쓰거나 아예 쓰지 않고, 개발은 `npm run dev`로 한다.**
- **되돌릴 때(R56):** 스냅샷 전 판으로 되돌리면 그 판은 상세 저장·격자 변경에서 더러움 표시를 올리지 않아서, 다시 이 판으로 올리면 되돌린 동안 만들어진 변화가 남은 스냅샷(최대 2시간)에 빠져 있다. 되돌린 뒤(또는 다시 올리기 전)에 스냅샷을 비운다: `npx wrangler d1 execute momeokjo --remote --command "DELETE FROM hub_snapshots"` (지우면 엣지 10분 뒤부터 지금 경로로 답하고 스냅샷 Cron이 다시 채운다).
- **카카오 개발자 콘솔 (2026-10-05 완료):** 앱 "모먹죠"(ID 1597800) 생성, JavaScript SDK 도메인에 `http://localhost:5173`·`https://mmj.itmz.me` 등록, 카카오맵 활성화(계정의 무료 쿼터가 이 앱에 귀속됨). 키는 `.dev.vars`(REST)와 `.env.local`(JS)에 있고 git에서 제외된다.

R38 가드는 그날 읽기가 3,000,000행(60%)을 넘으면 수집을 멈춰서 목록 서비스에 2,000,000행을 남긴다. 집계는 요청이 끝난 뒤에 더하므로 동시에 도는 warm 몇 회만큼 넘칠 수 있다.
R38 읽기 예산을 넘은 날에는 R56 스냅샷도 다시 만들지 않는다 — 남은 스냅샷이 만료(2시간)되면 그날 캐시 미스는 지금 경로(미스마다 수천 행)로 답한다.

캐시 미스 응답의 CPU는 예전에는 JSON 열 parse·stringify가 대부분이라 큰 거점(동대문)에서 10ms를 넘기 쉬웠다. 지금은 상세를 저장할 때 만든 목록 조각(`places.list_json`, 0005)을 이어 붙여 ~2ms로 어림한다(측정: `scripts/bench-places.mjs`, `docs/perf/2026-10-06-perf.md`). 0005 전 행이 남은 배포 직후 몇 시간은 예전 경로가 섞여 느리다. 처리하지 못한 오류는 JSON `{error: "internal"}` 500으로 답하고 원인은 Workers 로그에만 남긴다. D1 한도는 매일 00:00 UTC(09:00 KST)에 초기화된다.
